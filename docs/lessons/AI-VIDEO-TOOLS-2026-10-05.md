# 2026-10-05 调研定论：AI 视频工具能不能提效

20 个子 Agent 并行调研，报告全在 `.scratch\aivideo\`。本文只记**多方独立撞在一起的结论**，
单方主张一律回原报告看。**没有并列到两条独立来源的，不写进来。**

---

## 一、判读这条路：模型只能「定位」，不能「定性」

这是本轮最重要的结论，三条独立来源指向同一处：

| 来源 | 证据 |
|---|---|
| **#20** 游戏画面 VLM 评测 | EgoEsportsQA / GameplayQA / FPS-Bench 等 7 个公开评测。**零样本天花板约 71%（GPT-5）——比「猜多数类」还低**。20 次漏判里 **18 次同型**：专把结算面板 / 战利品界面读成非战斗 |
| **#1** 长视频模型 | 云端能一次看完 19 分钟、$0.09–¥0.63。**但每帧只有 33–65 token（≈300–460px）** |
| 本项目 864 实测 | 要让红血条 / 伤害数字 / 击杀横幅可读，**一格至少 960×540**；640px 联系表 **5/5 路全误判** |

**判定**：任何「让多模态模型看片自己找战斗」的方案，天花板就在这儿。
#1 的 460px 甚至**低于本项目已实测证伪的 640px**。

**这恰好是 864 漏战的根因类别**——把战斗中开面板读成「这是面板段」，进而挖掉整段战斗。

### 落到本项目的用法

| 用途 | 能不能交给模型 |
|---|---|
| 定位候选区间（找可能开打的地方） | **可以** |
| 判断「这一段算不算战斗」 | **不可以**——要靠 §2.2.2 的因果链判据 + 身份结构判据 |
| 定性取证（这次到底算不算漏） | **不可以**——必须人/Agent 读 960px 全分辨率裁切帧 |

**原则：VLM 只排序，不裁决。**

## 二、判读的另一条腿：机器信号

`#1`/`#3` 一致：**三类「零看图判据」各能定什么、各定不了什么**

| 类型 | 能定 | 定不了 |
|---|---|---|
| 数值型（亮度 / 色度 / 音频能量 / HUD 数字） | 「变了没」「第几秒」 | **「那是谁」** |
| 结构型（ffprobe / 场景切分 / 音频活动） | 「矛盾不矛盾」 | 同上 |
| 文本型（转写 + 战斗词扫描） | 「想干啥」 | 同上 |

**所以三者互补、都不能单独裁决。** 组合起来才是「零看图」流水线。

> ⚠ **别把弹匣读数曲线当零看图判据。** 项目实测：全库无 OCR、venv 未装 PIL，
> 那 34 张图是**人眼读 8× 放大裁图**，一轮烧掉 **68% 看图预算**。

## 三、最快的路线存在，但需要游戏侧配合

`#18`：**Overwolf 环形缓冲 + 游戏事件**，出片是「过去 / 未来 / 待定」三态，**即时**。

但本项目**没做**的三件事（也就是它快的真正原因）：

1. **事件 → 毫秒时间码层**（游戏直接给时间码，不用事后判读）
2. **合并窗的量化标准**
3. **审片短名单**（不是全片审）

**可行性**：#18 认为「收编现有像素签名」可行。

**代价**：需要装游戏侧 SDK 并改采集方式，**超出当前工作流范围**。
用户明确说「我给一套提示词和素材」——这条路要他先改采集，不在这一轮。
**但它是唯一能做到「即时出片」的路线，值得单独立项。**

## 四、编排与架构

| 来源 | 结论 |
|---|---|
| **#19** skill 与提示词架构 | **编排进脚本，不进 skill**。根因实测：项目根 `skills\` 不是 opencode 发现路径，29 个 skill 全隐形 → 211 行提示词被迫当加载器。**已修**（`opencode.json`） |
| **#6** 有没有现成「一句话出片」 | **没有可直接用的**。值得借鉴的是 `json-render`「用目录自动生成提示词契约」的做法 |
| **#16** 时间线中间表示 | **不换**。OTIO 能正确表达片段内挖洞，但它是**交换容器不是校验器**。该做的是把 `episode_geometry.py` 升成校验层。实测原型 10/10 拦下 bug、35 份真实时间线零假警报 |

## 五、审片：同源重复 = 增信为零

`#14`（34 篇文献 + 91 处 arXiv 链接）独立复现了本项目的两条实测：

- 删掉 `combat_009`（233.45 s，占节目 35%）**并规规矩矩登记成删段** → `qa_gate.py` **7/7 全绿、`pass=true`**
- `combat_003` 的 `source_end=404.0` 在 v1–v5 **五版一字未改**，同期 22 份对抗审全过

**结论**：N 路看同一份冻结预览 = 只增加措辞一致性，不增加证据。
**审片要异源交叉**（每路输入源必须与别路不同）。

> `#14` 注明：web search 全程 401，直接打的 arXiv 检索页。
> 它也主动指出「`coverage_complete` 已存在，抓得到未登记空洞，抓不到登记了却不该删」——
> 与我实测的 33 份真实时间线结论一致。

## 六、被否掉的方案（别再走一遍）

| 方案 | 为什么否 |
|---|---|
| 云端视频模型全量判读 | 每帧 33–65 token，低于已证伪的 640px（#1） |
| 本地大视频模型 | 8GB 显存只跑得动 2B–4B GGUF，单请求 ~3.7 分钟、19 分钟要切 6 段，Windows flash-attn 有坑（#1/#8） |
| 换 OTIO 当中间表示 | 它是容器不是校验器，换了也不会多抓 bug（#16） |
| 现成「一句话出片」产品 | 对游戏录屏适配度不明；且**审片环节不可省**——#20 的 71% 天花板就在这里 |
| 靠看图预算提效 | 看图占总耗时 9–14%，且**放宽不会变快、可能更慢**（注意力稀释）。已决定搁置 |

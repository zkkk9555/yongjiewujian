# 效率提升计划（2026-10-05，20-Agent 调研后）

用户目标（逐字）：**「给一套提示词和素材，它就给我输出经过验收的粗剪预览片。中间过程我不管，效率最高、速度最快。」**

现状：10.9 小时/局。耗时结构：**纯等待 46.5%**、审片 17.2%、合成 7.7%、返工 4.7%、**机器重活仅 3.1%**。

---

## 一、先回答「方法是不是落后了」

**是，但只落后了两处。** 其余部分是对的，不要动。

| 环节 | 判定 | 依据 |
|---|---|---|
| **子 Agent 抽帧读图做语义裁决** | **过时** | #20 零样本天花板 ~71%（GPT-5），**比猜多数类还低**；20 次漏判 18 次同型。#5 判为过时 |
| **人守编排 + 全回收才合成** | **过时** | 46.5% 纯等待；3 路被服务重启吞掉无人换路 |
| 并行分解 + 派工 brief | **保留** | #19、#5 一致 |
| 可回放证据链 | **保留** | 本项目唯一能复盘「这段为什么留」的东西 |
| 机器门禁 | **保留，且要加** | 门禁是唯一不靠自觉的部分 |
| 时间线 JSON + 单一真源 | **保留** | #16：不换 OTIO（它是容器不是校验器） |
| 判读改级联（便宜信号全片 + 贵模型只跑候选） | **要抄** | #5 指 hypecut 模式 |

### 关键的调和：#5 说业界主流是 VLM 直读，#20 说 VLM 天花板只有 71%

两条不矛盾，**合起来就是正确用法**：

```
便宜信号全片扫（场景切分 / 音频能量 / 转写战斗词）  → 候选窗
                    ↓
        只在候选窗上跑 960px 全分辨率取证            → 定性
                    ↓
        边界与「那是谁」交给结构判据 + 因果链        → 裁决
```

**#1 的实测给出了硬边界**：云端视频模型每帧只有 33–65 token（≈300–460px），
**低于本项目 864 已实测证伪的 640px**（一格至少 960×540 才读得出红血条/伤害数字/击杀横幅）。
所以**云端模型只能定位，不能定性**。

**成本不是问题**（#9）：全量上云 ¥0.79 / $0.59；10% 抽样 ¥0.08 / $0.06。
但**上云买不到可审计性**，只配做发现器。

> **#9 的两条意外发现**
> - `E:\OBS` 实测是 **40 分钟 / 2560×1440 / HEVC / 60fps / 5.9GB**——不是文档里写的 4K。
>   任务按单局处理，但探测基线要改。
> - **OpenAI 与 Claude 全系模态里没有 video**，这条路是断的。候选只剩 Gemini / 阿里 / 字节。
> - 阿里的 `FPS_MAX_FRAMES=2000` 会**静默抽稀**且不告知——**振刀只有 0.2–0.4 秒，落空概率很高**。

## 二、抽帧：变化驱动抽帧在本网**完全失效**

**#7 实测**：逐帧 `scdet` 扫 2151 秒（90% 全片），**静态秒占比 0.0%**。
阈值降到 1.0 仍出 1.83 帧/秒，**比固定 1fps 更差**。

**真正的杠杆**：同样预算下，把「盲取整秒帧」换成「**桶内变化最大帧**」——
平均场景分 **0.2182 → 2.2473，10.3×**。代价是多一遍全片扫描（全片 1fps 网格约 76 秒）。

**#7 还算清了联系表那个 131×74 的由来**：`cell = 1568 / cols`，`cols=12` → **恰好 131×74**，
与 864 事故记录**逐位吻合**。再套 token 参考实现算出：**一张 1568px 图最多装 2 格（高分档）/ 1 格（标准档）**
——所以联系表省的是 **2× 而非 25×**。

**结论：联系表基本没用武之地了，该改 960px 单帧。**（~38 张/局，50 张预算够用）

## 三、编排：不换框架，自建

**#13 结论**：
- **LangGraph 1.2** 是唯一五件齐的（断点续跑 / 超时重试 / 人工介入 / 中断恢复 / 可观测），
  **但要求放弃 opencode 子 Agent**——代价太大。
- **Temporal** 要起 server，且**换路同样得自己写**。
- **自建够**：opencode API 已实测提供 wait / interrupt+resume / fork / revert / event 五个原语，
  **缺的只是约 300 行看门狗**。

## 四、一个很急但**与画质冲突**的问题：DB 已 14.3 GB

**我实测**：`~/.local/share/opencode/opencode.db` = **14.31 GB**，
其中 **14.21 GB 全在 `session_message.data` 的 assistant 行**（35450 行）——
子 Agent 读联系表产生的 base64。

**官方有 `media.image.max_base64_bytes`（默认 5 MiB）可以止血。**

> ⚠ **但我反对直接调低它**，理由是它和画质直接冲突：
> 本项目刚用实测证明**一格至少要 960×540 才读得出 HUD 小字**，
> 再压 base64 会让取证帧被重新压缩/降尺寸，**正好制造 864 那类误判**。
>
> **正确的解法是从源头控制**：喂进去的帧**一开始就按 960px 出**，
> 而不是让 harness 收下 2000px 再压。#7 已经证明 1568px 的图最多装 1–2 格，
> **收 2000px 的大图进 DB 本身就是纯浪费**。
>
> 已落的 14.3 GB 是沉没成本（`PRAGMA freelist=1`，没有可回收空闲页），
> **不紧急，但它会继续涨**——所以要从源头限。

**需要你点头**：是否调全局 `~/.config/opencode/opencode.json`（影响所有项目）。
我的建议是**先不动全局配置**，改为在取证脚本侧就把帧出到 960px。

### Phase 1 —— 删除段语音战斗词门（**唯一的正确性缺口**）

**为什么必须做**：我实测发现**所有已交付时间线的覆盖都是完整的**——
说明 864 那次漏战**不是「忘了声明」，而是「规规矩矩声明成删除段」**。
覆盖门抓不到这一类，**只有它能抓**。

**设计约束（#14/#09 反复强调）**：必须是**缺席审查**门
（删除段命中强战斗词 → **必须有人工裁决记录**，缺则 FAIL），
**绝不能做成**「缺席战斗」门（会产出必然出错却带 PASS 的结论）。

- 强战斗词表：已存在 `123\21.864…\shots\audit_v1\scan_voice.py`（70 词）
- 落地：`qa_gate.py` 新增 `deleted_voice_audit`

### Phase 2 —— 编排进脚本（**46.5% 纯等待的解法**）

- 状态机落 `reports\delivery_state.json`（保留区，不被清理脚本删）
- 台账是状态机的**自动投影**，不是人工填
- 超时判据：`clamp(3×本波已回收路时延 p50, 60, 240) min` 且须 ≥50% 回收才开火
- `WITHHELD` 状态 + 强制降级（缺失即显式降级，不能静默继续）
- #13 给了 API 原语清单，缺的就是 300 行看门狗

**顺序铁律**：门禁与「接线进预览链路」**必须同批**，
否则中间态就是「门存在但没人调」——那正是今天的现状。

### Phase 3 —— 定位改级联

- 合并裁定降级成「读曲线」（#12：**边界定不了，±clip 长度，短战斗 mAP 仅 5.39**）

### Phase 4 —— 提示词瘦身 + 异源审片

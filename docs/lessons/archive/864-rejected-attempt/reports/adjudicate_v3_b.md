## 2. Q1 · P-01 的 8.9 s 空中滑翔：**不挖**

### 2.1 核心问句：「暗域纯空中滑翔」算不算「跑图」？

**算跑图 —— 但本条里「纯空中滑翔」只有 ≈0.79 s，不是 8.9 s。** 这是本裁决的关键。

规约 §5「删：跑图、搜物资、等待、重复操作、长时间无事件」中的「跑图」，
按 §5.2「画面证据优先于计时器」+ §5.1「钩锁/御空/蓝盾类位移特效**不得单独**作为交战证据」，
判定口径是**画面三信号（敌方红血条 / 伤害数字 / 锁定线）是否全程为零**。
位移**形态**本身（滑翔 vs 奔跑）不是判据，**三信号是否为零**才是。

**实测（4K 母版，帧级）：**

| 源 S | 帧号 n | 画面三信号 | 性质 |
|---|---|---|---|
| 948.99–949.72 | 56939–56983 | **全零**（`g_band60` m00001–m00008 逐帧零条，raw_max_run=0） | **跑图/纯位移，仅 0.73 s** |
| **949.7833** | **56987** | **敌方紫+红条对首帧**（`m00012`） | **目标在场**（对峙接近） |
| 949.78–952.x | 56987–57000+ | 条对持续存在、随镜头横移 | 对峙接近（§5「留」） |
| **953.0** | 57180 | **红条 + 绿色伤害数字「150 锤击」** | **硬交战开始** |
| 954–958 | 57180–57500 | 近身互殴、满屏斩击弧 | 交战 |

⇒ **「无接触纯位移」实测 0.79 s（948.99 → 949.78），不是 8.9 s。**

### 2.2 与 `combat_002` 判例的尺度一致性论证（本裁决的核心）

裁决 A 的判例原文：「**已授权的前置时长是硬上限，超出即须挖**」
（E9 只授权 `combat_002` 前置 5.0 s = 305→310，实测 15.27 s 无效位移，**超授权 10.27 s** ⇒ 挖）。

**该判例的适用前提是「超授权」。本条不满足这个前提，因此尺度一致的做法恰恰是不挖：**

| 维度 | `combat_002`（裁决 A） | `combat_010`（本条） | 是否同尺度 |
|---|---|---|---|
| 已登记授权 | **E9 明文授权 5.0 s** | **无任何授权**（E8 把 `combat_010` 前置记作 **0.01 s**） | — |
| 实测无效位移 | **15.27 s** | **0.79 s** | — |
| 是否超授权 | **超 10.27 s ⇒ 挖** | **不存在「超授权」这回事** | — |
| 位移内容 | 瓦顶滑行 → 绿勾锁锁滑翔 → 地面奔跑 → 传送 | 暗域空中滑翔 → 落地石板庭院 | **同型**（都是位移，都不是交战） |
| 敌方接触起点 | 320.267（条对）→ 333.0（首个打击） | **949.78（条对）→ 953.0（首个伤害数字）** | **同型、同间隔** |

**三条推论：**

1. **形态同型，处置必须同型。** 裁决 A 挖掉 `combat_002` 那 15.27 s，靠的是
   「15.27 s 内画面三信号全零」这个**画面事实**，不是「它是滑翔」这个形态。
   本条 0.79 s 之外的三信号**并不为零**——条对从 949.78 就在画上。
   ⇒ **按同一把尺子，形态相同但三信号不同 ⇒ 处置必须不同（不挖）。**
   反过来说：如果因为「空中滑翔」这个形态就挖 8.9 s，那才与判例**尺度不一致**。

2. **两场的「目标在场 → 首个打击」间隔几乎相同，进一步说明这是同一种结构。**
   `combat_002`：`320.267` 条对 → `333.0` 首个橙色火球，间隔 **12.73 s**；
   `combat_010`：`949.78` 条对 → `953.0` 首个伤害数字，间隔 **3.22 s**。
   本条的间隔**比判例里被认可保留的那段还短**。
   裁决 A 在 §7 待裁项里写「`320.27 → 333.0` 这 12.73 s 是否仍偏长」——
   **本条 3.22 s 连那个待裁门槛的 1/4 都不到**，谈不上超长。

3. **本条的前置连「已登记例外」都不需要。** `combat_002` 需要新授权，是因为它要保留 12.73 s；
   本条保留 0.79 s + 3.22 s 对峙，**远小于 §5.2 默认 `lead_in = 5 s`**，
   也小于 E9 授权过的 5.0 s。**没有任何超授权问题。**

> **⇒ 尺度一致性的结论：Q1 判「不挖」。**
> 判例支持「超授权就挖」，不支持「是滑翔就挖」。本条既没超授权，形态又是同型，
> 按同一把尺子只能得到同一个方向：**保留**。

### 2.3 附带纠正：adv6 自身的两处自相矛盾

1. **P-01 的定性与其建议自相矛盾**：adv6 把 `S 948.99–957.87` 标为
   **【跑图残留】**、说「8.9 s 暗域纯空中滑翔」，却在同一格里写
   「**画面无需任何改动，只需改秒点**」。若真是跑图残留，正确处置是**挖**；
   若是「有效接近必须留」，就不该挂「跑图残留」的类别。**本裁决判定：它既不是跑图残留，
   也不是 8.9 s——它是 0.79 s 位移 + 3.22 s 对峙接近，两段都该留。**

2. **P-01 的「零命中」下界过弱**：adv6 用 `redbar_strict`（`R>145 且 R>1.8G 且 R>1.8B`）
   得出「`P 433.0–441.89` 零命中」。该式在本素材**过严**：
   真实敌方血条实测 **rgb≈(240,119,125)**，换算 BGR 是 `(125,119,240)`
   ⇒ `R=240 > 1.8G=214` ✔ 但 `R=240 > 1.8B=225` ✔ 边际通过；
   而**半饱和/受特效遮挡的条**（本条实测 `(214,111,131)`、`(193,95,118)`）
   ⇒ `R < 1.8B` ⇒ **被漏掉**。所以「零命中」只证明「**没有近距离满血条**」，
   **不能证明「没有目标在场」**。这正是 AGENTS 与任务书第 2 条坑的又一次复现。

## 3. Q2 · `source_start` / `engage_start` 的帧级建议

### 3.1 结论

| 字段 | v3 现状 | **建议** | 帧对齐核算 | 严格性核算 |
|---|---|---|---|---|
| `source_start` | 948.99 | **948.99（不动）** | 948.99×60 = **56939.4** ⇒ 首帧 n=**56939** | 见下 |
| `engage_start` | **949.0** | **953.0** | 953.0×60 = **57180** ✔ **整数** | `948.99 < 953.0` ✔ **严格成立** |

| `source_end` / `outcome_time` | 1037.0 / 1024.0 | **不动** | — | `953.0 ≤ 1024.0 ≤ 1037.0` ✔ |

### 3.2 为什么 `source_start` 不动

- 实测首触（条对首帧）在 **S 949.7833**，比 `source_start = 948.99` 只晚 **0.79 s**。
- 挖掉这 0.79 s 会把段首切在**落地滑翔的中途**，且切口两侧同为暗域紫调
  —— 收益 ≈0，接缝风险 >0。**不动。**
- `948.99` 这个值是 v3 为满足 validate `start < engage` 严格小于而设的
  （`merge_decision_v3.md` §1.1 / 例外 E7 记录），**本裁决不触碰该机制**。

### 3.3 为什么 `engage_start` 必须改，以及为什么是 953.0

**v3 记的 949.0 是错的，且错得比 adv6 说的还严重。**
v3 `boundary_reason` 写「`P 440.5`（源 949.4）**首帧就是暗域紫空区里的接战姿态、
已有敌方红色名条 + 血条**」——这句话**经 4K 复核为假**：

- 源 949.4 的画面上**只有暗域雾 + 妖气星座线 + 一条绿色 181 m 菱形目标标记**，
  **无任何敌方条**（`a_census\c00001` = S949.0 零条；`g_band60` m00001–m00008 = S949.60–949.717 零条）。
- 于是 v3 把 `engage_start` 记成 949.0 ⇒ `lead_in = 949.0 − 948.99 = 0.01 s`，
  并在例外 E8 里把本场前置登记为「**0.01 s**」。
  **这是本条最实质的缺陷：它让下游任何按 `engage_start` 统计接战时长的工具，
  都从 948.99 起算，把 0.79 s 位移 + 3.22 s 对峙接近全部算成「已接战」。**

**取值 953.0 的依据（正是任务书要求的「首次出现伤害数字/受击反馈」那一帧）：**

1. **S 953.0 = n 57180** 是 4K 目视下**第一帧**同时出现
   **敌方红条 + 绿色伤害数字「150 锤击」**的帧（`a_census\c00005`、`e_full` 联系表第 3 行）。
2. 不可更早：`S 949.78–952.x` 只有「条对 = 目标在场」，
   按**裁决 A §6-N3 已确立的判例**（「紫条 + 鲑红条的一对 = 世界锚定的角色血/护甲条对，
   证明『目标在场』，**不证明『已交战』**」），那属**对峙接近**，不属 engage。
3. 不可更晚：`S 954.0` 起是明确近身互殴（`a_census\c00006`），953→954 连续无断窗。

**⇒ `engage_start = 953.0`（n 57180，整数帧）。**

### 3.4 若指挥仍要求「首触 ≠ engage」严格分离

任务书担心「首触点与 `source_start` 撞在同一帧」。本条**不会撞**：

## 4. Q3 · P-02 的 20 s：**不挖**

### 4.1 裁决

**不挖，且不建议做任何形式的登记例外**——因为「20 s 无接触」这个**前提不成立**。
若硬挖，会在 `combat_010` 段中部开一个 20 s 的洞，而洞的两侧**都在同一场交火里**，
直接违反 §5「**战斗中不切走。宁可留长，不漏战、不切断**」。

### 4.3 adv6 在这一条上的自相矛盾（必须点名）

adv6 §2 P-02 的**证据②自己写**：「`redbar_strict`：`P 486.40/487.50`、`488.20/489.10`、
`490.00/490.20` 三个命中窗口，**最早在 `P 486.40`**」，

**它自己的数值表已经推翻了它自己的目视结论**，却仍按目视（更宽松的读法）定性为
「无接触位移段」并挂上「跑图残留」。**同一份报告内的两个证据互相打架，而结论采信了错的那一个。**

### 4.4 规约上的三重支撑（即便真有一段无接触，也不该挖）

1. **§5「战斗中不切走」是硬规则**，「宁可留长」是其明示的取舍方向。
2. **§5.1「玩家倒地 ≠ 这段没战斗」**：`S 1003–1005` 玩家贴地翻滚，
   **敌方条在画** ⇒ 按规约这一段仍属战斗，不构成挖的理由。
3. **`S 987` 的「正在被淘汰」播报**是**结果播报**。按 §5.1 的精神与 `combat_002` 例外 E1 的写法
   （「没有击杀就没有播报」是**结果链的一部分**），在击杀爆之后紧跟的淘汰播报属**收束环节**，
   **§5 明确把「属收束环节的全屏 UI」排除在删除之外**，同理这条播报也不该被挖掉制造断点。

### 4.5 若指挥仍坚持要挖（我不建议，但给出风险量化）

- **不建议做成 `excluded_inside` 洞**：洞的两侧（`S 985.97` 与 `S 1005.97`）
  **都在交火中**（见 §4.2 表），两侧都带敌方条/名条 ⇒ 挖完的接缝是
  「打 → 突然无接触位移 20 s → 又打」，**观感上是把一场连续战斗腰斩**，

**输入 `-ss` 会重置滤镜的 `n` 计数器**，所以「先 `-ss` 再按绝对帧号 `select='between(n,A,B)'`」

**帧身份仍由源时间/PTS 决定**，符合「涉及某一帧到底是什么必须用帧号法」的要求。
附带收益：4K 无需从 n=0 解码，窗口抽取从「>10 分钟」降到 **~40–90 秒**。
另记：`-Ranges "a,b,c"` 内联传参会因 PowerShell 把逗号当数组而报
`InvalidCastFromStringToInteger`，**必须改用 `-RangeFile`**。

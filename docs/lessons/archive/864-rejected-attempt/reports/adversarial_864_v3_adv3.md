**帧号怎么钉死的（三条独立证据，互相印证）**

1. `sum(program_map_v3.renders) = 34817 = ffprobe nb_frames`，差 0 → 拼接没丢帧/插帧。
2. `cache\v3segs\vsegNNN.mp4` 逐个 `-count_frames`：vseg005=1621 / 006=1350 / 007=2202 / 008=339，与 map 一致。
3. 预览里每段起始都是 x264 的 IDR（全片 639 个 I 帧，`-g 60`）。凡 I 帧间距 ≠60 的地方就是段首：
   `idx 10050`(pts 167.521) / `11671`(194.538) / `13021`(217.038) / `15223`(253.738) / `15562`(259.388) —— **与上表逐个吻合**。

**两个必须先说清的技术事实（否则秒点会整体错 1 帧）**

- **渲染器的 `-ss` 取整**：`cache\render_preview.py` 用 `-ss <source_start:.3f> -i SRC -frames:v round(dur*60)`。
  `-ss` 在 `-i` 前 ⇒ 首帧是**第一个 pts ≥ source_start 的帧**。所以 **cut5 的首帧真实源秒是 `S 417.0000`（源帧 25020），不是 416.99**；
  末帧是 `S 444.0000`，比声明的 `source_end` 多 1 帧。cut6/7/8 的 `source_start` 都是整秒，无偏差。
- **预览的 PTS 有 +0.021 s 整体偏移**：`pts(index) = index/60 + 0.021`（idx 0 的 pts 就是 0.021）。
  内容不受影响（容器时长 580.304333 = 帧总和 580.2833 + 0.021），但**用 `-ss X` 抽帧时首帧序号 = `ceil(60X − 1.26)`**，
  比 `ceil(60X)` 早一帧。4K 源无此偏移（`start_time=0`，`pts=index/60`），首帧 = `ceil(60X)`。
  ⚠ 本轮第一版 `seam3.py` 就是在这里整体错 1 帧的，已修正并重测（见 §3.6）。

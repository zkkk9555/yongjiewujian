## 0. ⚠️ 首要发现：本机 ffmpeg 的 `-ss` 行为与作业书相反（必读，影响所有路）

`audit_brief_v2.md`「抽帧命令」一节指示把 `-ss` 放在 `-i` **之后**，并称「`-i` 之前的 `-ss`/`-t` 会被静默忽略」。
**在本机（`C:\Project\永劫无间\.video-tools\LosslessCut\resources\ffmpeg.exe`，n8.0-23）实测恰好相反**：

| 写法 | 实际行为 | 证据 |
|---|---|---|
| `-i in -ss 136.5 -t 4.0 …`（作业书写法） | **`-ss` 被静默忽略**，`-t` 生效 → 输出的是**从节目 0.0 开始**的内容 | 见下 |
| `-ss 136.5 -i in -t 4.0 …`（输入定位） | 正常，落在节目 136.5 附近 | `align3.py` testA |
| `-i in -vf "trim=start=A:end=B,setpts=…"`（**无 seek**） | **逐帧精确**，可作为基准 | `align3.py` testB，最后一帧与基准 `meanAbsDiff = 0.00` |

**量化证据**（`TASK\shots\adv2r2\align2.py`，把每次抽帧的每一帧与「从 0 开始、1 fps、无 seek」的基准集 `base/` 逐帧做最近邻匹配）：

```
census85 n=90  test[00] -> base program 0.0 (d=5.12) … test[89] -> base program 89.0 (d=5.50)
d137     n=16  test[00] -> base program 0.0 … test[15] -> base program 3.0
d167     n=16  test[00] -> base program 0.0 … test[15] -> base program 3.0
d111     n=27  test[00] -> base program 0.0 … test[26] -> base program 13.0
d152     n=30  test[00] -> base program 0.0 … test[29] -> base program 14.0
```

即：作业书命令抽出的「节目 85–175 / 110–124 / 136–140 / 152–167」**实际都是节目 0–15 / 0–90**。
我因此**作废了前 10 张看图**（见 §6 预算记录），改用 `trim` 滤镜重抽全部证据。

**同时钉死时间基准**：用 `trim` 法抽出的帧与 `base[n]` 逐帧比对，`base[n]` = 节目 `n + 0.5`（`fps=1` 取每个 1 秒桶的中点），
`trim` 法 `trim=start=136.5` 的第 239 帧（= 136.5 + 239/60 = 140.483）与 `base[140]` 的 `meanAbsDiff = 0.00`。
**本报告所有「节目秒」均为 `trim` 滤镜 PTS 绝对值，误差 ≤ 1/60 s。**

**建议（不在我职权内，仅登记）**：把作业书与 `scanner_brief_common.md` 的 `-ss` 示例改为 `trim` 滤镜或 `-ss` 前置；否则任何照抄作业书的审片员都会在不知情的情况下审错区间。

另有两个同源坑（我也踩了，均已绕开，登记备查）：
- `mk.ps1` 若含中文路径字面量且存为 **UTF-8 无 BOM**，PowerShell 5.1 按 ANSI 读源码 → 路径乱码（与 `AGENTS.md` 记的乱码目录同源）。我的版本改成参数传入 + 纯 ASCII，已正常。

## 0. 一句话结论（先看这个）

**全量上云的钱是个零头（19 分钟素材，全量喂一次 0.05–1.24 元人民币 / 0.22–1.24 美元），钱根本不是瓶颈；
真正的瓶颈是「上传带宽 + 判读不可复现 + 项目要求可审计」。**

所以答案不是「贵不贵」，而是「**这钱买不到你需要的那个属性（可审计性）**」。
建议：**全量上云当"第二意见/发现器"，绝不当"判决者"；本地流水线保留最终裁决权，云端只复核疑难片段。**
详见 §6。

### 1.2 谁**不**收视频（重要）

OpenRouter 模型清单里输入模态**只有 `text,image,file`，没有 `video`** 的（`实测`）：

- **OpenAI 全系**（`gpt-6.1-sol` / `gpt-6-astra` / `gpt-6-luna` …）：`text+image+file->text`
- **Anthropic 全系**（`claude-opus-5.5` / `claude-sonnet-5.5` / `claude-fable-5.1` …）：`text+image+file->text`

> `file` 是 PDF/文档，不是视频容器。**所以"OpenAI 视觉 / Claude 视觉"这条路对本项目是断的**——
> 想用它们，只能自己抽帧再送图，那样就退化成"抽帧方案"，不再享有视频模型的时序能力。
> OpenRouter 文档也明说 Messages API 不支持视频输入（`文档`）。

**结论（推断）**：如果坚持走"直接送视频容器"的路，候选只有 **Gemini + 阿里 Qwen + 字节 Doubao** 三家。

### 1.3 视频硬限制（各家单请求上限）

**阿里 Qwen（唯一读到完整官方限制的一家，`文档`）** — 来源 `https://help.aliyun.com/zh/model-studio/vision`：

- `fps` 抽帧参数：**取值 [0.1, 10]，默认 2.0**（这正好覆盖你问的 1fps / 2fps）
- `max_frames` 上限参数：抽帧数超限时**自动在上限内均匀抽稀**
- 官方示例常量里写死：`FPS_MIN_FRAMES = 4`，`FPS_MAX_FRAMES = 2000`
- **视频时长**（`文档` 原文）：
  - `qwen3.8 / 3.7 / 3.6 / 3.5` 系列：**2 秒 ~ 2 小时**
  - `qwen3-vl-plus / qwen3-vl-flash / …-thinking / …-instruct`：**2 秒 ~ 1 小时**
  - 其他 Qwen3-VL 开源、`qwen-vl-max`：**2 秒 ~ 20 分钟**
  - `qwen-vl-plus` 等：**2 秒 ~ 10 分钟**
  - 其他模型：**2 秒 ~ 40 秒**
- **视频体积**：公网 URL 传入，`qwen3.8` 系列 ≤ **2GB**；本地路径传入 ≤ 100MB；Base64 编码后字符串 < 10MB
- **视频数量**：单请求最多 **64 个视频**
- **视频尺寸**：无硬限制，但 > `max_pixels` 会被缩小，且**更大的文件不会带来更好的理解效果**
- **格式**：MP4 / AVI / MKV / MOV / FLV / WMV 等
- **音频：明确不支持对视频文件的音频做理解**

> ⚠️ **对本项目的直接杀伤**：
> 1. **2fps 下 19 分钟 = 2280 帧 > `FPS_MAX_FRAMES=2000`，会被静默抽稀到 2000 帧**——
>    也就是"2fps 全量"根本送不进去，会被悄悄降级。这是最容易误判的一点。
> 2. 本地路径只能 100MB。**5.9GB 的源文件想走"本地路径"是不可能的**，必须先降码率转码或转 1fps 帧序列再送。
> 3. Qwen 不吃音频 → **字幕/语音这条线云端帮不上忙**，本机 faster-whisper 那 2.6GB 工具链**不能省**。

**Gemini**：
- 上下文 1.05M tok（`实测` OpenRouter API）→ 19 分钟视频在 token 预算内绰绰有余
- 帧采样**可显式控制**：OpenRouter 文档记载 `video_metadata.fps` 直传 Gemini，LiteLLM 文档进一步给出

  即 **AI Studio 路径不接受本地 mp4 的公网 URL**，只能 base64 或 YouTube 链接。

### 2.2 一个反直觉但重要的发现：Qwen 的成本是"封顶"的，不是线性的

按官方公式（`文档` 原文）：

```
video_token = ceil(num_frames / 2) × resized_h/32 × resized_w/32
max_pixels_per_frame = min(VIDEO_MAX_PIXELS, VIDEO_TOTAL_PIXELS / nframes × FRAME_FACTOR)
VIDEO_TOTAL_PIXELS = 65536 × 32 × 32   （qwen3.8 等）
```

**总 token 被 `VIDEO_TOTAL_PIXELS` 死死锁在 ~65536**，帧越多、每帧越小，总量不变。
所以 **1fps 和 2fps 成本完全相同（都是 ¥0.79）**——多花一倍帧数一分钱不多，也**不会多看到任何内容**。

推论（`推断`）：
- 想省钱不该降 fps（没用），该**换模型**（omni-flash ¥0.05 vs max ¥0.79，差 15 倍）
- 想提精度该**分段送**（每段各自吃满自己的 65536 token 预算）而不是整局一把送

## 3. 耗时估算

### 3.1 上传（`实测` 帧体积 + `推断` 带宽）

`实测`：1fps @ 2560×1440、q:v 3 → **373 KB/帧**。

| 送什么 | 体积 | @10 Mbps 上行 | @50 Mbps | @300 Mbps |
|---|---|---|---|---|
| 1fps 帧序列（19 min，1140 帧） | 415 MB | 5.5 分 | 1.1 分 | 11 秒 |
| 1fps 帧序列 base64（×1.37） | 569 MB | 7.6 分 | 1.5 分 | 15 秒 |
| **原始 5.9GB mp4 直接传** | 5900 MB | **79 分** | **16 分** | 2.6 分 |

> **这是全量上云的真实代价，而且它跟模型无关。**
> 传原始 4K/2.5K 文件 = 光上传就 16 分钟到 79 分钟，**已经吃掉"本机 10 小时"里很大一块，
> 却一个帧的信息量都没多给**（云端会自己重采样 + 缩到 `max_pixels`）。
> **正解是本地 ffmpeg 抽 1fps 帧序列（415 MB）再送。**

### 3.2 推理（`推断`）

- **阿里**：官方明写「**非流式调用的最大超时时间不少于 300 秒**」，且超时后会在响应体里返回已生成内容，
  响应头 `x-dashscope-partialresponse: true` 标记超时（`文档` 原文）。
  → **单请求 300 秒是官方兜底线**，19 分钟视频建议**切段并行**，别指望一把过。
- **Gemini `agentic` 模式**：模型自己决定加载哪些帧，长视频延迟显著高于 `static`（`文档`，OpenRouter 原文定性描述，未给具体秒数 → `推断`）
- SDK 客户端默认超时可能不够，官方建议 `client.with_options(timeout=1800.0)`（`文档`）

### 3.3 与"本机 10 小时"对比（`推断`）

本机链路 10 小时里，**模型推理通常不是大头，抽帧/转写/渲染才是**。
云端把"抽帧 + 判读"压到分钟级，剩下 10 小时大头是**转写（faster-whisper）和 4K 重渲染**，这两项云端**替代不了**（Qwen 明确不吃音频；4K 渲染必须本地 NVENC）。
**所以"上云 = 10 小时变 1 小时"是不成立的推断，真正的上限是"10 小时变 7–8 小时"。**

## 4. 对游戏画面的适配（这一节是我最没底的）

**必须直说：我没找到任何针对"第一人称 HUD 密集游戏画面"的公开评测**（`未找到`）。

- 检索路径：websearch 工具本轮**全程返回空结果**（试了 5 个不同 query，全部 "No search results found"，`实测`），
  Bing HTML 可连但正文由 JS 渲染抓不到，startpage/searx/brave/mojeek/DDG **全部连接失败**（`实测`）。
  → **这一节的证据基础比 §2 弱得多，属于我的领域推断，不是实测。**

**推断层面我认为的风险（按可能性排序）**：

1. **帧率不足 ⇒ 动作漏检（最大的真风险）**
   Qwen `fps` 默认 2.0、上限 2000 帧。19 分钟 @2fps 已被抽到 2000 帧 ≈ **1.75fps 实际生效**。
   而《永劫无间》是 60fps 的振刀/反打/连招——**1.75fps 意味着一次振刀（约 0.2–0.4 秒）落在两帧之间的概率很高**。
   这恰好撞上 AGENTS.md §8.1 关心的"战斗窗口内不许挖洞"：**抽稀掉的帧就是事实上的洞，而门禁看不见它。**
2. **HUD 文本 vs 战斗状态的混淆**
   AGENTS.md §8.1 明确把"舔包/打药面板"判成**属于战斗**，旧口径"删全屏 UI"已经被否过六版。
   云端模型没有你这 7 轮迭代积累的"打药面板 = 战斗中"这个**项目内先验**，极可能把打药/舔包面板判成"看菜单"。
   这正是你担心的那个失效模式，而且**它不会报错，会安静地产生一份看起来合理的错误时间线**。
3. **缩放丢细节**
   Qwen 默认 `max_pixels=2621440`（≈2048×1280），`vl_high_resolution_images=true` 时上限 16384 token/帧。
   2560×1440 会被缩。**伤害数字、技能 CD 圈这些小字最先消失**——而它们正是判读"振刀/拆火"的依据。
   官方自己都说"更大尺寸的视频文件不会有更好的理解效果"（`文档`）——这话对普通视频成立，**对依赖 HUD 细节的游戏判读未必成立**。

## 5. 精度与不可控性（这一节结论很硬）

**致命，但要精确定位死在哪。**

| 失效模式 | 后果 | 严重度 |
|---|---|---|
| **不可复现**：同一素材两次问结论不同 | 时间线不可回放、无法复盘、无法追责 | **致命** |
| **无法指认证据帧**：模型说"12:34 有振刀"，但没有"我是看第 733 帧得出的" | 裁决链断裂 | **致命** |
| **静默降级**：2fps 悄悄被抽到 2000 帧，响应里**不告诉你** | 你以为看了 2fps，实际 1.75fps | **高**（隐蔽） |
| **超时部分返回**：Qwen 超时也返回已生成内容 | 拿到半份结果却当成完整结果 | **中高** |
| **静默错判**（§4-2 打药面板） | 错误时间线看起来很合理 | **高** |

对照项目铁律：
- `deliverables-and-qa` 要求**可审计、可回放证据**；`qa_gate.py` 的门禁建立在**确定性的源时间码**上
- **云端输出无法进 `timeline\combat_episodes_vN.json` 当证据**——它是一个不可复现的散文结论，不是时间码

> **结论（推断，但基于项目规则文本，是硬结论）**：
> **云端模型不能、也不该进入本项目的裁决链。它的合法位置只有"提示器"（discovery）——
> 告诉你"这里值得再看一眼"，由本地确定性流水线 + 人工审片去证实或否掉。**

|---|---|---|
| 全量 1fps 上云（qwen3.8-max） | **¥0.79 / $0.59** | 便宜，但**买不到可审计性**——钱花了属性没到手 |
| 10% 抽样上云复核 | **¥0.08 / $0.06** | **推荐**。钱花在刀刃上，且抽样天然规避"整局一起错" |

**注意反直觉点**：因为 Qwen 总 token 被 `VIDEO_TOTAL_PIXELS` 封顶（§2.2），
**抽样送不仅便宜 10 倍，而且每段能吃满 65536 的 token 预算 → 精度还更高。**
抽样是**双赢**，不是妥协。这是本报告最有价值的一条。

### 6.2 分工建议

**✅ 值得上云（发现器 / 第二意见）**
1. **疑难片段复核**：本地 PySceneDetect / Auto-Editor 标出"边界可疑"的 30–120 秒片段
2. **本地标记与云端判断的冲突仲裁**：两边不一致时，把该处送云端取第二票（只送 30 秒，不是 19 分钟）
3. **首轮"这段有没有在打架"的粗筛**：省掉人工在 40 分钟里找战斗的功夫

**❌ 必须留本地（不可替代）**
1. **字幕/转写** — Qwen 官方明确**不支持视频音频理解**（`文档`）；faster-whisper 那套工具链**必须留**
2. **源时间码与时间线** — 云端给不出可复现的帧级证据
3. **4K 渲染成片** — 必须本地 NVENC 从原素材重渲
4. **门禁裁决** — `qa_gate.py` 建在确定性时间码上，云端散文进不了
5. **字幕外挂 SRT** — AGENTS.md §5 铁律
6. **删除段审计** — AGENTS.md §8.2 新增的"删除段审计员"，靠的是可回放证据，云端给不了

### 6.3 如果要上云，技术上怎么送（避开三个坑）

1. **别传原始 5.9GB 文件**。先本地 `ffmpeg -vf fps=1 -q:v 3` 抽帧（实测 373 KB/帧 → 415 MB），
   或者降码率转一份 1080p/低 fps 的代理素材。官方自己也说更大体积不会更好（`文档`）
2. **按 Gemini 路线的话，AI Studio 只收 YouTube 链接**（`文档`），本地 mp4 只能走 base64
   → 意味着 415 MB 要 base64 成 569 MB 进 JSON body，**大请求更容易超时**。**分段送**
3. **用 Gemini 的 `start_offset`/`end_offset`（LiteLLM 文档）或 Qwen 的 `fps` 显式指定要看哪一段**，
   **不要依赖自动抽帧**——否则撞上 2000 帧上限被静默抽稀（§2.2），而你不会收到任何提示

### 6.4 给你的判断依据（一句话）

> **10 小时里，上云最多帮你省掉 2–3 小时（判读那一段），但要求可审计的话，这 2–3 小时本来就不能交给云端。
> 成本 ¥0.79 或 $0.59 折合每小时不到 3 毛钱——钱不是问题，别让"钱不是问题"误导你以为是速度问题。
> 真正该问的是：这 2–3 小时本地能不能靠并行/降采样优化解决，那大概率比引入不可复现的黑盒便宜。**

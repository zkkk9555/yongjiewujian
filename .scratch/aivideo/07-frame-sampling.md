# 07 · 抽帧与看图：有没有更省时间的技术路径？

调研日期 2026-10-05 · 调研员子会话 · 全部结论标注 **实测 / 文档 / 推断 / 未找到**

---

## 0. 一句话结论

> **固定 1fps 不算错，但"省时间"的杠杆不在抽帧数量上，在"送哪一帧"和"一张图能装几帧"上。**
> 实测：同样 2228 张图的预算，把盲取的整秒帧换成**桶内变化最大帧**，平均场景变化量涨 **10.4×**；
> 而"变化驱动抽帧"（阈值法）在 60fps 战斗画面上**几乎省不下任何东西**（静态秒 = 0%）。
> 最大的浪费在联系表：**48 格拼一张图在 API 上根本活不下来**（实测算出的 131×74 与 864 事故完全吻合）。

## 2. Q1 自适应抽帧：变化驱动在本项目上**失效**（这是本次最重要的负面结论）

### 2.1 全片逐帧场景变化率（实测）

`scdet` 对 60fps 战斗画面的逐帧分数（MAFD，越大越像"切了一刀"）：

| 分位 | p10 | p25 | p50 | p75 | p90 | p95 | p99 | max |
|---|---|---|---|---|---|---|---|---|
| score | 0.002 | 0.011 | **0.047** | 0.234 | 0.537 | 0.741 | 2.164 | 34.98 |

**中位数 0.047 意味着：连续两帧之间平均已有 4.7% 的画面变化。** 60fps 的战斗画面是"逐帧都在变"的。

### 2.2 全局阈值法会抽出多少帧（实测）

| 阈值 | 抽出帧数 | 相当于 |
|---|---|---|
| 0.001 | 120,869 | 54.3 帧/秒 |
| 0.01 | 100,307 | 45.0 帧/秒 |
| 0.05 | 64,849 | 29.1 帧/秒 |
| 0.1 | 48,193 | 21.6 帧/秒 |
| 0.2 | 36,618 | 16.4 帧/秒 |
| 0.5 | 15,026 | 6.8 帧/秒 |
| **1.0** | **4,120** | **1.85 帧/秒** |

**关键：要把帧率压到 1.85/秒（已经比固定 1fps 的 1.0/秒还多），阈值必须抬到 1.0**——而 1.0 已经高于 p99（2.157）之外的一大截，等于只保留最激烈的部分，**必然漏掉低速但关键的移动与 UI**。阈值再抬到 2 以上才开始省图，但那已经是在丢信息了。

**结论（实测）：阈值驱动的变化抽帧在本素材上比固定 1fps 更差——图更多、且不可控。**

### 2.3 静态内容有多少？（实测）——零

| 指标 | 结果 |
|---|---|
| 每秒峰值 < 0.001（近静止）的秒数 | **0 / 2228 = 0.0%** |
| 每秒峰值 < 0.05（低活动）的秒数 | 115 / 2228 = 5.2% |
| 每秒峰值中位数 / 均值 | 1.692 / 2.257 |

**永劫无间的 60fps 录像里不存在"静止段"。** 这直接推翻了 2026 年关键帧选择论文里反复用到的前提——QCA 论文原文写 *"a long static stretch inside an hour-long video automatically loses its quota"*（长静止段自动让出配额）。**那句话对自然视频成立，对本素材不成立。** 这是本项目不能照搬论文的关键理由。

### 2.4 那到底能省多少？——不省图，但**图的含金量翻 10 倍**

在**完全相同的图像数量**（2228 张）下比较（实测）：

| 策略 | 平均场景变化分 |
|---|---|
| A：固定 1fps 盲取整秒帧（现状） | **0.2177** |
| B：每 1 秒桶内取变化最大的那一帧 | **2.2572** |

> **10.4×。** 图没多一张，图的"信息密度"翻了十倍。
> 桶内峰值的时间分布是**完全均匀的**（因为没有一秒是静止的）——所以这不是"挑几个热点"，而是**每一秒的取样点都该换**。

### 2.5 唯一真能省图的两个方向（实测边界）

1. **降采样率本身**：2.0 帧/秒 = 4799 张，比 1fps 多一倍，画面冗余（相邻帧 ACF 很高，FOCUS 论文实测前 5 秒中位 ACF > 0.5）。**实测支持降到 0.5fps 再靠"桶内取峰"补回来**——0.5fps × 4 桶 = 2 帧/秒的候选里取峰值，信息量接近 1fps 桶内取峰，**候选池只需一半**。
2. **只对"用户已经圈定的战斗窗口"抽帧**，把"跑图/舔包/结算"整段排除——这是**业务层筛选，不是像素层筛选**，收益远大于任何抽帧算法。**这条已经被 §8.1 的"整场战斗"规则隐含覆盖了。**

## 3. Q2 场景感知抽帧：2026 年的工具长什么样

**全部是文档（论文），没有开箱即用的 Windows 工具。** 关键的一条：**它们绝大多数是 query-aware（需要一段文字提问）的视频 QA 方法，不是无查询的剪辑分析。**

| 方法 | 会议/日期 | 训练 | 核心 | 对本项目的适配度 |
|---|---|---|---|---|
| **FOCUS** | ICLR 2026 | 免训练 | 把关键帧选择建模成多臂老虎机的**组合纯探索（CPE）**，用 Bernstein 置信半径分配预算；先粗后细两阶段。**处理 <2% 的帧**，>20min 视频在 LongVideoBench 上 **+11.9%** | **最高**：不需要 query（本方法只要"分配预算"那部分，不要相关性打分那部分）。可直接实现，见 §7 |
| **CSES** | 2026-08 | 免训练 | 覆盖度驱动的**次模**目标（语义相关 + 时间冗余 + 视觉冗余），贪心有 (1−1/e) 保证。打分帧数少 4–13×，选择快 3.1–5.4× | 中：需要 query embedding |
| **LENS** | ECCV 2026 | 免训练 | 让模型自己把帧预算按比例拆给**空间放大（CLIP 注意力遮掉无关区）**与**时间缩小（2×2 hyperframe 把锚帧+时序邻居打包成 1 个槽位）**。Video-MME 53.3→60.7 | **高（就 hyperframe 那半）**：§5 实测 hyperframe 是本项目唯一可行的"一图多帧" |
| **GIFT** | CVPR 2026 | 免训练 | 不可替代性 = 相关性 × **方向多样性**（到"所有比它更相关的帧"的最小距离）；预算递增时分批"选→移除→重算" | 中 |
| **QCA** | ECCV 2026 | 免训练 | 段级贡献分（query 匹配 + 内容偏移）→ 幂归一化分配配额 → 段内"语义锚 + 距离贪心" | **低**：核心前提（静止段让出配额）被 §2.3 实测证伪 |
| **AKS / BOLT / MDP3** | CVPR 2025 | 免训练 | 相关性与时间覆盖自适应平衡 / 锚定传播 / 相关+多样+时序建模 | 低-中 |
| **VideoBrain** | 2026-02 | **需训练** | VLM 直接当决策器，两个采样 agent（CLIP 检索 + 均匀密集）迭代补采；少用 30–40% 帧 | 低：要训 |
| **Q-Frame** | 2025 | 免训练 | **联合分配帧数与分辨率**（Q3 的正解，见 §4） | **高（就多分辨率那半）** |

**未找到**：任何"抽帧 + 自动判断这段值不值得细看"的**离线命令行工具**，尤其是 Windows 可用、不需要 GPU 模型的。现成可用的仍是 **ffmpeg `scdet`/`select`/`signalstats` + PySceneDetect**（项目已有）。

## 4. Q3 多分辨率策略：有论文思路，**但本项目的瓶颈根本不在这里**

**实测：分层的真正瓶颈不是"自动挑出需要高分辨率复核的候选"，而是"一张图能合法装几帧"。** 见 §5。

Q-Frame 的联合分配思路（先粗采样定位 → 对高价值帧给高分辨率）是正确方向。**推断**：本项目可以照抄其骨架，但**分配信号不能用 query 相关性**（剪辑分析没有 query），只能用**逐帧 scdet 分数**——这就退化成 §7 的两遍扫描。这仍然是净赚，因为 §2.4 实测有 10.4× 的空间。

## 5. Q4 联系表参数：**这是本项目最大的浪费，且已造成过事故**

### 5.1 `tile` 多输入在 ffmpeg 8.0 是否仍失效？——**是，实测确认，但项目脚本的理由说错了**

**实测（ffmpeg n8.0-23）**，6 张图各一个 `-i`：

```
[AVFilterGraph] More input link labels specified for filter 'tile' than it has inputs: 6 > 1
Error linking filters
```

`tile` 是**单输入**滤镜，项目脚本 `scripts\make_contact_sheet.ps1` 的注释成立。**但是**——把帧按**时间序列**喂给它就完全正常：

| 方式 | 结果 |
|---|---|
| `tile` + 6 个 `-i`（多输入） | **失败**，`6 > 1` |
| `tile` + image2 序号输入 `-i "g%03d.jpg"` | **成功** |
| `tile` + concat demuxer | **成功**，与上一行**输出字节数完全相同**（84266 B） |

> **修正项目认知**：不是"tile 对多图输入只进首帧"（它会直接报错，不会静默出错），而是 **"tile 只吃单路时序流"**。正确解法不是换 `xstack`，是**改成 image2 序号输入**。

**实测性能（50 张 960×540）**：

| 方案 | 耗时 | 输出 |
|---|---|---|
| A `xstack` + 50 个 `-i`（现状） | 2.35s | 4800×5400 PNG，11.19 MB |
| B `tile` + image2 序号 | 1.96s | 4800×5400 PNG，**11.19 MB（与 A 等价）** |
| C `tile` + `scale=1568:-2` | **0.60s** | 1568×1764，3.12 MB |
| D `tile` + `drawtext` 每格打时间码 | 0.68s | 1568×1764，3.33 MB |

`xstack` 还有两个实测毛病：
- **Windows 命令行长度炸了**：给 A 的滤镜串再加 `[o];[o]scale=1568:-2[out]` 之后，直接报 `文件名或扩展名太长`——已经在临界点上。
- 50 个输入 = 50 个解码器实例，内存与句柄都涨。

### 5.2 总宽上限：算术直接复现了 864 的 5/5 误判

**实测**：项目记录的 864 事故是"640px 联系表 12 列被 1568px 封顶压成每格 131×74"。用 `cell = 1568 / cols` 反算：

| 列数 | 需要总宽 | 1568 封顶后每格 | 判定 |
|---|---|---|---|
| 1 | 960 | 1568×882 | **可读** |
| 2 | 1920 | 784×441 | 勉强 |
| 3 | 2880 | 523×294 | **不可读** |
| 5 | 4800 | 314×176 | **不可读** |
| 12 | 11520 | **131×74** | **不可读 ← 与 864 事故记录逐位吻合** |

**模型可信**：格子宽度只由"总宽上限 ÷ 列数"决定，与源分辨率无关。

### 5.3 真正的上限比 1568 更狠（实测 + 文档）

**文档**（Claude 视觉文档，`platform.claude.com/docs/en/build-with-claude/vision`）：图片超限时按**长边 + 视觉 token 预算**两个约束之一缩放，`token = ⌈w/28⌉ × ⌈h/28⌉`。
- 标准档：**长边 1568px / 1568 token**
- 高分辨率档（Claude 4.7+）：**长边 2576px / 4784 token**
- `>20 张图`的请求还会叠加**每图 2000px 硬拒绝**（不是缩放，是 `invalid_request_error`）→ **我们单轮 50 张图的场景正踩在这条线上，必须每张自己先缩到 ≤2000px。**

**实测**用官方参考实现算出的各档实际尺寸：

| 输入 | 标准档实际收到 | token | 高分档实际收到 | token |
|---|---|---|---|---|
| 2560×1440 | 1456×819 | 1560 | 2560×1440 | 4784 |
| **960×540** | **960×540（不缩放）** | **700** | 960×540 | **700** |

> **960×540 是甜点**：刚好落在两档限制内**都不被缩放**，稳定 700 token。**这就是项目"定性用 960px 单帧"的量化依据，现在有了解释。**

**把 §5.2 的格子表套进 token 预算重算（实测）**：

| 列数 | 标准档（1568px/1568tok）格子 | 高分档（2576px/4784tok）格子 |
|---|---|---|
| 2 | 420px **不可读** | 742px 勉强 |
| 3 | 423px **不可读** | 737px 勉强 |
| 4 | 392px **不可读** | 644px 勉强 |
| 5 | 313px **不可读** | 515px **不可读** |
| 12 | 130px **不可读** | 214px **不可读** |

### 5.4 结论：**联系表在本项目里最多省 2×，不是 25×**

**实测 + 文档**：一张图里能活下来且保持 ≥960px 可读的格子数——
- 标准档：**1 格**（单帧）
- 高分档：**2 格**（2×1 横排）

> 也就是说，项目以为的"50 帧 = 1 张图 = 省 25× 轮次"，**真实上限是省 2×（高分档）或 0×（标准档）**。
> **联系表在本项目不是省时间，是把每格分辨率砍到 1/7 然后让 5 路审片集体误判——864 已经用一次全毁 5/5 审片力证明了这一点。**

### 5.5 唯一实测可行的一图多帧：LENS 式 2×2 hyperframe

**实测 token**：把 4 帧源画面 2×2 拼成一张（不做缩放）：

| 版式 | 拼后尺寸 | token | **每帧 token** |
|---|---|---|---|
| 单帧全尺寸 | 2560×1440 | 4784 | 4784 |
| 单帧缩到标准档 | 1456×819 | 1560 | 1560 |
| **2×2 hyperframe（源 2560×1440）** | 1280×720 | 1196 | **299** |
| **2×2 hyperframe（源 1920×1080）** | 960×540 | 700 | **175** |
| 2×1 横排 | 1280×1440 | 2392 | 1196 |

> **2×2 hyperframe 是唯一"格子仍 ≥960px 可读、又能一图装 4 帧"的版式**：源 1920×1080 → 拼后 960×540 → 每子帧 960×540 刚好达标，**700 token 换 4 帧 = 175 token/帧，比单帧 700 省 4×**。
> 代价：**丢失时间分辨率的细节**——子帧是 1/4 面积，血条/伤害数字只在"复核定性"时能看，"细看"仍需单帧。
> **推断**：这应该取代联系表，成为唯一的"一图多帧"手段。

**推荐替代命令（实测通过）**：

```powershell
# 定位用：4 帧拼一张，每格带序号，缩到 ≤2000px（规避 >20 图的硬拒绝）
$ff='C:\Project\永劫无间\.video-tools\LosslessCut\resources\ffmpeg.exe'
$src='E:\OBS\2026-10-04 15-40-42.mp4'
& $ff -y -v error -ss 300 -i $src -t 50 `
  -vf "fps=0.5,scale=960:540,drawtext=text='%{eif\:n*2\:d}s':x=6:y=6:fontsize=32:fontcolor=yellow:box=1:boxcolor=black,tile=2x2,scale=1568:-2" `
  -frames:v 1 -update 1 "sheet_%02d.jpg"
```
> 关键点：`tile` 单输入（image2 或 `-i` 视频都行）、`scale=1568:-2` 压在两档限制内、JPEG 而非 PNG（§6）、每格 `drawtext` 打真实时间码、`-update 1` 避免 PNG 序列警告。

## 6. Q5 图像 token 优化：**格式不是 token，PNG 是纯浪费**

**实测**（同样 4800×5400 像素）：

| 格式 | 体积 | 相对 PNG |
|---|---|---|
| PNG（现状） | **11.19 MB** | 1× |
| JPEG q=2 | 3.68 MB | 3.0× |
| JPEG q=3 | 2.97 MB | 3.8× |
| JPEG q=5 | 2.34 MB | 4.8× |
| JPEG q=8 | 1.83 MB | **6.1×** |

**关键认知（文档 + 实测）**：**视觉 token 数只由"缩放后的像素尺寸"决定，与文件格式、字节数无关。** 11 MB 的 PNG 和 1.8 MB 的 JPEG 送进 API 后**花的 token 一模一样**（都是缩到 1568×353 = 1568 token）。

> 所以 PNG 不只是慢，是**纯粹白付 6× 的传输与 base64 开销，token 一点不省**。
> ⚠️ 但 10 MB/图（API 上限，bedrock 5 MB）会被拒——11.19 MB 的 PNG **已经超限**，JPEG q=3 的 2.97 MB 才安全。

**裁剪 ROI / 只传差异区（Q5 后半）**：
- **文档**：LENS 的"空间放大"用 CLIP 注意力把与问题无关的区域**灰掉**，把分辨率花在关键处；对剪辑分析可类比成"只裁 HUD 区/中心区"。
- **实测支持**：§5.3 表明 960×540 在两档下都不缩放。**所以 ROI 裁剪应做成"从 2560×1440 裁到 1280×720 的中心区"而不是"缩到 960×540 全图"**——前者保留原始像素密度，后者是重采样。
- **未找到**：开箱即用的"自动裁出游戏 HUD/伤害数字区域"的工具。OpenCV + 模板匹配可自建，但本项目**没有做过 ROI 标注，暂不建议先做这一步**。

## 7. Q6 关键判断：多模态模型读帧这件事，**没有被取代**

**文档**：2026 年确实有"视频原生"路线——Qwen3-VL 技术报告（arXiv 2511.21631）支持 256K 上下文，评测时"每视频最多 2048 帧、总计不超过 224K 视频 token"。Gemini 2.5 Pro 喂 512 帧、GPT-5 喂 256 帧、Claude Opus 4.1 喂 100 帧。

**算一下就知道它不是替代品（实测 + 文档）**：

| 路线 | token 成本 | 与本项目 50 图红线的对比 |
|---|---|---|
| **现状：50 张 960×540 单帧** | 50 × 700 = **35,000 token** | 基准 |
| 视频原生 Qwen3-VL 满配（2048 帧） | **224,000 token** | **贵 6.4×** |
| 视频原生按 1fps 喂 2399 帧 | ~45,000 token（4.8% of 2048 帧上限外的部分需降分辨率） | 与现状同量级，**无收益** |

> **结论**：视频原生模型走的是**"同样送帧、账单更大"**的路子。它绕不开"帧要变成 token"这件事，也绕不开本项目的 50 图上游红线的同类约束。
> **2025–2026 年的真正进展不在"取代读帧"，而在"同样的帧数怎么选得更值"**——即 §3 那批 FOCUS / LENS / GIFT / QCA。它们**全部仍然以"送帧给多模态模型"为前提**。
> **一句话**：读帧没被取代；被取代的是"均匀抽帧"这个默认做法。

## 8. 对现有项目认知的三处修正

### 8.1 `fps=1` 网格落在 +29 帧，不是 +28（实测，逐帧哈希比对）

**实测**：用 `-f framemd5` 逐帧哈希，把 `fps=1` 的输出帧与源帧逐一对撞：

```
fps=1 out #0 -> n=29   (0.4833s)   offset=29
fps=1 out #1 -> n=89   (1.4833s)   offset=29
fps=1 out #2 -> n=149  (2.4833s)   offset=29
```

> 项目记录的 `+0.4667s (+28 帧)` **方向正确、数值差 1 帧**（24ms）。可视为同一结论的两次测量，不影响任何剪辑决策。

### 8.2 但 `-ss T` 作为**输入参数**是**逐帧精确**的（实测）

```
-ss 10  -> 161794227811f4094bfb83a112513d81
n=600   -> 161794227811f4094bfb83a112513d81   ← 完全相同
```

> **这是两件不同的事**：`-ss` 输入定位**精确**；`fps=1` 网格**偏移 +29 帧**。
> **推论**：§7 的"桶内取峰"流水线可以用**时间戳精确回抽**每一帧，不需要担心 `fps` 滤镜的偏移。定位帧请用 `-ss`，不要用 `fps` 网格。

### 8.3 `.ps1` 无 BOM 的乱码故障在本机**当场复现**（实测）

本次调研写的第一个 `.ps1` 因为存成 UTF-8 无 BOM，PowerShell 5.1 把路径里的中文项目名读成乱码，`ffmpeg.exe` 变成 `C:\Project\�����޼�\...` 而**无法启动**。

> 这正是 `AGENTS.md` 里 `[WARN] script encoding` 描述的故障，**它今天仍然是活的**。
> 修法实测有效：`Set-Content -Path x.ps1 -Value $c -Encoding UTF8`（PS 5.1 的 `UTF8` = 带 BOM），或首字节为 `EF BB BF`。
> **建议**：所有新建 `.ps1` 一律带 BOM；`check_video_environment.ps1` 的这条 WARN 值得考虑升级。

## 9. 推荐的抽帧流水线（实测各环节可跑）

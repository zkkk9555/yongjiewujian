## 0. 一句话结论

> **`seg_render_master.sh` 慢，不是因为 ffmpeg 用错了，而是它把两笔纯浪费的钱写死了：`-preset p7` 和一条在 4K60 素材上逐字节空转的滤镜链。**
>
> - **实测：`-preset p7` → `p1`，同参数、同体积，编码时间 3.55×（min-of-6 交错采样），而画质只差 0.42 分 VMAF（90.80 → 91.22，p4 差 0.014 分）——低于"肉眼可辨"的量级。** 这是全场最大的一笔。
> - 补一条实测：**p3 的 VMAF / SSIM / PSNR 三项全部略高于 p7**，在这个码率上 p7 的额外算力**没换来任何可测画质**。
> - **实测：那条 `fps=60,scale=3840:2160:flags=lanczos,setsar=1,format=yuv420p` 滤镜链，输出与完全不写 `-vf` 的结果 `cmp` 逐字节相同**（SSIM 1.000000(inf)）。它值 8.1% 的时间、**零画质**。
> - **实测：`-noaccurate_seek` 一点不快（2.246 s vs 2.350 s），却把切口最多挪 29 帧。项目要求帧级准确 → 直接禁用。**
> - **实测：NVDEC / 纯 GPU 链可用、且输出逐字节相同，但一点不快（0.94×）。瓶颈在 NVENC 编码档，不在解码。别上。**
> - **实测：分段并行能拿 1.2–1.5×（中位 1.54×），但 12 个臂里出现过一次 531.6 s 的卡死**——和 `123\workflow_upgrade\f-render-split.md` 记的 840 事故同源。上并行必须带看门狗。
> - **实测：concat 那一步只占 1.2%（0.26–0.38 s / 24 s 节目）。换成 concat filter 慢 175× 且帧数多 3 帧。现路径是对的，别动。**
> - **实测：项目规则「NVENC 全局锁 / 成片禁并行」在本机不成立**——8 路并发 NVENC 全部成功（8/8，0 失败）。
>
> **净效果（按同会话内比值换算，标注为推断）**：把 preset 降到 p4，4K 240 s 节目 **265 s → 约 130 s（≈2×）**；
> 降到 p1 约 **3.5×**；再加 P=3 并行约 **4×**。
> **但 p4/p1 的画质判定只有客观指标（VMAF/SSIM/PSNR），不能替代人眼抽帧放行。**
> **最该先改的那一条是 `-preset p7` → `p4`：单点、零结构风险、3.55× 的量级里占大头。**

### 1.1 计时方法（必读：本机绝对值不可当预算用）

调研期间同机还有另外两个子会话在跑 4K 基准（`Temp\opencode\early\bench.sh`、`.scratch\aivideo\bench\*.ps1`），
采样时同机 ffmpeg 进程数在 **0–12** 之间波动，CPU **15%–100%**。

因此本报告的三条纪律：

1. **不用单次墙钟**。每个臂 **min-of-N**，并把原始样本全部列出（干扰只会加时间，min 是无竞争成本的最好估计量）。
2. **严格交错**采样（`A B A B …`，并行测试还轮换了 P 的顺序）。这一步不是形式主义——
   **我第一版按顺序扫 preset 得到的"p1 7.89 s → p7 27.67 s，3.5×"看起来很漂亮，但那是负载单调上升造出来的趋势**；
   交错重测后结论的**量级居然仍然成立**（3.55×），但**换一组时间就不成立了**。见 §2.2 的对照表。
3. **同一命令跨会话的绝对值仍可差 50%**：同一条 6 s 4K60 p7 命令，A 会话 min 8.693 s、B 会话 min 10.982 s、
   C 会话 min 16.214 s。**结论只用同会话内的比值。**

## 2. 分段并行：能不能并行？能快多少？

### 2.1 项目里那条"成片禁并行"规则，本机实测不成立

`skills\naraka-highlight-studio\references\time-budget.md` 写：
> "Rendering stays serial: … NVENC encoding holds a single global lock so parallel jobs cannot wedge the driver."

`roughcut-launch.md` §2 写：「成片 NVENC 全局锁只认冻结版（预览可并行，**成片禁并行**）」。

**实测（8 路并发 NVENC，单张 RTX 4060 Ti）**：

| 项 | 值 | 标注 |
|---|---|---|
| 8 路并发 `h264_nvenc -preset p7`（各 4 s 720p） | **ok = 8/8，非零退出 0**，墙钟 **5.851 s** | 实测 |
| 单路同规格（4 s 720p p7）min-of-3 | **4.144 s**（原始 4.299 / 4.699 / 4.144） | 实测 |

**读法**：8 路并发的总耗时只有单路的 **1.41×**——**吞吐近似 5.7×，驱动没有卡住、没有丢帧、没有非零退出。**
"NVENC 全局锁"这个前提在这台卡 + 这版驱动上**是错的**。

> ⚠️ **但这不等于"可以放心开并行"**——见 §2.3 的卡死观测。

### 2.2 并行加速比实测（4 段 × 6 s = 24 s 节目，脚本链原文）

`T11`，每个 P **4 轮、轮换顺序**，并采样运行期的 GPU/NVENC 利用率：

| P | min (s) | median (s) | 加速比（按 min） | 原始样本 |
|---|---|---|---|---|
| **1（现状，串行）** | **48.301** | **64.936** | 1.00× | 64.936 / 48.301 / 70.814 / 70.455 |
| 2 | 41.331 | 43.562 | 1.17× | 54.152 / 41.331 / **531.640** / 43.562 |
| 3 | 39.751 | 42.483 | 1.22× | 39.751 / 55.441 / 60.490 / 42.483 |
| **4** | **38.584** | **42.042** | **1.25×** | 38.584 / 53.106 / 85.654 / 42.042 |

- **按中位数算是 1.54×**（64.936 → 42.042），按 min 算是 **1.25×**。
- **P≥3 之后基本没有边际收益**（P3 39.751 / P4 38.584，差 3%）。**建议 P=3，不要上 P=4。**
- 内部一致性检查通过：**单独渲一段 6 s 的 min 是 16.214 s，×4 = 64.9 s，与 P=1 的中位 64.936 s 吻合**。

运行期 NVENC 利用率（`nvidia-smi utilization.encoder`）**在 P=1 时就已经是 84%–100%**：
说明串行单跑时编码引擎本来就没闲下来，并行能拿到的 1.2–1.5× 是靠**把解码/滤镜/音频/磁盘这些非编码时间藏进编码的空隙**，
**不是靠"多开编码器"**。这也解释了为什么加速比远低于线性。

### 2.3 ⚠️ 并行的真实代价：一次 531.6 s 的卡死

`P=2` 的第 3 轮，24 s 的节目渲了 **531.640 s**（正常 41–54 s，**慢 10–13×**），同轮 P1/P3/P4 都正常（70.8 / 60.5 / 85.7 s）。

这和 `123\workflow_upgrade\f-render-split.md` 记的 840 事故是同一类现象：
> "单条 6/8 路大 `filter_complex` 在 840 ep2 内约 150 s 处卡死：同一帧 20 分钟无进展、无报错"

**判定（推断）**：这台机器在多路并发编码下**确实存在病理性卡死**，机制未查明（没有留下 ffmpeg 日志）。
**含义**：`time-budget.md` 那条"禁并行"的规则，**很可能就是被这类事故逼出来的**——它防的不是驱动锁，是卡死。
**所以正确的结论不是"删掉规则"，而是"上并行必须同时上超时看门狗 + 单段失败即中止并落日志"**（§8 第 5 条）。

### 2.4 并行不影响成片正确性（实测）

|---|---|---|---|---|

## 3. `-noaccurate_seek` / keyframe-only seek：能快多少？帧级误差多少？

**结论：不快，而且破坏帧级准确。直接禁用。**

### 3.1 边界误差实测

参考基准用**素材自身的帧栅格**（CFR 60/1 + 起始 pts 0），不是"另一条同管线"——
这是 `docs\lessons\POOL.md` L-052 说的循环论证坑，本报告特意避开。

```bash
ffmpeg -hide_banner -v info [-noaccurate_seek] -ss <T> -i src.mp4 -frames:v 1 -vf showinfo -f null -
```

| target (s) | 精确 seek 首帧 pts | `-noaccurate_seek` 首帧 pts | 帧误差 |
|---|---|---|---|
| 5 | 0 | 0 | **0** |
| 5.4 | 0 | −0.4 | **−24** |
| 5.9833 | 0.0000333333 | −0.4833 | **−29** |
| 6.0167 | 0.0166333 | −0.0167 | **−1** |
| 6.5 | 0 | 0 | **0** |
| 7.3 | 0 | −0.3 | **−18** |
| 35 | 0 | 0 | **0** |
| 95.733 | 0.000333333 | −0.233 | **−13** |
| 155.25 | 0 | −0.25 | **−14** |
| 245.5 | 0 | 0 | **0** |
| 275.0167 | 0.0166333 | −0.0167 | **−1** |
| 293.7 | 0 | −0.2 | **−11** |

**读法**：

- **默认（精确）seek 是帧级的**：落在"第一帧 ≥ 目标"，误差恒为 **0 或 +1 帧**（只取决于目标是否正好卡在两帧之间）。这正是项目要的。
- `-noaccurate_seek` 落在**目标之前最近的那个 IDR**：误差 **0 … −29 帧**，上限由 GOP=2 s=120 帧封顶。
  `t=6.0167` 只差 1 帧，是因为 6.0 恰好是 IDR——**说明误差取决于素材的 GOP 相位，完全不可控**。
- **`-fflags +fastseek` 对 MP4 完全无效**：实测 pts 与精确 seek 逐位相同（`t=5.4 / 95.733 / 245.5` 三点全同）。MP4 本来就有完整索引。
- **`-noaccurate_seek -copyts` 也救不回来**：实测 pts=5（原始时间戳），画面起点仍是那个关键帧。

### 3.2 收益实测：**0**

| 项 | 墙钟 (s) | 标注 |
|---|---|---|
| 10 s 4K60 解码，**精确** seek | **2.246** | 实测 |
| 10 s 4K60 解码，`-noaccurate_seek` | **2.350** | 实测 |
| 裸 `-ss 299.5 -c copy -f null`（纯 demux 跳转，零解码） | **0.093** | 实测 |
| `-ss 155 -to 165 -f null`（解 10 s） | **1.851** | 实测 |
| `-ss 155` 直到 EOF（解 145 s） | **26.033** | 实测 |

**为什么不快**：MP4 有完整索引，`-ss` 跳转本身只要 **0.093 s**；精确 seek 相对 keyframe seek 多付的钱
只是"从前一个 IDR 解到目标帧"——**最多 1 个 GOP = 120 帧**，不到 0.35 s，被秒级的解码时间淹没，测出来是噪声。

**磁盘 I/O 也不是瓶颈**：同一段 `-c copy` 走盘只要 0.093 s。

> **「keyframe-only seek 能快很多」这个假设在本项目素材上不成立。**
> `-noaccurate_seek` 唯一成立的场景是不要求帧级准确的场合（比如自己抽缩略图），
> 而本项目**明确要求帧级准确**。**判定：禁用，且没有理由解禁。**

## 4. decode 加速：`-threads` / NVDEC / GPU 滤镜链

### 4.1 `-threads` 怎么设最优？—— **别设**

解码 6 s 4K60（`-f null`，min-of-3，原始样本一并列出）：

| `-threads` | min (s) | 原始样本 |
|---|---|---|
| **0（auto，默认）** | **0.789** | 0.789 / 0.799 / 0.824 |
| 1 | 4.069 | 4.098 / 4.069 / 4.106 |
| 2 | 2.351 | 2.392 / 2.351 / 2.833 |
| 4 | 1.505 | 1.553 / 1.559 / 1.505 |
| 8 | 0.981 | 0.981 / 0.989 / 0.983 |
| 16 | 0.912 | 0.912 / 0.917 / 0.940 |

| `-thread_type`（threads=8） | min (s) |
|---|---|
| frame | 1.003 |
| slice | **4.088**（差 4×） |
| **slice+frame（默认）** | **0.973** |

**结论（实测）**：ffmpeg 的 `-threads 0`（auto）**已经比任何手填值都快**（0.789 vs 16 线程的 0.912），
`-thread_type` 默认的 `slice+frame` 也是最优的。**在脚本里加 `-threads` 只会变慢。**

> ⚠️ **但这只对独占的单条 ffmpeg 成立。** 上了并行（§2）之后，每路都开满 16 线程会互相抢核，
> 必须反过来收窄到 `-threads <16/P>`。**这一点我没有实测（时间不够），标为推断。**

### 4.2 NVDEC 在本机可用吗？—— 可用，但**必须写对参数**

**实测四种写法：**

| 写法 | 结果 |
|---|---|
| `-hwaccel cuda -hwaccel_output_format cuda` + CPU 滤镜（`hwdownload,format=yuv420p,scale=...`） | ✅ 能跑 |
| `-c:v h264_cuvid`（CUVID 专用解码器） | ✅ 能跑，但 `-ss` 快寻址路径不同，不推荐 |
| `-hwaccel cuda … -vf scale_cuda=…` **但保留 `-pix_fmt yuv420p`** | ❌ **报错**：`Impossible to convert between the formats supported by the filter 'Parsed_scale_cuda_0' and the filter 'auto_scale_0' … src: cuda  dst: yuv420p …` |
| `-hwaccel cuda … -vf scale_cuda=…` 且 `-pix_fmt cuda` | ✅ **能跑，零主机回读** |

**这是最容易踩的坑，值得单列：**
`-pix_fmt yuv420p`（`seg_render_master.sh` L96）会让 ffmpeg 认定"编码器只吃系统内存帧"，
于是在 `scale_cuda` 之后**自动插一个 `auto_scale` 把 CUDA 帧下载回主机**——想省的那次搬运被加回来了，
而且因为图里没有 CUDA→CPU 转换器，直接 link 失败。**要让 `h264_nvenc` 直接吃 CUDA 帧，必须写 `-pix_fmt cuda`。**

实测该编码器确实支持 CUDA 像素格式：

```
$ ffmpeg -h encoder=h264_nvenc
Supported pixel formats: yuv420p nv12 p010le … cuda d3d11
```

### 4.3 GPU 链快多少？—— **不快，别上**

`T8.3`，6 s 4K60，脚本链 vs GPU 链，**交错 4 轮**：

| 臂 | min (s) | median (s) | 原始样本 |
|---|---|---|---|
| 脚本链（CPU 解码 + lanczos） | 9.415 | 10.504 | 10.683 / 10.504 / 9.415 / 12.584 |
| **GPU 链（NVDEC + `scale_cuda` + `-pix_fmt cuda`）** | 9.988 | 10.445 | 10.445 / 9.988 / 12.597 / 15.627 |

**GPU 链是 0.94× —— 没有加速，噪声范围内。**

**为什么**：解码只占整条链的一小段（§4.1：6 s 4K60 纯解码 **0.789 s**，而整条链 ~10 s）。
把解码搬下 GPU 最多只能省 ~8%，而 `scale_cuda` 本身有 GPU 提交开销、NVENC 才是真瓶颈。

**顺带回答题面那个担心——「用了 NVDEC 后 filter 链还能不能用 CPU？回读两次搬运会不会反而更慢？」**

**答：会，而且这就是实测到的结果。** `-hwdownload` 版本要把每帧搬回主机，收益被搬运吃掉，
所以 NVDEC 在这条链上**净收益为零**。GPU 全驻留（`scale_cuda` + `-pix_fmt cuda`）能避开搬运，
但也没能变成瓶颈的解药。

**一个有价值副产品**：GPU 链的输出与脚本链**逐字节相同**（`SSIM Y:1.000000 (inf)`，360 帧 / 6.000 s / `60:1`）。
**所以"源=目标分辨率时换 GPU 链"是一个零画质风险的等价改写**——只是**不提速**，没有理由上。

## 5. concat 的最快方式（2026 最佳实践）

**实测：4 段 × 6 s = 24 s 节目（60.6 MB），同一台机器**

| 方法 | 墙钟 (s) | 帧数 | 时长 (s) | `avg_frame_rate` |
|---|---|---|---|---|
| **concat demuxer `-c copy -movflags +faststart`（现脚本）** | **0.381** | 1440 | 24.021333 | **60/1** |
| concat demuxer `-c copy`，无 faststart | **0.283** | 1440 | 24.021333 | **60/1** |
| concat demuxer + 每段 `duration` 指令 | 0.282 | 1440 | 24.021333 | **60/1** |
| demuxer → matroska → mp4 copy（两步） | 0.334 + 0.147 = **0.481** | — | — | — |
| **concat filter**（对已渲好的 4 段重编码） | **66.767** | **1443** | 24.064 | 60/1 |
| **4×(`-ss -to -i`) 多输入 + concat filter，无中间件** | **69.394** | 1440 | 24.000 | 60/1 |

**结论**：

1. **concat 本身根本不是瓶颈**（0.26–0.38 s / 24 s 节目 ≈ **1.2%**）。想靠换 join 方式提速，**天花板就是 1%**。
2. **不要换 concat filter**：它要把已渲好的段**再解码再编码一遍**（66.8 s vs 0.38 s，**175×**），
   而且实测**帧数从 1440 变成 1443**——每个接缝多吐 1 帧。本项目要求帧级准确，这是**负收益**。
3. **多输入单进程（"无中间件"）也不划算**：69.4 s，而"分段渲 + concat" 是 4×10.5 + 0.4 ≈ 42 s。
   **省下的中间件磁盘（60 MB）远不值 27 s。**
4. **`+faststart` 值不值**：0.381 − 0.283 = **0.098 s**（24 s 节目）。成片是给用户本地播的，**这 0.1 s 不值得省**。
5. **`duration` 指令**：ffmpeg 文档说它 "more efficient"，**实测无差别**（0.282 vs 0.283）。
   可以加（整片可 seek、`verify` 时长更稳），**但别当提速手段汇报**。

> **并且：`concat demuxer` 没有复现 L-057 担心的帧率退化。** 实测 `3×6s`（18.021333 s / 1080 帧）
> 和 `4×6s`（24.021333 s / 1440 帧）两种规模，`avg_frame_rate` 都是**精确的 `60/1`**，
> 帧数与 `秒数 × 60` **完全相等**。唯一偏移是**容器时长比节目长约 1 帧**（音频首帧 priming，0.021 s），
> `verify_master.sh` 容差 2 s，**过**。

## 6. ffmpeg 8.x 里有没有专门针对"批量切片段"的新特性？

**未找到。** 8.0/8.1 的发布说明里没有任何一项是"为批量切片段 / 多段渲染而设计"的。以下为**文档**结论
（读 ffmpeg 官方 8.0 发布公告 + 本机 `-version` / `-filters` 实测确认可用性）：

| 8.x 相关项 | 与本场景相关性 | 标注 |
|---|---|---|
| GPU 缩放 `scale_cuda` / `scale_vulkan` / `scale_d3d11` / `scale_vaapi`（8.0 新增 `pad_cuda`、`scale_d3d11`） | **相关**——本机全部可用，实测 `scale_cuda` 能让整条链留在显存 | 文档 + 实测可用性 |
| 8.0 大量 ASM 优化（"significant performance benefits for **AVX-512** CPUs"） | **不适用**——7800X3D 是 Zen4，无 AVX-512 | 文档 |
| 8.0 Vulkan compute codec（FFv1 / ProRes RAW） | 无关（本项目是 H.264） | 文档 |
| 8.0 原生 AAC 编码器脱离 experimental | 无关（本项目音频本来就该 `-c:a copy`） | 文档 |
| 8.1 swscale Vulkan、D3D12 H.264/AV1 编码、Windows.Graphics.Capture | 不相关（8.1；本机是 8.0-23） | 文档 |
| concat demuxer 的 `duration` 指令 / `-segment_time_metadata` | 弱相关，实测**不提速** | 文档 + 实测 |
| `-fflags +fastseek` | 实测对 MP4 **无效** | 文档 + 实测 |

**真正管用的"新特性"其实是老特性 + 正确用法**：`-ss` 前置快进 seek、concat demuxer `-c copy`、
以及**硬编码目标分辨率的滤镜必须先核对源分辨率**（§7 第 2 条）。

## 7. `scripts\seg_render_master.sh` 现况 + 可改进的具体点

### 7.1 它现在做了什么（读码，L87–104）

```bash
for ((i=0; i<N; i++)); do                     # ← 完全串行；本项目典型 N=109 段
  "$FF" -hide_banner -y -v error -ss "$S" -to "$E" -i "$SRC_W" \
    -vf "fps=60,scale=3840:2160:flags=lanczos,setsar=1,format=yuv420p" \   # L92 空转
    -c:v h264_nvenc -preset p7 -tune hq -profile:v high -level:v 5.2 \      # L93 最贵的档
    -rc vbr -b:v 18M -maxrate 28M -bufsize 56M -g 120 -bf 2 \               # L94
    -spatial-aq 1 -temporal-aq 1 -aq-strength 8 \                            # L95
    -pix_fmt yuv420p -r 60 -fps_mode cfr \                                  # L96
    -c:a aac -b:a 320k -ar 48000 -ac 2 "$SEG"                               # L97 音频白编一遍
done
"$FF" -f concat -safe 0 -i concat.txt -c copy -movflags +faststart "$OUT"   # L103-104 这步是对的
```

一句话：**每段跑一条在 4K60 素材上逐字节空转的滤镜链、用最贵的 nvpreset、把已经是 AAC 48k 立体声的源再编一遍 AAC，
完全串行地渲 100 多段，最后 `-c copy` 拼起来。**
**拼接那步是对的，前面每一条都还有水分。**

### 7.2 可改进的具体点（按实测收益排序，每条带证据 + 风险）

| # | 改动 | 实测依据 | 风险 |
|---|---|---|---|
| **1** | **`-preset p7` → `p4`（或 `p3`）** | §2.2 表：**p7 min 8.693 s vs p1 min 2.446 s = 3.55×**；§8 画质：**p4 与 p7 的 VMAF 差 0.014 分 / SSIM 差 0.00007 / PSNR 差 0.03 dB**，且 **p3 三项指标全部略高于 p7** | **零风险档位建议 p4。** 本报告只能证"三项客观指标无差"，**证不了"肉眼无差"**——上线前必须人眼抽帧对比。**p1 需单独放行**（VMAF 掉 0.42 分，是三者里唯一有可见余量的） |
| **2** | **删掉 `scale=3840:2160:flags=lanczos`，改成"源分辨率 ≠ 目标才加"** | §8 A6：脚本滤镜链输出与 `-vf format=yuv420p` 的输出 **`cmp` 逐字节相同**、SSIM=1.000000(inf)；§2.3 T8.2：去掉后 min 10.982 → 10.095（**0.92×，省 8.1%**） | **零画质风险（已证明逐字节相同）。** 但注意：**源不是 3840×2160 时这行现在会把画面放大**——那是**既存 bug，不是优化**，顺手修掉 |
| **3** | **`fps=60` 与 `setsar=1` 同样按需加** | 源实测 CFR 60/1、SAR 1:1，两者都空转（同上逐字节相同）；且 **`setsar` 不接受 cuda 帧**，是 GPU 链的拦路虎（§4.2 实测报错） | 零画质风险 |
| **4** | **`-c:a copy` 代替 `-c:a aac -b:a 320k -ar 48000 -ac 2`** | §8 A7：源就是 AAC LC/48k/stereo。`-c:a copy` 实测 `aac,48000,2,317413`（**比特级原样**）；重编后 `aac,48000,2,252620`。**重编既慢又掉音质** | 需确认 concat demuxer 的"各段流参数一致"仍成立（成立：同一源同一参数）。**低风险** |
| **5** | **串行 for → 有上限的并行（P=3）+ 强制超时看门狗** | §2.2：**P=3 中位加速 1.54×**；§2.1：8 路 NVENC 并发全部成功；§2.4：并**不损帧级准确** | **必须同时上超时/单段失败即中止并落日志**——§2.3 观测到 **P=2 出现过 531.6 s 卡死**（正常 41–54 s）。**并且这是流程规则变更（要改 `time-budget.md` 的"成片禁并行"），不是改脚本就行** |
| **6** | **并行时每路加 `-threads <16/P>`** | §4.1：独占时 auto 最优；并发时 auto 会让每路开满线程 | **推断，未实测。** 需实测 P × threads 矩阵 |
| **7** | **concat list 加每段 `duration` 指令** | 文档说 "more efficient"，**实测 0.282 vs 0.283 无差别** | 零风险，但**不要当提速手段汇报** |
| **8** | **不要动 concat 那一步** | §5：0.26–0.38 s = 1.2%；换 concat filter 慢 **175×** 且帧数多 3 帧 | — |
| **9** | **不要上 GPU 链（`-pix_fmt cuda` + `scale_cuda`）** | §4.3：0.94×，**不提速**；且 `scale_cuda` 没有 lanczos | 输出逐字节相同（SSIM inf），所以是安全的**等价**改写，但**没有理由上** |
| **10** | **不要加 `-threads`、不要加 `-noaccurate_seek`** | §4.1：auto 已最优（0.789 vs 0.912）；§3：noaccurate 不快且最多偏 29 帧 | 加了就是变慢 + 破帧级准确 |

## 8. 画质：降 preset 到底损不损？（对**源**测，不是对另一个编码测）

> 标定纪律：参考帧取**源片解码帧**，不与被测对象共用管线（`POOL` L-052 的循环论证坑）。
> 6 s 4K60，脚本原参数（VBR 18M/28M/56M，AQ 全开，p7 与各档同参）。
> VMAF 滤镜链按 `[1:v][ref]` 顺序（编码结果在前、源在后），各档用**同一区间** `[155,161)`。

| preset | **VMAF** vs 源 | SSIM (All) vs 源 | PSNR avg (dB) vs 源 | 输出 kbps | 编码 min (s) |
|---|---|---|---|---|---|
| p1 | 90.799 | 0.986070 | 42.394 | 18 917 | **2.446** |
| **p3** | **91.542** ← 最高 | **0.987175** ← 最高 | **42.858** ← 最高 | 19 136 | — |
| p4 | 91.205 | 0.987030 | 42.751 | 19 255 | — |
| p5 | 90.902 | 0.986804 | 42.639 | 19 187 | — |
| **p7（现脚本）** | 91.219 | 0.987099 | 42.777 | 19 559 | **8.693** |

**读法（这条是全场最有价值的画质实测）**：

- **p1 → p7 的全部跨度：VMAF 90.80 → 91.22，即 0.42 分。** VMAF ≥ 90 属于"绝大多数观众看不出差别"的区间。
- **p4 与 p7 的 VMAF 差 0.014 分**（91.205 vs 91.219），SSIM 差 0.00007，PSNR 差 0.03 dB——**三项指标一致地判定"没有差别"**。
- **p3 的三个指标全部略高于 p7**（VMAF 91.542 / SSIM 0.987175 / PSNR 42.858）。
  **在这个码率、这个内容上，p7 的额外算力没有换来任何可测的画质——反而是 p3 最高。**
- 而 p7 的代价是 **3.55× 的编码时间**（2.446 s vs 8.693 s）。

⚠️ **三条必须一起读的告诫**：

1. **样本只有一段 6 s / 360 帧**，只覆盖这一段内容的难度。
   **换几段不同难度（高运动/大特效/暗场/大地图）复测后再定档。**
2. **本项目素材是 4K 竞技游戏画面**（大量 UI 文字、高频细节、小面积高对比），
   这类内容对编码器"工具数"的要求与自然视频不同。**SSIM/PSNR/VMAF 对 NVENC 的时域伪影
   （涂抹、闪烁、块边界游走）不敏感**，所以"三指标一致"是必要条件，不是充分条件。
   **上线前必须人眼抽帧对比。**
3. **码率本身才是主变量。** 全部档位都锁在 VBR 18M，输出 18.9–19.6 Mbps，
   彼此只差 3.4%。**如果嫌画质不够，该动的是 `-b:v/-maxrate`，不是 preset。**
   （本报告**没有实测**码率敏感性。）

### 附：一次被自己的噪声骗过的记录（留给下一个人）

第一版我按 `p1 → p3 → p4 → p5 → p6 → p7` 的**顺序**扫 nvpreset，得到一条漂亮的单调曲线
（7.890 → 8.569 → 12.338 → 17.623 → 27.405 → 27.667，p7/p1 = 3.51×），

> **教训（在负载会漂的机器上，这条比任何单条数字都值钱）**：
> **顺序扫描 = 伪造趋势。** 哪怕最后蒙对了量级，你也说不清哪个部分是负载、哪个部分是信号。
> 交错 + min-of-N + 原始样本全列，是唯一能拿去汇报的形式。

## 2. 预览阶梯：各档要多久（GPU 空闲轮）

### 2.1 完整阶梯

来源：`final.sh`，8 段 × 30 s，GPU 0–1% / 534 MiB，`seg_render_master.sh` 同拓扑（`-ss` 前置 + 分段 + `concat -c copy`）。

| 档 | 编码参数 | 240 s 节目墙钟 | s 节目/s 墙钟 | 实时倍速 | 体积 |
|---|---|---|---|---|---|
| **720p60** | `h264_nvenc -preset p5 -b:v 8M -maxrate 12M -g 60` | **29.378 s** | 0.122 | **8.2×** | 242 MB |
| **540p60** | `-preset p4 -b:v 5M -maxrate 7M -g 60` | **26.504 s** | 0.110 | 9.1× | 121 MB |
| **480p60** | `-preset p1 -b:v 3M -maxrate 4M -g 60` | **28.043 s** | 0.117 | 8.6× | 91 MB |
| 720p60（复跑） | 同第一行 | **29.559 s** | 0.123 | 8.1× | 242 MB |
| **4K60 母版** | `-preset p7 -tune hq -rc vbr -b:v 18M -maxrate 28M -bufsize 56M -g 120 -bf 2 -spatial-aq 1 -temporal-aq 1 -aq-strength 8` | **244.511 s** | 1.019 | **0.98×** | 550 MB |
| 4K60 母版（复跑） | 同上 | **259.485 s** | 1.081 | 0.92× | 550 MB |

> **标注：实测。** 两轮 720p（29.378 / 29.559）差 0.6%，两轮 4K（244.5 / 259.5）差 6.2%——母版档抖动大是因为它跑 25 秒对 1 秒，采样噪声占比高。
>
> **⚠ 这与项目历史记录不一致，必须记下来**：`07-delivery-wait.md §4.3` 记 864 真实 4K 母版是
> 799 s 节目 / 882 s 墙钟 = **1.104× 实时**，而本次实测 240 s 节目 / 252 s = **0.98× 实时**。
> 两者都在"约 1× 实时"这个量级，不是矛盾；但**新脚本如果照抄 `-preset p7`，不要指望快于实时**。

### 2.2 决定性比值：预览 : 母版

交错重复（`final.sh` 的两轮）：

```
720p  29.378 s  /  29.559 s
4K   244.511 s  / 259.485 s
比值  8.32×      /  8.78×
```

> **标注：实测。预览约等于母版的 1/8.5。**

**为什么这条最重要**：它意味着**"先渲低清预览、授权后再渲 4K"这个折中在时间上几乎不成立**——
低清预览只要 30 s，母版要 252 s，**两者都在 5 分钟以内**。
所以 07 号报告 P0 建议的"先渲到 `cache\seg4k\`、授权后只重跑 concat"（实测 concat 只要 0.75–0.9 s）之所以成立，
**靠的不是"低清更快"，而是"concat 几乎是免费的、可以先渲 4K 段再等授权拼"**。这两件事别混。

### 2.3 降分辨率为什么不省时间（这一条纠正了一个直觉）

同一轮、同一批切口，720p → 480p 只从 29.4 s 掉到 28.0 s，**省 4.7%**；720p → 540p 省 9.8%。

单段逐项拆（`isolate.sh`，**该轮 GPU 49%、被污染，仅看量级关系**）：

| 步骤（30 s 切口） | 墙钟 | s/s |
|---|---|---|
| 只解码（`-f null`） | 3.467 s | 0.014 |
| 解码 + `scale=1280:720` | 5.150 s | 0.021 |
| 解码 + `scale=854:480` | 5.066 s | 0.021 |
| 720p `nvenc p5`（含编码） | 5.453 s | 0.023 |
| 480p `nvenc p1`（含编码） | 5.118 s | 0.021 |
| 720p `libx264 -preset veryfast` | 8.187 s | 0.034 |
| 4K `nvenc p7`（含编码） | 42.290 s | 0.176 |

> **标注：实测（该轮绝对值被污染，比值可用）。**
> **720p 档里，"解码+缩放"就占了 5.150/5.453 = 94% 的时间，编码本身几乎不花钱。**
> 降到 480p 省的是那 6% 里的一部分，所以整体只省 5%。
>
> **推论（推断）**：`final.sh` 里 240 s 节目 29.4 s 换算成 0.122 s/s，而单段是 0.023 s/s——差 5.3 倍。
> 差额来自 **8 次 `-ss` seek 落在 3.2 GB 的 4K 文件的 8 个不同位置**，每次都要重新起解。
> 也就是说：**切得越碎、跨度越大，seek 开销占比越高，而分辨率越低这个占比越难看。**
> **推论**：预览档若真要再快，杠杆在"少 seek"（代理一次建好、之后在代理上切）而不是"降分辨率"——但代理实测只省 5–8%（§3），远小于预期。

## 4. 流式 / 增量渲染：三种机制，都实测过

### 4.1 【最有用】分段渲 + 每段落地就拼已完成前缀 —— 简称"前缀 concat"

`earlywatch.sh`：渲一段 → 立刻把 `[0..i]` concat 一次 → 每落一段都产出一个更长的可播放文件。

```
after seg0: seg=5432ms  wip-concat=131ms  total_since_T0=5574ms
after seg1: seg=5298ms  wip-concat=170ms  total_since_T0=11846ms
after seg2: seg=5524ms  wip-concat=265ms  total_since_T0=19229ms
after seg3: seg=5609ms  wip-concat=301ms  total_since_T0=27301ms
after seg4: seg=5412ms  wip-concat=391ms  total_since_T0=36121ms
after seg5: seg=5503ms  wip-concat=444ms  total_since_T0=45917ms
after seg6: seg=5624ms  wip-concat=505ms  total_since_T0=56660ms
after seg7: seg=5325ms  wip-concat=582ms  total_since_T0=67834ms
FINAL full preview: 74236 ms
```

`ffprobe` 复核每个 wip 文件（全部可解码、时长精确）：

| 文件 | 时长 |
|---|---|
| `wip-0.mp4` | 30.021333 s |
| `wip-1.mp4` | 60.021333 s |
| `wip-2.mp4` | 90.021333 s |
| … | … |
| `wip-7.mp4` | 240.021333 s |

> **标注：实测。**
> **第一版可看预览 = 5.574 s**（第一段落盘 + 131 ms concat）。批量路径要 74.2 s 才出第一个文件。
> **提前量 = 68.7 s / 13.3×。** 换算到真实项目（864 的 807.5 s 节目、31 个 episode 段）：
> 720p 全片预览约 807.5 × 0.122 = **98.6 s**，第一段约 **3–6 s**。
>
> **concat 成本随段数增长**：131 → 582 ms（8 段）。31 段时约 1.5–2.5 s，相对每段 5 s 的编码仍是小头。
> **推断（未实测到 31 段）**：段数上百时 concat 会线性涨，届时应改成"每 k 段一个 wip"而不是每段一个。

### 4.2 fMP4（fragmented MP4）：编码中途真的能解码

`fm3.sh`：全片编码到 `+frag_keyframe+empty_moov+default_base_moof`，编码仍在跑时抓文件。

```
=== PARTIAL FILE IS 13107228 bytes ===
duration=25.050000
--- decode frames from INSIDE the partial region (t=2, t=10) ---
fm03.jpg   56707 bytes
fm03b.jpg  49165 bytes
```

> **标注：实测。** 中途的 fMP4 不只是能被 `ffprobe` 读出 stream 信息，**能真的抽出 t=2s 和 t=10s 两帧**。
> 这条对"用户边渲边看"成立，但**对本项目价值不大**——因为 §4.1 的前缀 concat 已经能做到同样的事，
> 而且产物是**普通 MP4**（能拖进任何播放器、能被门禁脚本用 `ffprobe` 查、能挂外挂 SRT），
> fMP4 的好处（可流式播放）对一个本地文件没有意义。
>
> **文档**：`ffmpeg-formats.html §4.4.2 Fragmentation` 是 `-movflags +frag_keyframe/+empty_moov/+default_base_moof` 的出处。

### 4.3 HTTP / HLS

> **未找到**：本项目**不需要**。理由是本地单机交付，没有网络环节。
> `ffmpeg-protocols.html` 确认 `-listen 1`（实验性 HTTP 服务端）和 `hls` muxer 都存在，

## 5. 续跑渲染：ffmpeg 支持到什么程度

### 5.1 ffmpeg 本身：**没有 resume，这是事实**

> **文档 + 项目既有实测**：`scripts\seg_render_master.sh:87-100` 是 `for ((i=0; i<N; i++))` 无条件循环，
> `-y` 覆盖，不看 `seg_i.mp4` 是否已存在。`123\18.860…\reports\freeze_gate_master_18_v7.md:62` 已写明这一点。
> ffmpeg CLI **没有任何"从上次位置继续"选项**——它是无状态的一次性进程。

### 5.2 但"续跑"是脚本层的事，20 行就能做完，且已实测

`resume_test.sh` 做了三件事：

**（a）校验而不是只看文件存在**（这是关键，只判 `-s` 会把 863 那种白渲重演一遍）：

```bash
valid_seg () {   # 文件 + 期望时长 -> 可解码且时长差 <0.2s 才算有效
  [ -s "$1" ] || return 1
  local d
  d=$("$FP" -v error -show_entries format=duration -of csv=p=0 "$1" 2>/dev/null) || return 1
  [ -n "$d" ] || return 1
  "$FF" -v error -i "$1" -f null - 2>/dev/null || return 1
  awk -v a="$d" -v b="$2" 'BEGIN{exit !(a>b-0.2 && a<b+0.2)}'
}
```

实测把 `seg_1.mp4` 截断到 500 KB 后：

```
--- corrupt segment 1 (truncate to 500KB) to test validation ---
  GOOD: truncated seg1 rejected
```

**（b）续跑**（复用通过校验的段、重渲其余）：

```
=== pass 2: resume ===
  seg0 REUSE
  seg1 RENDER          <- 被截断的那段
  after1: segs 0..2 -> preview duration=90.021333 s
  seg2 REUSE
  seg3 RENDER
  after3: segs 0..3 -> preview duration=120.021333 s
  ... (每段渲完立刻产出更长的预览)
  seg7 RENDER
RESUME pass2 reused=2 fresh=6 wall=117854ms
```

> **标注：实测。`reused=2 fresh=6`，全部 8 段最终时长逐位精确，续跑零返工。**
> 注意 `afterN` 那一列：**这同时就是 §4.1 的前缀 concat**，两者在同一个循环里免费搭车。

**（c）ETA 心跳**：见 §6。

> **结论（实测）**：ffmpeg 不支持续跑，**但续跑不需要 ffmpeg 支持**——
> 「分段落盘 + ffprobe 校验 + 跳过已验证段」是纯脚本逻辑，20 行，零依赖，本机已跑通。
> 这与 07 号报告 §6.1 的 A 项（把 860 那份已验证的 `cache\render_master_resume.sh` 从 `cache\` 提到 `scripts\`）是同一件事，
> **07 号说它「被 cleanup_after_master.ps1 当垃圾删了」——本文补一条：那 20 行现在有实测背书，不再是"某个任务目录里的口头知识"。**

## 6. ETA 与心跳：用户不要被问，但要不要被告知

### 6.1 原生机制：`ffmpeg -progress`

> **文档**：`ffmpeg -progress pipe:1 -nostats` 让 ffmpeg 把 `out_time_us` / `total_size` / `frame` 等
> **机器可读的键值**打到 stdout，而不是给人看的 `speed=0.7x` 滚动条。
> 与 `-stats_period 1` 配合即每秒一行。

`heartbeat.sh` 实跑输出（节选）：

```
[05:25:18] seg 1/8  src=0s  program=30s
    3%  1.00x realtime  seg-ETA 29s  elapsed 1s
   26%  1.60x realtime  seg-ETA 13s  elapsed 5s
   53%  1.60x realtime  seg-ETA 8s   elapsed 10s
   90%  1.50x realtime  seg-ETA 2s   elapsed 18s
[05:25:37] seg 2/8  src=60s  program=30s
    0%  0.00x realtime  seg-ETA 30s  elapsed 1s
   ...
```

换算逻辑只有 4 行（`out_time_us / 1000000` = 已渲节目秒；除以 `elapsed` = 倍速；`(DUR-OT)*EL/OT` = ETA）。

> **标注：实测 + 文档。**
> **这一条直接对上"用户明确不要被问"这条诉求**：心跳是**单向播报**，不问任何问题、不要求确认、
> 不改变任何控制流。它和"分段汇报"是两件事——用户拒绝的是**要他做决策**，
> 不是**让他知道机器还活着**。07 号报告 §1.2 的判据"机器从来没有『知道自己该干活』的时刻"，
> 心跳正是把那个状态显式化。

### 6.2 建议的心跳形态（推断，基于上面的实测形态 + 项目既有台账要求）

| 场景 | 播报内容 | 落盘位置 | 频率 |
|---|---|---|---|
| 扫描波 | `W2 回收 9/14`（只报数字，不报内容） | `reports\dispatch_ledger.md` 追加一行 | 每路回收时 |

## 7. 预览编码：720p 够不够？有没有更快的可靠档？

### 7.1 项目已有的硬线（文档）

`skills\naraka-highlight-studio\references\complete-combat-roughcut.md`：

- L74 / L231：「分辨率分级沿用初筛 **320px** → 判定 **640px** → 定点 **960px**，报告写清结论用的是哪一级，稀疏图初筛结论不得直接定生死」
- L236-242：「**640px 联系表会系统性地把「战斗」误读成「面板」。** 864 重剪轮 **5 路扫描员各自独立踩到，没有任何一路是看了联系表就下对的**……**联系表只用于「定位」，不用于「定性」**」
- L172 / L208：「须在 **≥960px** 复核后才可定罪」「删除区内的疑似交战必须用 **≥960px** 高清 + 转写连续语音双重否定后才能删」

`.scratch\aivideo\07-frame-sampling.md §5.3` 补了量化依据：**960×540 是甜点**（在两档尺寸限制内都不被缩放，稳定 700 token/图）。

### 7.2 实测：从各档预览里抽帧，拿到什么

`fidelity.sh`，用项目标准取证命令 `ffmpeg -ss 100 -i <预览> -frames:v 1 out.png`：

| 预览档 | 预览分辨率 | **抽出的帧原生尺寸** | PNG 体积 | 加 `-vf scale=960:540` 后 |
|---|---|---|---|---|
| 720p60 | 1280×720 | **1280×720** | 673 KB | 960×540 |
| 540p60 | 960×540 | **960×540** | 441 KB | 960×540 |
| 480p60 | 854×480 | **854×480** | 361 KB | 960×540（放大） |
| 720p（x264 vf） | 1280×720 | **1280×720** | 652 KB | 960×540 |
| 4K 母版 | 3840×2160 | 3840×2160 | 3241 KB | 960×540 |

> **标注：实测。**
> **720p 预览抽出的帧是 1280×720 —— 在 960px 判定线之上，是有富余的。**
> **540p 预览抽出 960×540 —— 正好卡在判定线上，无富余。**
> **480p 预览抽出 854×480 —— 低于判定线 11%，而"放大到 960"不会凭空多出细节。**

### 7.3 视觉抽检：480p 到底能不能判"这是战斗"

选了源 893 s 的一帧——**远端敌人 + 紫色血条**，正是 864 把血条读成"强化面板"的那一类。

| 尺寸 | 判读结果 |
|---|---|
| **854×480** | 画面中央偏下能看见一条细横条，**紫色填充与白色剩余部分基本糊在一起**，无法确认那是敌人血条还是 UI 装饰；「被击飞」提示文字辨认不出 |
| **1280×720** | 紫色敌人血条与白色剩余段**清晰可分**，左侧「陀螺是小邪被击飞」一行文字可读，右上角「距离第3次喊话复活 00:56」可读 |

> **标注：实测（视觉判断，样本数 = 1 帧 × 2 尺寸）。**
> **样本量很小，只能作为方向性证据，不能当定量结论。** 但它与项目已有的 640px 5/5 误判记录方向一致。
>
> **结论**：
> - **720p 预览：够用，且有余量。** 抽帧原生 1280×720，比判定线高 33%。
> - **540p：临界可用**（原生 960×540 正好等于判定线），不建议作为默认。
> - **480p / 360p：不要用于定性。** 且 §2.3 已证明它们**只省 5% 时间**——省时间换不可靠判定，是负收益。
>
> **一句话**：**这一档不存在"更快的可靠档"。** 720p 已经是分辨率与可靠性的交叉点，
> 想更快只能往**拓扑**（分段 + 前缀 concat + 并行）走，不能往**像素**走。

### 7.4 渐进式交付的分辨率阶梯（建议，推断）

| 阶段 | 分辨率 | 帧率 | 码率 | 时长 | 依据 |
|---|---|---|---|---|---|
| **v0 「有声粗剪」**（可选，见 §8） | 720p | 60 | 8M | 全片 | 本次实测档 |
| **wip 预览**（扫描波期间） | 720p | 60 | 8M | 已决定段 | 本次实测档 |
| **正式审片预览** | 720p | 60 | 8M + 外挂 SRT | 全片 | 项目现行 |
| **4K 母版** | 2160p | 60 | 18M VBR | 全片 | `AGENTS.md §6` |

> 全部实测档位只有两档是必要的：**720p 与 4K**。中间档（540p/480p/360p）**实测不省时间且降低判定可靠性**，建议从 ladder 里删掉。

## 8. 「几秒出粗剪预览」到底能做到什么程度

### 8.1 实测：零 Agent 时间的静音粗剪

`zero_agent3.sh`：提 16 kHz 单声道音频 → `silencedetect=noise=-35dB:d=0.6` → 桥接 <3 s 的空隙 → 切口表 → 分段渲 720p → concat。

```
audio+silence+cutlist: 1008ms
  silences=48 keep=31 program=1186.7s / 1258.6s (94.3%)
render 31 segs (ok=31 bad=0): 148096ms -> 1192157KB
TOTAL zero-agent roughcut: 149115ms
```

> **标注：实测。**
> - **从源文件到可播放的 720p 文件：149 s（2.5 min）。**
> - 其中**分析只有 1.008 s**；148 s 全是编码 1186.7 s 节目（0.125 s/s，与 §2.1 的 0.122 吻合）。
> - **但这个"粗剪"只留下 94.3% 的源**——静音切对永劫无间这种全程有 BGM/环境音的战斗录像**基本无效**。
>
> **所以这一条的正确读法不是"可以 2.5 分钟出粗剪"，而是**：
> **"渲染侧从决定到出片只要 2.5 分钟，所以用户等的那 10 小时 100% 不是渲染造成的。"**
> 这与 `05-time-to-first-preview.md §1.2` 的账目一致（机器重活合计 13–36 min），
> 也与 §2.1 的比值一致（720p 是 4K 的 1/8.5）。

### 8.2 「不等所有素材准备好就开始渲」在本项目的真实形态

> **推断（基于 §4.1 + `05-time-to-first-preview.md` 的台账证据）**：本项目不存在"素材没准备好"这个问题——
> 源片从 T+0 就在盘上。**"准备好"指的是"剪辑决定做完了没有"。**
> 所以"不等素材就开始渲"在这里的正确翻译是 **"不等决定做完就开始渲已决定的那部分"**，
> 技术形态就是 §4.1 的前缀 concat，规则形态就是 §9 的 wip 例外。

### 8.3 三个时间点的重算（用项目真实时间戳）

口径：`05-time-to-first-preview.md` 记的 864-att2 时间线 + 本次实测的渲染速率。

| 任务 | 现「第一版可看」 | 改成前缀 concat 后 | 省 | 依据 |
|---|---|---|---|---|
| **864-att2** | 15:40:36（T0+2.94 h） | 首路 13:42:38 回 → 渲首段 ≈6 s → **13:42:44（T0+0.99 h）** | **≈ 1.95 h** | 实测首段 5.6 s |
| **861** | 04:10:06（T0+10.05 h） | 26/29 已回于 19:15:06 → **19:15:1x（T0+1.14 h）** | **≈ 8.9 h** | 同上 |
| 864-att2 的 4K | T0+10.63 h | 同上，**wip 预览与 4K 母版可并行起步**（4K 是 720p 的 8.5×，仍是分钟级） | — | 实测 §2.2 |

> **标注：实测速率 + 文档时间戳 = 推断出的收益。**
> 864 的收益（1.95 h）来自"末路比首路晚 108 min"这个尾巴；
> 861 的收益（8.9 h）来自"干等 7.83 h 之后 26/29 已足以拼一版"。
> **两个收益的机制不同，但都只需要同一处改动。**

## 9. 建议的改动（按杠杆排序）

### P0 · 给「渲染员只认冻结版」加一条 `wip-` 例外

规则出处（**三处独立禁止**，这是为什么它从未生效）：

| 出处 | 原文 |
|---|---|
| `roughcut-launch.md §2.3` 触发器六档末句 | 「字幕员、渲染员、自审员只认冻结版，不认 partial。」 |
| `roughcut-launch.md §2.8` 岛定义 | 「partial 命名 `merge_decision_vN-partial-r{k}`……**永不转正**……**字幕/渲染/自审禁认 partial**」 |
| `roughcut-launch.md §2.6` | 「草稿带 `-partial` 后缀，**不冻结、不送字幕渲染自审**。」 |

> `05-time-to-first-preview.md §3.2` 已判定：**这道隔离把逃生阀的药性废掉了**——它治的是"合成排队"，用户排在"渲染"上。
> 本文给出它缺的另一半数据：**渲染侧根本不是瓶颈（720p 只要 0.122 s/s，4K 只要 1.02 s/s），所以"渲 wip"没有任何性能代价。**

**改法（最小改动）**：

1. `§2.3` / `§2.8` / `§2.6` 三处各加一句例外：
   > 允许渲染员渲 `preview\<序号>-wip-vN.mp4`，文件名强制带 `wip-` 前缀，台账状态记 `PARTIAL-WIP`。
   > **`wip-` 文件永不进 QA 依据、永不送用户审片、永不作交付、可随时删。**

3. `deliverables-and-qa.md` 命名节写明 `wip-` 前缀文件"可随时删、不可引用"。

**配套（§4.1 已实测）**：渲染脚本渲一段就 concat 一次已完成前缀，写 `wip-<i>.mp4`。
本次实测 8 段共 8 个 wip，第一个在 **5.574 s** 落盘，concat 成本 131–582 ms。

**为什么这不违反质量守恒**：wip 是**只读旁路产物**，不进 `timeline/`、不进 `freeze_kit`、不作任何裁决依据。
`§2.8`「永不全回不冻结」的原意（**不能拿未闭合的东西当结论**）一字不动，改的只是"能不能看一眼"。

### P0 · `seg_render_master.sh` 加 resume（20 行，零依赖）

按 §5.2 的 `valid_seg` 三段校验 + 跳过实测 `reused=2 fresh=6`。
与 07 号报告 §6.1 的 A 项同一件事；本文补的是**它已经被独立实测跑通**，
不再依赖"860 那份在 `cache\` 里、已被 `cleanup_after_master.ps1` 删掉"的口头知识。

**顺带消灭 863 那次 11.7 min 白渲**（`.scratch\efficiency\07-delivery-wait.md §5.2`：`CONCAT_FAIL exit=127`，
concat demuxer 相对路径双重拼接）。带 resume 后，同类失败只需重跑 concat（实测 **0.75–0.9 s**）。

### P1 · 渲染日志接上 `-progress pipe:1`

按 §6.1 的形态：每秒一行 `seg 12/31 · 63% · 2.1× · ETA 00:48`。
**不问了，只告知**——这与用户的「不要问我」不冲突。
副产品：**自动填台账的"回收时间"列**，补上 `05` 报告 §3.3 指出的四局台账共同缺陷。

### P2 · 从 ladder 里删掉 540p / 480p / 360p

§7.3：480p 实测只省 5% 时间，且抽帧原生 854×480 低于 960px 判定线。

### P2 · 明确写"不做 HTTP/HLS 流式"

§4.3：本地单机交付没有网络环节，`-listen 1` 是实验特性。
**写下来是为了下次不用再讨论**，不是因为它不好。

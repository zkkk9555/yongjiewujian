# 看图预算 05：去掉限制的风险分析（反方）

> 分析员任务单第 5 份。01 查来源、02 查自动探测、03 查替代路径、04 查厂商限制。
> 本单站在**反方**：假设把「50 张」这条限制**完全删掉**，列出最坏会发生什么。
>
> **一句话结论：删掉「50」这个数不会出事，但删掉「先计数、后分轮、落盘结论」这套动作会出事。
> 而且本单挖到一件前四份都没发现的事——harness 自己就在做图片限流（2000px 缩图 + 5 MB/图 + 溢出自动压缩），
> 「厂商不管」这个前提本身是错的。**

## 1. 先把一件事钉死：前四份都漏了 harness 的图片配置

这是本单最重要的发现，也是所有风险判断的前提。

**02 号报告说「客户端零图片逻辑」——这句话是错的。** 它搜的是错误字符串，搜到了 0 命中就下了结论。
但 harness 有一整套**图片处理配置**，只是不在错误路径上，而在**正常路径**上。

207 MB 二进制里的原文（`ImageAttachmentConfig` schema）：

```js
eb = o({
  auto_resize:        B  // "Resize images before sending them to the model when they exceed configured limits (default: true)"
  max_width:          ht // "Maximum image width before resizing or rejecting the attachment (default: 2000)"
  max_height:         ht // "Maximum image height before resizing or rejecting the attachment (default: 2000)"
  max_base64_bytes:   ht // "Maximum base64 payload bytes for an image attachment (default: 5242880)"
})
// 暴露为 config.attachment.image.{auto_resize,max_width,max_height,max_base64_bytes}
// 描述原文: "Attachment processing configuration, including image size limits and resizing behavior"
```

配套的图片处理实现（同一二进制，`sharp` 风格）：`maxPixels` / `ERR_IMAGE_TOO_MANY_PIXELS` /
`autoOrient` / `Image: input exceeds maxPixels limit` / 格式白名单 JPEG·PNG·WebP·GIF·BMP·TIFF·HEIC·AVIF。

**这解释了 864 报告里那些没人解释过的尺寸。** 864 的 `adversarial_*` 大量抽帧后 `Read` 出来的图，
实际尺寸是 `2000x844`、`2000x1125`、`2000x1500`——**恰好顶在 `max_width=2000` 上**。
不是 Agent 主动选的分辨率，是 **harness 按 2000px 上限自动缩的**。

> **对风险分析的意义**：harness 已经在替我们省 token 了，而且是**静默地**省。
> 这意味着「厂商不管」不成立，但「厂商也不管张数」成立。**张数这一层仍然是空白。**

### 1.1 顺带修正 02 号的 token 模型

02 号实测出「上游有约 1568px 长边封顶」，据此得出「4K 静帧 ≈ 1844 tok」。

**我用 436 张真实图片的 token 增量回归，这个封顶不存在。** 实测（`w·h/750`，无封顶）：

| 实测尺寸 | 张数 | **实测 tok/图** | `w·h/750` | 02 号的 `1568 封顶`模型 | 谁对 |
|---|---|---|---|---|---|
| 960×540 | 166 | **718** | 691 | 691 | 都对 |
| **2000×844** | 92 | **2248** | **2251** | 1383 ❌ | **w·h/750 对** |
| **2000×1125** | 15 | **2978** | **3000** | 1844 ❌ | **w·h/750 对** |
| 1280×720 | 12 | **1348** | 1229 | 1229 | 都对 |

**2000×844 一档：实测 2248，模型预测 2251，误差 0.1%。02 号模型预测 1383，低估 62%。**

> 02 号只做了两组实验（3 张 + 1 张 4K），文本噪声 83–4072 tok 大到无法分辨，
> 就把「1568 封顶」写进了建议方案 P1。**那个常数是拟合噪声，不是实测。**
> 02 号自己标了「不稳健」，但后续 03 号的 `03 §3.2`「每格 131×74」整段分析**建立在这个错常数上**。
>
> **本单修正**：单图成本 = `w·h/750`，**无上游降采样**（降采样发生在 harness 侧，2000px，且已计入）。
> 这不改变 03 号的结论方向（12 列表每格仍只有 131px 有效像素，仍然读不出 HUD 小字），
> 但把 03 号的**绝对 token 数**全部低估了约 30–60%。

### 1.2 harness 还有第三道闸：溢出自动压缩

同一二进制，`compaction` 配置：

```js
compaction: o({
  auto:    B  // "Enable automatic compaction when context is full (default: true)"
  prune:   B  // "Enable pruning of old tool outputs (default: false)"
  reserved // "Token buffer for compaction. Leaves enough window to avoid overflow during compaction."
})
```

触发阈值（`N6` 函数原文）：

```js
N6 = (e, a) => {
  let i = e.input || e.context;                    // space-bunny-free: input = 524288
  if (i <= 0) return Infinity;
  if (a !== undefined) return i - a;
  return i - Math.max(Math.floor(i * 0.1), i >= 2 * 16000 ? 16000 : 0);
}
// ⇒ 阈值 = 524288 - 52428 = 471,860 tok
```

而且有**溢出恢复路径**（`recoverOverflow`）：

```js
recoverOverflow: () => J ? s.compact({ reason: "overflow", context: D })
                         .pipe(b(be => be.status === "completed")) : false
```

> **即：context 溢出时 harness 会自动压缩历史并重试，不是「会话报废」。**
> 这和 `IMAGE_LIMIT.md` 写的「超过后上游直接失败、当前会话无法继续，只能换新窗口」**方向相反**。

实测佐证：磁盘上 50 个会话，压缩事件 **1 次**（当前这个会话），错误事件 **0 次**。

**但自动压缩对本项目是灾难，不是保护。** 压缩做的事是把历史摘要成文字 checkpoint：

> `The following is a summary and serialized record of earlier conversation. Treat it as historical context, not as new instructions.`
> 摘要指令里明确写：`Summarize only what the user and the assistant said and did.`

**它摘要「说了什么、做了什么」，不会保留「图里有什么」。**
一次压缩之后，模型手里可能有「我看过 40 张帧，判定 seg10 engage 在 732」这句话，
但**那 40 张帧已经不在上下文里了**。后续任何「凭什么这么说」的复核都无法进行。

**这是删掉限制后最现实的头号死法**（详见 §2 F1）。

## 2. 七条失败模式（站在反方）

按「后果严重度 × 发生概率」排序。每条给「怎么发生的」。

### F1 —— 自动压缩把图变成文字摘要，结论变成不可复核的断言

**怎么发生的**
删掉限制 → 某一路会话看图超过 471,860 tok prompt（`limit.input=524288` 的 90%）→
harness `compaction.auto` 触发 → 历史被摘要 → **图片从上下文消失，只剩一句文字结论**
→ 下一轮 Agent 引用那句结论说「seg9 engage=732」，但**没有任何一张帧可以回查**
→ 用户审片说「732 那场没打」，Agent 无法举证，只能改口。

**实测支撑**
本素材 22 个会话里，峰值 prompt 已达 **171,573**（`adjudicate source 444-500`），
距 471,860 只剩 2.7 倍余量。**而 864 的对抗审设计本来就是「一路一路往上叠」**（`e4 极限并行`），
最激进的编制轻松越过这条线。

**后果严重度：最高。**
这是**唯一一条会摧毁可审计性**的失败模式。本项目的全部价值建立在
「每个秒点都有帧可回查」上（`AGENTS.md §8.1`：判断一个面板删不删，看它在不在这场战斗的因果链里）。
**压缩把「证据」变成「主张」，而本项目交付的正是证据。**

**注意**：这条**不是删限制造成的，是删限制后更容易造成的**——
因为没有分轮计数，Agent 不知道自己正在逼近压缩线。

---

### F2 —— `2000px` 静默缩图吃掉 HUD 小字，重演 864 的 5/5 误判

**怎么发生的**
删掉限制 → 「反正没有张数限制了，直接抽 4K 原帧看」→ Agent `Read` 3840×2160 静帧 →
harness `auto_resize` **静默**缩到 2000×1125 → **HUD 文字从 8px 缩到 5px** →
「攻击提升」横幅、紫色敌人血条、弹匣数字读不出来 → 读成「面板」→ 误删战斗段。

**实测支撑**
harness 默认 `max_width=2000`。864 的教训（`POOL.md L-044`）是
**640px 联系表会把战斗误读成面板，五路独立误判**。
2000px 比 640px 好，但**比源帧差**，而且差多少没人知道——
`auto_resize` 不通知任何人。

**这个失败模式的恶劣之处在于：它伪装成「看得更清楚」。**
Agent 会报告「我看了 4K 帧」，但它看的是 2000px。**报告与事实不符，且无法自查。**

**后果严重度：高。** 直接导致删错段 → 用户否决 → 重做。864 已因此被否六版。

**修法**：项目显式出图（`-vf scale=960:540`）而不是让 harness 缩，
并**在报告里记录实际送出的分辨率**。864 的 `scanner_brief_864.md` 已经这么做了（`scale=960:540`），
但对抗审各路没有统一要求，所以 2000px 的图才会大量出现。

---

### F3 —— 成本失控：没有张数上限 = 没有 token 预算 = 单路可烧掉整月额度的一半

**怎么发生的**
删掉限制 → 「token 不限」被理解成「图也不限」→
一路 Agent 抽 500 帧联系表一次性 `Read` → 500 × 691 = 345,500 tok 单次请求
→ 加上文本已用 100k，**直接越过 471,860 压缩线，触发 F1**。

**实测支撑（本素材真实账）**

| 口径 | 数字 |
|---|---|
| 22 个会话累计看图 | **436 张** |
| 图片 base64 载荷 | **502.7 MB** |
| 图片 token（一次性） | **707,052** |
| 输出 token | 480,900 |
| **图片占（图片+输出）** | **59.5%** |
| 图片占（全部 prompt，按轮重发） | **14.6%** |
| 单张成本区间 | 162 – 3,534 tok（**21.8 倍**） |
| 单张 base64 区间 | 6 KB – 3,524 KB |

**成本区间**：按 `w·h/750`，单张 960×540 = 691 tok，2000×1500 = 4,000 tok。
`limit.input = 524,288` → 单轮能塞 **758 张** 960×540，或 **131 张** 2000×1500。
**50 这个数在 token 口径下什么都不是。**

**后果严重度：中高（钱，不是质量）。**
网关按 token 计费（04 已证「Images are converted into tokens … billed as input tokens」），
**免费模型也有月度金额 + 5 小时窗口**。删掉限制 = 把「可观测的固定成本」换成「不可观测的浮动成本」。

---

### F4 —— 上下文被图片挤占，文本推理质量下降（长上下文里的位置衰减）

**怎么发生的**
删掉限制 → 单轮灌 100 张图 → 模型的注意力被 100 个视觉 token 块摊薄 →
**文字部分（时间线 JSON、秒点表、`AGENTS.md` 铁律）被挤到上下文边缘** →
模型开始漏读约束：忘了「面板候选必须 960px 复核」、忘了「删段审计员必派」。

**实测支撑**
本素材里 `adjudicate source 444-500` 一路：图片占该路 prompt 的 **51.9%**，
`seg10/seg11/seg8/adv3/adv2` 都在 **44%–50%**。
**换句话说：当前这套「已合规」的做法，图片已经吃掉近一半上下文了。**
删掉限制只会更糟。

**后果严重度：中高。**
表现是**静默的**：Agent 不会说「我忘了规则」，它会**正常地**给出一份漏了约束的结论。
这与 `AGENTS.md §8.1` 那句「门禁是必要条件，不是充分条件……864 的 v6 在这两条上干净，但用户审片后说它仍有问题」是同一类病。

---

### F5 —— 注意力稀释：一轮看太多张，单张判读质量下降（不是成本问题）

**怎么发生的**
删掉限制 → 一轮 `Read` 60 张联系表格子图 → 模型对每张的平均注意力低于逐张看
→ **「这一格是战斗还是面板」的判断出错**，且**错得更均匀、更不容易被自己发现**。

**实测支撑（这是反直觉的一条）**
01 号和 03 号都发现 640px 联系表在 864 上 5/5 误判。
但那次的混淆变量有两个：分辨率（131px/格）和**一次看 24 格**。
本单的实测显示：harness 把 2000×844 的联系表缩到 2000px 上限后，**每格仍是 2000/12=166px**——
**换更高分辨率的表并不能救回 12 列布局**，因为宽度是硬约束。

**更要紧的**：864 各路的报告自己写着「Budget: 28 used. +1 = 29. OK.」（02 号 §活体旁证）。
**Agent 在手写预算追踪。** 删掉限制 = 抽掉它唯一的自限机制，
而这个机制的实际作用不是防超限，是**强制它把注意力分配到「还剩几张」上**。

**后果严重度：中高。**
这一条最容易被忽略，因为它是**质量退化而非报错**。
一次 `Read` 60 张不会有任何错误，只会有更差的结论。

---

### F6 —— 误把联系表当原图，定性反转（864 已经踩过，被限制"意外"挡住）

**怎么发生的**
删掉限制 → 想省事 → 「一张 24 格表算 1 张，50 张预算够看 50 张表 = 1200 帧」
→ 全片都用表看 → 全片都是 131px/格 → **所有战斗判读都不可靠** → 时间线整体崩。

**实测支撑**
03 号 §3.2 算过：864 用的 12 列 × 24 格 = 7680×720，harness 缩到 2000×168 后**每格 166×14**。
（本单修正 03 号的 1568 假设后，实际比 03 号估的还糟一档。）

**但要注意一个反讽**：**现有 50 张限制可能正在**充当**这个错误的刹车。**
864 一路扫 85 秒只用 28 张，**说明它确实被迫在「多看几张」和「拼成表」之间做过选择**。
删掉限制后，Agent 会理性地选「拼成表」（因为张数不再贵）——
**也就是说，删掉限制可能会加剧它想解决的问题。**

**后果严重度：高，但已被 864 实证过（被否六版）。**

---

### F7 —— 拿掉预算当「不思考」的借口（软约束腐化）

**怎么发生的**
删掉限制 → 「看图不要钱」成为默认心态 → Agent 用「我再看看图」代替「我用数值信号交叉验证」
→ 864 的 `POOL.md L-013/L-014` 那类**零图片成本的硬判据**不再被开发
→ 时间线的依据从**可复现的算术**退化成**目视断言**。

**实测支撑（这是本单最想说的一条）**
864 最有决定力的证据是 `program_map_v3.json` 与 `merge_decision_v3 §1.3` 的**逐条算术对账**，
`selfaudit_864_v3 §8` 明确列「零图片成本的取证」。
**这些全是在「看图预算紧张」的压力下逼出来的。**

删掉限制 = 拿掉压力 = 拿掉这些成果的成因。
**这不是「更安全」，这是「回到更差的取证方法」。**

**后果严重度：中（但它决定了前六条的长期走向）。**

## 3. 硬上限 vs 软约束：现有 7 条规则逐条归类

先说结论：**这 7 条里，硬上限 0 条，软约束 7 条。**
「硬上限」的定义是：**上游会因此拒绝请求，且不可恢复**。

| # | 现有条文（`AGENTS.md §9` / `IMAGE_LIMIT.md`） | 归类 | 触发后果 | 删掉会怎样 |
|---|---|---|---|---|
| 1 | 「上游单次请求图片总数上限 50 张」 | **假硬上限**（软） | 无。当前 host 无此限制（04 已证），harness 无此逻辑（本单复核） | 无后果。**这个数在 token 口径下跨度 21.8 倍，数学上无意义** |
| 2 | 「累计口径：历史 + 本轮全部图片工具加总」 | **软**（但计错了轴） | 无。真实累计轴是 **prompt token**，不是张数 | 无直接后果，但**会让 Agent 算错账**（见 F3） |
| 3 | 「单轮新增 ≤10 张」 | **软**（唯一真正起作用的一条） | 无 | **有后果**。这是唯一在约束注意力分配的机制（F5） |
| 4 | 「超 10 帧优先拼联系表」 | **软**，且**已被 864 证伪一半** | 无 | **有后果**，且是**反向**的（见 F6） |
| 5 | 「逐帧时先抽稀（1/10fps），只对边界前后补帧」 | **软**，**正确且应保留** | 无 | 有后果（抽帧量爆炸，F3） |
| 6 | 「每轮看完先写核实结论再开下一轮」 | **软**，**这是全条里最重要的一条** | 无 | **有后果，且是最严重的**（F1 的唯一防线） |
| 7 | 「确实需要超过 50 张时拆成多个单轮」 | **软**（爆炸半径控制） | 无 | 有后果（单批越大，一次失败/一次压缩损失越多） |

### 3.1 关键修正：**规则保护的不是「不被拒」，是「不被压缩」**

现有规则全部写的是「超限会作废」（01 号已证：零实证）。但本单挖出的机制说明：

| 机制 | 是否存在 | 触发条件 | 后果 |
|---|---|---|---|
| 上游因**张数**拒请求 | **不存在** | — | — |
| harness 因**单图过大**拒 | **存在** | 单图 base64 > 5 MB（`max_base64_bytes`） | 单图失败，**可恢复** |
| harness 因 **context 溢出**拒 | **存在** | prompt > 471,860 tok | **自动压缩并重试**（`recoverOverflow`） |
| 压缩导致证据丢失 | **存在** | 每次压缩 | **不可恢复** ← 唯一真威胁 |

> **所以真正需要硬拦的只有一件事：在逼近 471,860 tok 之前主动分轮并落盘。**
> 「50 张」不在这件事上。「10 张/轮 + 每轮落盘」才在这件事上。

## 4. 分层方案（不一刀切）

### L-A 硬上限（真正的，保留）

| 项 | 值 | 来源 | 为什么是硬 |
|---|---|---|---|
| **单轮 prompt token** | `已用 + 本轮预估 ≤ 0.75 × limit.input` | `/api/model` 的 `limit.input` | 越线触发压缩 = 证据不可逆丢失（F1） |
| **单图 base64** | ≤ 4 MB（留 1 MB 余量） | harness `max_base64_bytes = 5 MB` | 越线单图被拒 |
| **单图分辨率** | 项目显式出 ≤ 960×540 或联系表，**不依赖 `auto_resize`** | harness `max_width = 2000`（静默） | 静默降采样 = 报告与事实不符（F2） |

**这三条都可以机器算**：`check_image_budget.ps1` 读图片头拿 `w×h`，算 `Σ w·h/750`，
再从 `/api/session/{id}/context` 取已用 token。三个数字全部现成，**不需要任何人公布上限**。

### L-B 软约束（引导，不拦）

| 项 | 建议 | 性质 |
|---|---|---|
| 单轮新增张数 | **≤10 张**（保留原值） | 注意力分配，不是防超限 |
| 超 10 帧 | 联系表，**但列数 ≤ 6**（03 号建议，本单支持） | 补 864 缺失的分辨率护栏 |
| 每轮落盘 | **强制**，且落盘内容必须含**秒点 + 帧文件名 + 每格有效像素** | 这是压缩的唯一防线 |
| 抽帧密度 | 保留 `1/10fps` 常规档 + 边界 ±2s 加密 | F3 |

### L-C 完全放开

| 场景 | 张数 | 理由 |
|---|---|---|
| **定点复核 5–10 张**（候选删除段、敌方名字、弹药读数、入片首帧） | **不限** | 这些是 03 号 L2 层，「定生死」必须看原图。任何限制都在伤害质量 |
| **门禁 FAIL 后的坐标复核** | **不限** | 2–3 张的事 |
| **用户点名的某一张帧** | **不限** | 人要看的东西不该被限制 |
| **合并/裁决阶段的定点回查** | **不限** | 同上 |

> **这正是用户直觉里对的部分：「定点复核 5–10 张」完全不该有限制。**
> 现有 7 条规则把它们和「批量抽帧 500 张」放在同一个计数口径里，这是设计缺陷，不是保守。

## 5. 「厂商应该能自己处理」在什么前提下成立

### 5.1 复核 02 号的判定

**02 号说：「不成立。模型看不到请求信封，harness 零图片逻辑。」**

**这个判定要拆成两半：**

| 层 | 02 号判定 | **本单复核** | 证据 |
|---|---|---|---|
| **模型层** | 不参与 | ✅ **同意** | 模型收到的是已装配好的 image parts 数组，架构上无法判断「这些太多了」。这条是硬的 |
| **harness 错误层** | 「零图片逻辑」 | ✅ **同意** | 207 MB 二进制：`too many image` / `max_images` / `image limit` / `image_count` **全部 0 命中**（本轮实测） |
| **harness 正常路径** | 未查 | ❌ **02 号漏了** | `attachment.image.{auto_resize, max_width, max_height, max_base64_bytes}` 全部存在且有默认值；`compaction.auto` 默认 true |

**修正后的结论**：

> **「厂商会自己管预算」在「管单图」这件事上成立，在「管总量」这件事上不成立。**
>
> - 成立的部分：harness 会把 4K 缩到 2000px、会拒 >5 MB 的单图、会在溢出时自动压缩。**这些都是厂商行为。**
> - 不成立的部分：**没有任何一层会数「这一轮带了几张图」，也没有任何一层会决定「该分轮了」。**

### 5.2 成立的前提

用户那句话要成立，需要同时满足：

| # | 前提 | 今天满足吗 |
|---|---|---|
| 1 | 厂商公布**单一可机器读取的上限**（不是 token、不是字节，是张数） | ❌ 网关未公布；`/api/model` 无 `attachment` 字段；models.dev 8393 模型 0 个图片字段（04 已证） |
| 2 | 超限时**返回可诊断的错误**，而不是静默压缩 | ❌ 溢出被 `recoverOverflow` 自动压缩**吞掉**，Agent 不知道自己丢了证据 |
| 3 | 压缩**保留原始证据**（至少保留帧引用） | ❌ 压缩只摘要「说了什么、做了什么」 |
| 4 | 客户端不需要自己算 | ❌ `limit.input` 可读，但「本轮该带多少张」必须自己算 |

**四条全不满足。所以这句话今天不成立——02 号的方向对，理由要换成上面这四条。**

### 5.3 用户该在哪一层管

| 层 | 能管什么 | 能不能管张数 | 判定 |
|---|---|---|---|
| **模型层** | 无。看不到请求信封 | ❌ | **管不了** |
| **harness 层** | 单图缩放、单图字节上限、自动压缩阈值——**都能配**（`config.attachment.*` / `config.compaction.*`） | ❌ **没有这个旋钮** | **能管一半** |
| **提示词层**（`AGENTS.md §9`、`IMAGE_LIMIT.md`） | 引导 Agent 自觉分轮 | ⚠️ 只能引导 | **必要但不充分** |
| **客户端脚本层**（`check_image_budget.ps1`） | **唯一能算 token 的地方**：`w·h/750` + `/api/session/{id}/context` 已用 token + `limit.input` | ✅ | **这就是该管的那一层** |

**给用户的答案**：

> **该在客户端脚本层管，而且这一层现在有确凿的可行性证据**——
> 本单已经把三个数字全部读出来了（`limit.input = 524288`、每张图的 `w·h`、
> 当前会话已用 token），全部来自本机 API，不需要厂商公布任何东西。
>
> 但**脚本必须先修三个已知 bug**（01 号已实测，本单确认）：
> `-Recurse` 缺失（子目录少算）、`-Cap` 可被调用者覆盖、超额只 `exit 0`。
> **修完之后把「50」换成 `Σw·h/750 ≤ 0.75 × limit.input − 已用`，这条规则就从迷信变成算术。**

**harness 层有一件事值得现在就做**：把 `config.compaction.reserved` 调大，
给压缩留更大的缓冲。默认阈值是 471,860（`524288 − 52428`），
意味着**离证据丢失只有 52,428 tok 的距离，也就是 76 张 960×540**。
调大 `reserved` 就是把这个悬崖往外推——**一个配置项，零代码**。

## 6. 结论

1. **「50 张」这个数删掉，没有任何失败模式会被触发。** 它保护的东西（不被拒）今天不存在：
   网关无此限制（04 已证）、harness 无此逻辑（本单实测 0 命中）、三个任务峰值 44 张从未逼近。

2. **真正该保留的是三条软约束**：单轮 ≤10 张、超 10 帧拼表且列数 ≤6、**每轮先落盘再开下一轮**。
   第三条最重要——它是自动压缩丢证据的唯一防线。

3. **最现实的头号风险不是「会话作废」，是 `AGENTS.md §9` 和 `IMAGE_LIMIT.md` 反复承诺的那个后果
   根本不会发生，而真正会发生的那个后果（471,860 tok 触发的静默压缩）没有任何一条现有条文在防。**

4. **成本区间**：19 分钟素材看图占 token 的 **15%（按轮重发）到 60%（一次性口径）**；
   单张成本跨度 **21.8 倍**（162–3,534 tok），单张载荷跨度 **587 倍**（6 KB–3.5 MB）。
   **「张数」这个单位描述不了这个成本函数——这是 50 这个数在数学上无意义的根本原因。**

5. **「厂商会自己管」今天不成立，但 02 号给的理由不完整。**
   正确说法：harness **已经在管单图**（2000px 缩图、5 MB 上限、自动压缩），
   **但没有任何一层在管总量**。而且自动压缩对证据型工作是**净损害**——
   它把帧换成文字 checkpoint，并且**不会告诉 Agent 它换了**。

6. **该在客户端脚本层管。这一层现在有确凿可行性证据**：三个数字全部现成可读，不需要厂商公布任何东西。

## 附：本单的方法与局限

**实测（全部本机，可复现）**
- 207 MB `opencode-cli.exe` 字符串统计（`too many image` / `max_images` / `imageCount` / `maxPixels` / `auto_resize` / `compaction` / `payload too large`）
- 反汇编出 `ImageAttachmentConfig` 与 `compaction` 的完整 schema 与默认值
- 反汇编出压缩阈值函数 `N6` 与 `recoverOverflow` 恢复路径，算出 471,860 tok 触发线
- 通过 `127.0.0.1:49374` 读取 864 任务全部 **22 个子会话、436 张图的原始 base64**，
  逐张解出真实像素尺寸，按轮统计 token 增量，反解出 `w·h/750`（实测吻合，误差 0.1%–4%）
- 修正 02 号的 1568px 封顶模型（该模型在 2000px 档低估 62%）
- 盘点磁盘上 50 个会话：压缩事件 1 次、错误事件 0 次

**局限（必须交代）**
1. **`w·h/750` 是回归出来的，不是厂商公布的。** 吻合度：960×540 误差 3.9%、2000×844 误差 0.1%、
   2000×1125 误差 0.8%。**小样本档位（n<10）噪声大，报告里已剔除。**
2. **`limit.input = 524288` 是声明值不是实测上限**（04 号已指出，本单沿用）。
   保守正确，但若厂商实际更宽松，本单所有 token 估计偏保守。
3. **未做「真的塞 60 张进去试试」的破坏性探测**（02 号也已拒绝，理由我同意：
   拿一个正在跑的会话去赌一个可能不存在的悬崖，期望收益为负）。
   **所以「删掉限制后会不会被拒」这一条，本单与 01/02/04 一样：零实证。**
   本单的贡献是**证明了它不需要被拒也会出事**（F1 压缩、F5 注意力）。
4. **`recoverOverflow` 的压缩是否真的会在本项目触发，未实测**（阈值 471,860 tok，
   本素材峰值 171,573，没到过）。这是**推断，依据是代码路径 + 阈值算术**，不是观测。
   **但也正因如此，它是当前唯一无人防守的失效路径——项目至今没有一次踩到它，
   所以没有一次经验告诉团队「它会来」。**

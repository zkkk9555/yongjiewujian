# 07 号 · 看图预算：三个可选方案 + 推荐

> 分析员第 7 份。前六份的结论本单**采信、不重查**：01（8 副本 2 漂移、脚本只打印不拦、50 是旧网关产物、864 峰值 44 张）、
> 02（硬失败非静默降级、本方网关无图片上限、「模型侧自己管」不成立）、03（三类零图判据都定不了「那是谁」、
> 看图可减到 1/5、弹匣曲线不是零图判据）、04（现用 `opencode-go/space-bunny-free`，三家数字无法核实不编）、
> 05（7 条规则硬上限 0 条、软约束 7 条；真威胁是 **471,860 tok 自动压缩把帧换成文字** 与 `auto_resize` 静默缩到 2000px；
> 该在客户端脚本层管，三个数字现成可读）、06（脚本 8 缺陷、`IMAGE_LIMIT.md` L7/L17 自相矛盾、L21 把数字焊死）。
>
> **本单新增的东西只有一类：方案可执行性的第一手验证**（见 §5）。这不是重查 01–06 的结论，是验证「B 到底能不能写出来」。

## 0. TL;DR

| 方案 | 一句话主张 | 门禁单位 | 换模型要重配吗 | 防住压缩丢证据吗 | 工作量 | 需要用户点头 |
|---|---|---|---|---|---|---|
| **A 彻底放开** | 「50」不保护任何东西，删数字、留方法 | 无（纯纪律） | **不用** | ❌ 无人防守 | 小（文档为主） | 是（改强制条文） |
| **B 换 token 硬约束** | 唯一不可逆的失效是静默压缩，所以门禁单位必须是 token 而不是张数 | **token（运行时读机读源）** | **不用，自动适配** | ✅ 唯一能防的 | 中（脚本要重写） | 是（含读本机凭据 + harness 配置） |
| **C 分级** | 按判读阶段给不同纪律：初筛放开、定性收敛严管、批量抽帧最严 | 分档 token/张数 | 不用（数与模型无关） | ⚠️ 靠档位自觉，仍可绕 | 大（三套阈值 + 三处文档同步） | 是 |

**推荐 B**（保留 A 的方法纪律作为软约束；C 作为 B 的后续增量）。
理由一句话：**压缩丢证据是唯一不可恢复的失效，只有按 token 算的门禁能防它，而 B 需要的数字本轮已实测可读、且换模型自动适配。**

**什么时候改选另一个**：
- 本机 API 读不到（harness 升级改了路由/端口/认证）→ **退回 A**，只保留「每轮落盘」这一条防线。
- 你不接受读本机凭据、或要在别的机器/别的 harness 上跑 → **退回 A**（B 会退化成需要手填配置的半成品）。
- 想要更细的粒度又不介意多一套配置 → 在 B 之上**加 C 的档位字段**（`config/image_budget.json` 里加 `tiers`，是 B 的子集，不是替代）。

## 1. 方案 A：彻底放开（把限制从「数量」改成「方法」）

### 1.1 核心主张

**「50 张」这条红线保护不了任何东西，删掉它、只留「先数后看 / 每轮落盘 / 拼表 / 抽稀」这套方法纪律。**
依据：05 已证 7 条规则**硬上限 0 条、软约束 7 条**；01 已证 5 个「作废会话」零原始证据、864 峰值仅 44 张从未逼近；
02/04 已证本方网关无图片上限。所以删数字的代价是零，收益是**停止一个假承诺**——
现在 8 份文档反复保证的「会话作废」不会发生，而不真正会发生的那个后果（静默压缩丢帧）无人防守。

### 1.2 具体改什么

### 1.3 对用户工作方式的影响

- 打开管理窗口看 **`IMAGE_LIMIT.md`**：标题仍是「看图纪律」，但**全文没有一个张数**；第一屏是三句「先数 / 落盘 / 拼表」。
- 说的话从「按 50 张来」变成三句：
  1. 「**按 `IMAGE_LIMIT.md` 走**」——日常不用记任何数字。
  2. 「**这一轮放开，定点复核别拦我**」——05 §4 L-C 已论证：定生死必须看原图，限它就是伤害质量。
  3. 「**把结论先落盘再开下一轮**」——这一句从建议升级为**唯一不可省的一条**。
- 出 4K 前的自检清单少一项（不用再对账张数），但**多一项**：报告里要记每轮落盘的秒点+帧文件名（压缩后的救命绳）。

| F5 注意力稀释 / F6 联系表当原图 | 中高 | 05 指出「单轮 ≤10」是**唯一真正起作用的软约束**；A 若把它也一并放松，F5/F6 全开。且 F6 有反讽：**现有限制正在当这个错误的刹车** |
| F7 拿掉预算当「不思考」的借口 | 中 | 864 最硬的证据（`program_map_v3.json` 逐条算术对账）正是预算压力逼出来的；放开 = 退回目视断言 |
| **换模型会不会重配** | ✅ **不会** | A 里根本没有需要重配的数字。这是 A 唯一的、也是实打实的优点 |
| 假承诺被删掉后没人接手 | 中 | 「50」虽然无功能，但它的**存在**让所有派工 prompt 都必须提一句看图纪律。全删后，纪律靠 `IMAGE_LIMIT.md` 一条指针存活，**漏派就彻底漏派**（861 已经出现过任务层自创 40 张这个数，01 D4） |

### 1.5 需要用户点头吗

**需要。** 它改的是 `AGENTS.md §9` 的强制条文（「硬红线」「违者会话作废」），属**规则语义变更**，
且会让 9 份历史报告里的「红线 50 张」自述与新规则不一致（不改报告，只改现行规则）。
但**不算扩大范围**：不新增依赖、不装东西、不碰源盘与任务目录。

## 2. 方案 B：换成真正的硬约束（按 token 预算管）

### 2.1 核心主张

**唯一不可恢复的失效是 harness 在压缩阈值处把帧换成文字摘要；所以门禁的单位必须是 token 而不是张数，
而 token 预算的三个数字全部现成可读、必须运行时读、不需要厂商公布。**
05 已把机制挖穿：`limit.input=524288` → 阈值 `524288 − 52428 = 471,860` → `compaction.auto` 静默触发 →
摘要指令只说「说了什么、做了什么」，**不保留「图里有什么」**。本项目交付的正是证据，所以这一条是头号威胁。

### 2.2 具体改什么

**新脚本 `scripts\check_view_budget.ps1`（或现有脚本 v3），四个输入全部机读：**

| 输入 | 来源（本单已实测，见 §5） | 备注 |
|---|---|---|
| `limit` | `GET /api/model` → 当前模型的 `limit.input`，**缺则退回 `limit.context`**，再缺则读 `config/image_budget.json` 手填值并打 WARN | 40 个模型里只有 6 个有 `limit.input`（192,000 → 922,000，**差 4.8 倍**），所以**必须运行时读**，不能硬编码 |
| `used` | `GET /api/session/{id}/message` → **最后一条 assistant 消息**的 `tokens.input + tokens.cache.read + tokens.cache.write` | ⚠️ **绝不能用 `/api/session` 的 `tokens.input`**——那是会话累计，实测最大 **6,289,132**（见 §5 陷阱 1） |
| `cost` | `Σ w·h/750`（PowerShell 5.1 `System.Drawing.Image::FromFile` 读宽高） | **不需要装包**：venv 里没有 PIL（03 已证），但 .NET 自带 |
| `moot` | `/api/model` → `capabilities.input` 是否含 `"image"` | 40 个模型里 **10 个是纯文本**（`hy4-preview` / `glm-5.3` / `deepseek-v4-flash` / `minimax-m2.7` …）→ 不含 image 就打 `[MOOT] 本模型不能看图，本门禁不适用` |

**判定**：`used + cost ≤ 0.75 × limit` → `[PASS]`；否则 `[FAIL]` + **exit 2**，输出三行可执行指令：
① 立刻把已得结论落盘（秒点 + 帧文件名）→ ② 开新会话/新窗口 → ③ 重跑本脚本（`used` 会重新变很小）。

**同时删掉的**：所有「50」；L21 焊死句；L7/L17 矛盾。
**同时保留的（软约束，与 A 相同）**：单轮新增 ≤10、超 10 帧拼表且**列数 ≤6**、抽稀 1/10fps、每轮先落盘、定点复核不限张数。

**一个零代码的可选加固**：`config.compaction.reserved` 调大 → 把 471,860 那道悬崖往外推
（默认只留 52,428 tok 余量 ≈ 76 张 960×540）。

### 2.3 对用户工作方式的影响

- 打开管理窗口看 **`IMAGE_LIMIT.md`**：数字区变成**一行公式**（`已用 + 本轮预估 ≤ 0.75 × 上限`，上限运行时读、当前模型是什么就显示什么）。
- 说的话：
  1. 「**看图前跑 `check_view_budget.ps1`**」——和现在的 `check_image_budget.ps1` 同一个位置、同一个手感，只是它会真的拦。
  2. 「**到线了就开新窗口，别硬扛**」——这是 B 唯一新增的用户动作，也是唯一需要人介入的时刻。
  3. 「**这路是定点复核，别拦**」——`-Tier spotcheck` 跳过 token 门禁（05 L-C：定生死必须看原图）。
- 多出来的一件事：报告里要记 `used/limit/cost` 三个数（`qa_gate.py` 可以消费 `-Json`，让看图预算**第一次成为可被门禁核对的项**）。

### 2.4 风险（尤其换模型）

| 风险 | 严重度 | 说明与缓解 |
|---|---|---|
| **耦合 harness 私有 API** | **最高** | `/api/*` 要 Basic auth（`opencode:<pw>`，pw 在 `~/.config/opencode/service.json`），端口**动态**（今天 49374），路由形状无版本承诺。harness 一升级就可能读不到 → **缓解：读不到时 fail-open（打 WARN 继续干活）而不是 fail-closed 卡死流程**，并在报告里写明「本轮门禁未生效」 |
| `0.75` 是拍的 | 中 | 471,860 = `input − 10%` 是 05 从代码路径算的，**但 compaction 到底用 `limit.input`(524,288) 还是 `limit.context`(1,048,576) 未实测**（本单发现两者差 2 倍，见 §5）→ **保守取 min**，阈值做成 config 项，可调 |
| `w·h/750` 是回归式不是官方式 | 中 | 05 已交代误差 0.1%–3.9%，够用；但联系表/缩图的**有效像素**问题（F6）它管不了 → 靠「列数 ≤6」软约束补 |
| 读凭据=碰本机密钥 | 中 | 只读 `service.json`、只连 `127.0.0.1`，不外发、不落盘密码。**但这是安全面的扩大，需要明确点头** |
| 换模型会不会重配 | ✅ **不用，且这是 B 最大的优点** | `limit` 运行时读，实测 6 个模型的 `limit.input` 从 192,000 到 922,000 差 4.8 倍——**任何写死的换算在数学上都不可能对**。换到纯文本模型则门禁自动打 `[MOOT]`，不需要人记得改规则 |
| 门禁被绕过 | 中 | 脚本管不了 harness 往请求里塞图（01 §2 已引 spec 自己承认 Out of Scope）。B 的防线是「**提前分轮 + 强制落盘**」，不是「拦截」 |

### 2.5 需要用户点头吗

**需要，且比 A 多一层。** 三件事各自需要点头：
1. 改 `AGENTS.md §9` 强制条文（与 A 相同）；
2. **新脚本读本机 `service.json` 凭据 + 连 127.0.0.1 私有 API**——这是安全面扩大；
3. 可选的 `compaction.reserved` 调大——**改 harness 配置**。
建议拆成两步落地：**第一步今天就能做（A 的文档部分 + 脚本 4 个致命缺陷），第二步再做 token 门禁**。
这样即使第 2 步被否，项目也已经脱离「假红线」，不再倒退。

## 3. 方案 C：分级（初筛放开 / 定性收敛严管 / 批量抽帧最严）

### 3.1 核心主张

**同一次任务里三种看图活动的风险完全不同，用一个数字管它们必然要么太松要么太紧；分三档，各档只管自己那一档。**
依据：05 §4 L-C 已论证「定点复核 5–10 张完全不该有限制」，而 03/05 又证明「批量抽帧」才是烧 token 和误判的来源
（12 列表每格 131px → 864 五路独立误判；弹匣曲线一轮烧掉 68% 预算）。

### 3.2 具体改什么

**新增 `config\image_budget.json`（三档表，数字只此一处）：**

| 档 | 适用 | 单轮新增 | 累计 | 特殊要求 |
|---|---|---|---|---|
| `census` 批量普查 | seg 扫描、全片清点 | ≤6 | 按 token 门禁（B） | 联系表**列数 ≤6**；每格有效像素 ≥ 160px，否则判读作废 |
| `adjudicate` 定性收敛 | 对抗审、裁决、合并 | ≤10 | 按 token 门禁（B） | **每轮强制落盘**（秒点 + 帧名 + 有效像素）；结论必须可回查 |
| `spotcheck` 定点复核 | 候选删除段、门禁 FAIL 复核、用户点名 | **不限** | 不限 | **必须看原图，禁止用联系表代替** |

- `scripts\check_image_budget.ps1` 加 `-Tier`，三档各有各的判定。
- `IMAGE_LIMIT.md` 从「7 步流程」改成「三档表 + 落盘铁律」，**档名（不是数字）**是各文档唯一需要复制的东西。
- 8 份副本里所有「单轮 ≤10 / 累计 ≤50」字样 → 换成档名；派工 prompt 必须写明本路档位（`roughcut-launch.md` L68/L90/L106/L159 四处）。
- 配套：`qa_gate.py` 增一条 gate，核对「每份 `adversarial_*` 报告声明的档位 == 实际单轮峰值张数」。

### 3.3 对用户工作方式的影响

- 打开管理窗口看 **`IMAGE_LIMIT.md`** 顶部一张三行表，第一眼就知道「现在这一路属于哪档」。
- 说的话：
  1. 「**这路是 seg 扫描，按 census 档**」——派工时一句。
  2. 「**这是裁决轮，最严**」——升级时的口头切换。
  3. 「**我要看那一张，别拦**」——spotcheck 档自动放行。
- 额外成本：多一次「这一路是哪档」的判断失误风险（判错档=用错纪律，且脚本**能校验**报告自述与实际是否一致，所以这一项可机器核对）。

### 3.4 风险（尤其换模型）

| 风险 | 严重度 | 说明 |
|---|---|---|
| **档位归属靠自觉，且这是第三个可绕过的软约束** | 高 | 现在已有「手填 `-AlreadySeen`」（06 S4）这一个绕过点；再加档位判断，等于**开三个后门**。缓解靠 `qa_gate.py` 事后核对，但那已经晚了 |
| **配置面变大 = 漂移源变多** | 高 | 06 已实证 8 份副本能漂出 2 处矛盾；C 要维护「3 档 × 8 份文档」的一致性，是 A/B 的 3 倍同步面 |
| 三档阈值都是拍的 | 中 | 6 / 10 / 不限——6 和 10 没有实测依据（05 只论证了「≤10 是唯一起作用的」，没论证 6 更优） |
| F1 压缩 | ⚠️ **仍未解决** | C 的 `census`/`adjudicate` 档若不叠 B 的 token 门禁，**压缩丢证据照样无人防守**——C 单独用不够 |
| **换模型会不会重配** | ✅ 不用 | 档位阈值与模型无关。但**若换到纯文本模型**（10/40），三档全部作废，需要靠 B 的 `[MOOT]` 检测提醒 |
| 与「用户日常只看一份入口」冲突 | 低 | `粗剪提示词.md` 需要塞进三档，等于给最常用的那份文档加负担 |

### 3.5 需要用户点头吗

**需要。** 新增 `config\image_budget.json` + 三档条文 + `qa_gate.py` 新 gate（后者会**改变现有门禁行为**，
可能让此前全绿的 864/863 类任务在新门禁下变红——这是对外可见的影响，必须先说清）。
**建议：作为 B 的第二阶段增量，而不是替代 B。**

## 4. 三个方案的共同前置（无论选哪个都必须先做）

## 6. 推荐：B（token 门禁），保留 A 的方法纪律

### 6.1 推荐理由（三条，按权重）

1. **它防的是唯一不可恢复的失效。** 05 已把机制挖穿：越 471,860 tok → 静默压缩 → 帧变文字 checkpoint →
   「凭什么这么说」再也回查不了。A 和 C（不叠 B）都**没有任何条文盯这条线**，而这恰恰是本项目交付的核心资产。
   反过来，删掉「50」本身零代价（硬上限 0 条、峰值 44 张、零原始证据）——**该换的是单位，不是要不要管。**
2. **它的数字全部现成可读，而且必须运行时读。** 本单实测：`limit` 在 `/api/model`，
   `used` 在每条 assistant 消息的 `tokens`，`cost` 是 `Σw·h/750`。**不需厂商公布任何东西**，
   而跨模型跨度 4.8 倍（192k → 922k）意味着**任何硬编码换算注定是错的**。
3. **它正面回答了「换模型后要不要重配」：不用。** 这是 A 的优点、B 也占（数字运行时读），
   而 C 的档位阈值虽然也与模型无关，但**多出「档位归属」这个新的可绕过点**。

### 6.2 落地顺序（把风险摊开，可中途叫停）

| 步 | 内容 | 产出 | 可否单独叫停 |
|---|---|---|---|
| 1 | §4 的四条共同前置 | 文档脱离假红线 + 脚本不再发假绿灯 | ✅ 这一步本身就值得做，与 B 无关 |
| 2 | B 的 token 门禁脚本 + `IMAGE_LIMIT.md` 改写 | 8 份副本收敛 + 真门禁 | ✅ 可停在「读不到就 warn」的弱版本 |
| 3 | 可选加固：`compaction.reserved` 调大 | 把悬崖往外推 | ✅ 零代码，随时可撤 |
| 4 | 可选增量：C 的三档 + `qa_gate.py` 新 gate | 粒度更细 | ✅ 纯增量 |

### 6.3 什么情况下改选另一个

| 触发条件 | 改选 | 理由 |
|---|---|---|
| 本机 `/api/*` 读不到（harness 升级改了路由/端口/认证），或你不愿意让脚本读 `service.json` | **A** | B 会退化成「需要手填配置」的半成品，那还不如老实承认没有门禁，只留「每轮落盘」这一条防线 |
| 你要在**另一台机器 / 另一个 harness / CI** 上跑这套 | **A** | B 明确耦合本地桌面应用的私有 API，不可移植 |
| 你不信任 `0.75` 这个经验系数 | **先跑 A 一轮**，记录峰值 `used/limit`，拿到实测分布再上 B | 一次任务的观测成本远低于拍脑袋系数 |
| 想要「初筛放开、定性严管」的粒度 | **B + C 的 tier 字段** | C 的三档放进 `config/image_budget.json` 的 `tiers`，是 B 的子集；`spotcheck` 档直接对应 05 L-C 的「定点复核不限张数」 |
| 换到了**纯文本模型**（40 个里 10 个，如 `glm-5.3`、`hy4-preview`） | **A 的简化版** | 没有图就没有看图预算；脚本会打 `[MOOT]`，此时应把精力转到 03 号的零图判据（数值/结构/文本型）上 |

### 6.4 一句话总结

> **把「50 张」换成「`已用 + 本轮预估 ≤ 0.75 × 运行时读到的上限`」，其余方法纪律（先数、落盘、拼表、抽稀、定点复核不限）一条不动。**
> 这一步让规则从迷信变成算术，而算术不需要厂商配合，也不会因为换模型而失效。

## 1. 我的划分规则（先说清为什么与 01 号有出入）

01 号的 7 条我都认，但**其中有几条的归属被他判错了**。我先把准入规则立起来，再逐条套：

> **允许进提示词的只有四类**：
> **(a)** 这个入口特有的**契约/申报义务**（「本轮即终态」「缺口必须点名」）；
> **(b)** 以**能力是否存在**为条件的**回退分支**（有子 Agent / 没有子 Agent；有 `taskstate.ps1` / 没有）；
> **(c)** 让 skill 里**已有规则变得可达**的**指针**（不给第二条真源）；
> **(d)** 因为 50 张门而必须写清的**禁令**。
>
> **禁止进提示词**：编排拓扑（谁排第几）、阈值（几轮、几路、几秒）、将来由脚本拥有的 schema。
> 这三类写进去就是设计原则 1 明令禁止的「第二份副本」。

按这条规则过一遍，01 号的 7 条里有 **1 条（G2）大半要退出去**，**2 条要改写**，**1 条要加**。

## 2. 那 7 条缺口（我的一行版）

1. **P1 派工形态声明 + 无派工能力的单路回退** —— 让 Agent 知道这套流程按多路并行设计，并预先声明回退，不猜、不问。
2. **P2 台账两形态契约** —— 有 `taskstate.ps1` 就以脚本为真源、没有才手填 11 列；写死「回收时间留空 = 未回」。
3. **P3 阻塞换路的收敛阶梯** —— 冻结原路 → 换号从断点续 → 到上限留保守边界继续；外部事故同样消耗一次尝试。**不写数字**。
4. **P4 本轮即终态 + 已知缺口必列** —— 交付判据从「完美」改成「能改的都改了，剩下的都点名」；给大白话模板，绕开黑话禁令。
5. **P5 续剪健康度体检** —— 三条 2 分钟读盘检查（已冻结无成片 / 回收时间空着过半 / 20 分钟无新文件），判「坏没坏」而不只是「做到哪」。
6. **P6 主 Agent 零图 + 回灌禁令 + 单路自看的可判定规格** —— 解 50 张门与「自己看片」的正面冲突（§5）。
7. **P7 缺料不停机的预授权** —— 找不到脚本/范例/标定资料时自己写一份继续跑，但必须声明「未校准」，不许当 QA 依据。

### P2 · 台账（两形态二选一）

**锚点**：插在 `═══ 任务目录（新剪和续剪共用这一段）═══` 一段的**末尾**，即 L123 之后、`═══ 不可违反 ═══`（L125）之前。
**理由**：台账文件落在任务目录里，跟着目录规则走最自然；且它和续剪分支是同一批「产物判进度」的逻辑。

```text
═══ 台账（判断"哪几路还没回来"的唯一凭据）═══

台账固定写在 <任务目录>\reports\dispatch_ledger.md，每路一行，表头就这 11 列，不许增删不许改名：

  路 | 区间(源秒) | 类型 | 状态 | 派工时间 | 心跳 | 回收时间 | 尝试 | 父路 | 报告路径 | 下一步

- **派工时间、心跳、回收时间必须填真实时刻**（如 2026-10-05T14:02:11+08:00）。
  不许填 T0，不许留空。回收时间 = 这一路的报告落盘**并被验完**的那一刻。
- **回收时间留空就等于这一路还没回来**，不许当"大概好了"处理。
- 只追加，不许改旧行；回来一路更新一次，顺手加一行时间戳附注。
  口头说"回来了"不算回，报告落盘 + 台账更新才算回。
- 如果盘上有 scripts\taskstate.ps1，就靠它维护台账、以它的输出为准：
  不要手填，不要另建第二份表。两份不一致时以脚本那份为准。
```

> **审计**：无打断。✅
> **与 02 的兼容写法说明**：这一段是**临时形态**。`taskstate.ps1` 上线后**整段删掉**，
> 不是改——因为脚本会自己生成投影，提示词再手抄一遍就变成第二份副本（原则 1）。
> **不许写「12 列」这个数字**：02 §6.2 的表头渲染出来是 **11 列**，而它自己的小标题写「12 列」。
> 提示词若跟着写「12」，就凭空造出第三个不一致源。上表只列名字，不列个数。
> `心跳 / 尝试 / 父路` 三列是 02 的增补；若 02 最终 schema 与此不同，以 02 为准并**整段删**。

## 4. 编排剧本该写在哪（问题 3 的回答）

### 4.1 判定

> **内容写进新文件 `skills\naraka-highlight-studio\references\one-shot-playbook.md`；
> 提示词里只放 4 行指针，不放任何一条步骤。**
>
> 但**建文件本身是零效力的**——必须同时改 `SKILL.md` 的路由表，否则没有任何 Agent 会读到它。

### 4.2 为什么不能塞进提示词

设计原则 1（L13–15）已经自己写明了：复述会产生第二份副本，两份不一致就是漂移的根源。
编排剧本恰恰是最容易漂移的东西——它是**步骤序列**，而步骤序列每隔几轮就会被局部改写一次。
放两份 = 迟早不一致，而且不一致的时候**没人知道该信哪份**。

### 4.3 为什么也不能塞进 `roughcut-launch.md`

因为它是**另一种文体**：

| 文件 | 体裁 | 装什么 |
|---|---|---|
| `roughcut-launch.md`（现 30.7 KB） | **规则集** | 谁干、切多细、几轮算超时、冻结怎么判 —— 全是「是什么」 |
| `one-shot-playbook.md`（新） | **步骤序列** | 先做什么、什么时候派什么、卡住了走哪条分支 —— 全是「先做这个再做那个」 |

规则变更和顺序变更的频率不一样。塞进同一个文件，改顺序时会顺手改规则，改规则时会顺手调顺序。
**分开的实际收益**：规则被 848/861/864 三局反复调过，顺序却稳定——它们本就该分开演进。

### 4.4 关键一步：**可发现性**（01 号和 02 号都没说，但它是成败点）

现在 `SKILL.md` L39–47 是一个**白名单**式路由表，开头写着：

> Read **only** the relevant supporting references:
> - … — Roughcut launch rules: `references/roughcut-launch.md`
> - …

`only` = 只有列出来的才读。**没列的文件等于不存在**，Agent 不会去 `dir` 一遍 references。
所以落地要**两处指针**：

**① `SKILL.md` L47 之后加一行**（唯一的真源指针）：

```markdown
- One-shot run script (order of operations, branching on blockers): [references/one-shot-playbook.md](references/one-shot-playbook.md)
```

**② `docs\粗剪提示词.md` L46–48 的第 3) 步加三行**（指针，不是一份拷贝）：

```text
3) 读 C:\Project\永劫无间\skills\naraka-highlight-studio\SKILL.md，
   启用 complete_combat_roughcut（完整战斗粗剪）模式，
   然后完全按该 skill 的 references 执行，不要凭印象另发明流程。
   其中 references\one-shot-playbook.md 是**执行顺序剧本**（先做什么、什么时候派什么、
   卡住了走哪条分支）；roughcut-launch.md 是规则与阈值本身。
   剧本里只有顺序，数字一律回 roughcut-launch 查，不要在剧本里自己另定一个。
```

> 这 4 行**不含任何一条步骤**，只声明两份文件的分工。它不是副本，是索引。

### 4.5 剧本里允许写什么 / 不允许写什么（可验证的验收标准）

| | 内容 |
|---|---|
| **允许** | 阶段顺序（PREFLIGHT → PROBE → TRANSCRIBE → PROXY → SCENE → FRAMES → DISPATCH → SCAN → MERGE_PARTIAL → RENDER_PREVIEW → SELF_AUDIT → ADVERSARIAL → ACCEPT → FREEZE_GATE → REWORK ⟲ → DELIVER_MASTER → CLEANUP → DONE）；每阶段的**进入条件**和**卡住时的下一跳**；每跳指向 `roughcut-launch §X` |
| **禁止** | 任何数字（80–90 秒、3 轮、≤10 张、24 路…）——**一个都不许出现** |
| **禁止** | 台账列名、角色名、状态词表——都是 `roughcut-launch` 的 |

**验收方法（一条命令）**：剧本里如果出现任何阿拉伯数字阈值，就是违规。

```powershell
Select-String -Path 'skills\naraka-highlight-studio\references\one-shot-playbook.md' `
              -Pattern '\d+\s*(秒|轮|路|张|分钟|路)'
# 期望：零命中（阶段名 PREFLIGHT/RENDER_PREVIEW 之类不含数字，不受影响）
```

**附一条免费漂移探测器**：让剧本的阶段表成为「阶段名的唯一散文出处」，然后让 `taskstate.ps1`
的 18 值闭集与它对照。以后有人往枚举里加阶段而不改剧本，这个 grep 就会不一致——
**两份文件唯一共享的 token 是一个封闭枚举，它不会静默漂移。**

## 5. 核实 50 张门与「自己看片」的冲突（问题 5 的回答）

### 5.1 核实结论：**冲突真实，且比 01 号说的更硬**

01 号的表述是「与提示词 L163 对撞」，语气像是**预算压力**。实测是**两份文件直接互相否定**：

| 出处 | 原文 | 指向 |
|---|---|---|
| `粗剪提示词.md` L163 | 「门禁通过后**还要自己看一遍成片**」 | 主 Agent **要**看图 |
| `粗剪提示词.md` L128 | 「单次请求累计不超过 50 张（含历史已看），单轮新增不超过 10 张」 | 主 Agent **没几张** |
| `roughcut-launch §2.1` 指挥行 | 「**禁止 `Read` 任何图片/缩略图/联系表**」 | 主 Agent **不许**看图 |
| `roughcut-launch §2.1` L50 | 「**主Agent不看图做审片（省预算）**……定点裁决由主Agent下发」 | 同上，两处独立重申 |
| `roughcut-launch §3.3` | 验收角色「本路 **0 图**可完工」 | 数字验收不需要看图 |
| `roughcut-launch §3.6` | 预览对抗审逐路看片，**每路独立图片预算**，报告是文字 | 看片**在子 Agent 里** |

**关键点：规则是对的，是提示词这一句把它推翻了。**
skill 的设计本来就是「主 Agent 不看图，看片全在子 Agent，主 Agent 读书面报告」。
864att2 的真实做法正是这样：13 份审件全在子 Agent，主 Agent 零图。
**提示词 L163 让 Agent 以为「看片」是它自己的活**，于是它去 `Read` 帧——直接踩 50 张红线，
而这个红线的失败模式不是报错，是**整个会话作废**（AGENTS §9：已有两个会话因此报废）。

### 5.2 提示词侧的处理（只改提示词，不动预算机制）

三条，全部含在 §3 的 P6 里：

1. **把义务从「自己看」改成「有人看」** —— 义务保留（这是 §3.7 G2/G4 的真实要求，删不得），
   但执行者默认是派出去的那一路。这消掉了与 skill 的矛盾。
2. **回灌禁令** —— 这是 01 §4.2 点出的真实漏洞：**L128 写了 50 张，但没写「回灌上限」**。
   子 Agent 各有独立窗口（每路 ≤10 张安全），**只要有一路把图回灌进主会话就爆**。
   实测 6 号那局 8 路编制 = 84–90 张/轮。禁令要写死：**回灌只能是文字 + 绝对路径**。
3. **无派工能力时的回退规格** —— 不留空。给出可判定的做法（节目轴 30 秒/张联系表）、
   可算的边界（25 分钟节目时长以内够用）、以及冲突时的优先级
   （**额度优先于看完**，缺口写进交付报告）。

### 5.3 明确不动的东西

| 不动 | 为什么 |
|---|---|
| `check_image_budget.ps1` | 参数（`-ImageDir` / `-AlreadySeen` / `-Cap 50` / `-PerRoundNew 10`）已核实可用，无缺陷 |
| AGENTS §9 的 50 / 10 口径 | 那是上游硬上限，任何本地改动无效 |
| `make_contact_sheet.ps1` | 一表计 1 图的机制就是为这条红线造的（其头部注释明写它是「sanctioned way to stay inside the 50-image-per-request red line」） |
| 任何「放宽预算」的提议 | 上游不接受放宽，只有拆轮与拼表两条路 |

> 顺带一条操作细节：P6 里写的 `-ImageDir` 传的是**该段联系表目录**。
> `make_contact_sheet.ps1` 是按 `-Pattern` 对**一个目录**取前 `MaxPerSheet` 张（已读源码），

> `shots/segN/contact_*.jpg` 已经是这个结构，不需要新约定。

## 6. 硬约束逐条检查：7 条里几条违反「不打断用户」

> 用户原话：「中间出几版、推几轮我不在乎，**不要问我，不要分段汇报，最后一次性给结论**。」

**结论：0 条违反。**（不是「我改过所以不违反」，是逐条比对后的判定）

| # | 新增文本里的中断风险点 | 判定 |
|---|---|---|
| P1 | 「按哪种形态跑」天然像是要问的 | 末行明写「**不许中途停下来问我选哪种**」→ 反向封死 |
| P2 | 台账没填会被理解成要汇报 | 无任何询问语气；缺口由「回收时间留空 = 未回」消化 |
| P3 | 「卡住」最容易被写成「那我问你」 | 末句明写「**卡住不等于可以问我**」→ 反向封死 |
| P4 | 缺口清单最容易被写成中途请示 | 明确挂在**最后一次**报告的第 7 条，且明写「不是草稿」 |
| P5 | 体检命中「已冻结但无成片」最容易被写成「要不要出 4K？」 | 改成在报告里写明「这一版不是冻结依据」，不问。**（草稿此处原本写了「明确告诉我」，已自查删除）** |
| P6 | 「没人看片」可能被理解成请用户看 | 义务落给派工路 / 联系表回退，不指向用户 |
| P7 | 「缺料」最容易被写成「缺 X，要我怎么办」 | 标题即禁令：「**缺东西不许卡住，也不许问我**」 |

**两条反向观察（比 0 条违反更重要）**：

1. **01 号原版 G2 若照写，会违反 1 次。**「`streak≥1` 即可送审」在一句话模式里等于
   把「送审」提前到中途——那是一次用户介入。所以我把它退回 skill 侧（P4 只保留申报义务）。
2. **P7 消除的是一次真实的、高频的打断。** 01 §2.2 亲口说了：
   「**Agent 不会说『我缺脚本』，它会重写一个**」。没这条，它重写；有了这条，它重写但必须申报。
   这正是用户「不要问我」在能力缺失场景下的真正落点。

## 8. 诚实边界

1. **这 7 条不解决任何一处干等。** P3 只是**策略句**——「不许原地等」在主 Agent 身上没有执行点，
   因为它下一次工具调用发生在用户下次发言时（02 §5.2 论证）。真解是 `taskstate.ps1 watchdog`。
   P3 的实际价值是：机制上线后，Agent 不会因为「提示词说要一路跑到交付」而替脚本的判定找借口。
2. **P2 是临时条文，会过期。** `taskstate.ps1` 上线当天就该删掉整段。
3. **P6 的 25 分钟边界是算出来的，不是测出来的**（50 × 30 秒）。
   若改用 60 秒/张，上限变 50 分钟，但漏检率上升——这个折中项目里没有数据，本轮不替它定。
4. **我改写了 01 号的 G1 和 G3。** G1 的改法保住了设计原则 2（不出现接口名），
   代价是「有派工能力」这句话依赖 Agent 自我判断——但这是**能力探测**，
   不比对具体接口名更脆弱。
5. **§1.2 那个「3 轮 vs attempt 2」的矛盾不归我这 7 条**，它属于 skill 侧。
   我不在提示词里写数字来「顺手解决」，那正是产生第三个数字的最短路径。

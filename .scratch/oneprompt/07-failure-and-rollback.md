## 0. 一页结论

| 项 | 判定 |
|---|---|
| 新失效模式 | **21 条**，分五组（无人发现 / 状态漂移 / 门禁误报 / 收编不泛用 / wip 泄漏） |
| 最危险的一条 | **FM-02「自洽的谎言」**——自动化必然顺手把缺口登记成删除段并重算 program map，19 扇门全绿。04 号已实测 |
| 最阴的一条 | **FM-05「已知缺口」写成空话**——它是用户不在场时**唯一**的信息通道，而它是自由文本，且机检为零 |
| 谁发现 | **一个独立于指挥 Agent 的审计脚本**（`taskstate.ps1 audit`，零图、只读、**Agent 不可否决**）。7 项 CHECK → 三态出口：`DELIVERABLE` / `DEGRADED` / `WITHHELD` |
| 一句话机制 | **「不可信就别交」= 交付前审计不过，就不许把预览当正常成片交出去；且不许靠"补几条声明"骗过它。** |
| 回退判据 | **质量优先于时间**：交付被否决 → 立即降级该门为 WARN 并重设计（不是加更多门）；连续 2 局更慢 → 撤该批 |
| 回退顺序 | **倒序撤，先撤会产生错交付的（wip → 新门 → 状态机强制），最后撤只是慢的（脚本收编）** |
| 分批 | **6 批**。104 字段必须拆：**批 5a 先上 12 个字段**，其余 92 个"有触发器才加" |
| 「一版过」与本次机制的关系 | 本次机制**不承诺一版过**，只承诺"**可解释地交一版，或明确地不交**"。前者是 864att2 的运气，后者是这次要造的东西 |
| 对「等焦虑」的回答 | **给台账算出来的 ETA，不给早半成品。** 心跳必须是「通知」不是「汇报」（四条判据见 §6.3），且**它与 watchdog 是同一件事**——这是 watchdog 上线最强的论证，比省 6.5 h 更强 |

> **总判定**：这套改造的方向是对的，但它的**真实交付物不是那个 mp4，是那一行「能不能看、打折在哪」的结论**。
> 现在那一行是自由散文（05 号 P4 给了两句话的模板，仅此而已），改造若不把它机器化，
> 整套东西就只是把 861 的失败从"干等 7.8 h"换成"安静地交一版错的"——**后者更坏，因为用户看不见过程**。

## 1. 前置：这套改造把「谁在环」换掉了，风险结构随之换掉

改造前：用户是环节的一部分。861 干等 7.83 h 时用户**看得见**（他知道在跑、知道卡了、能叫停）。
864-att1 走 v1–v6 被整局否决时用户**看得见**（他在审片）。

改造后：用户不在环内，只拿最后一句结论。**风险从「看得见的慢」搬到「看不见的错」。**

这不是"风险变大"，是**风险换了币种**。因此下面三条判断标准贯穿全篇：

| 判断标准 | 来源 |
|---|---|
| ① 一个环节做错时，**有没有一个独立于做活者的人/脚本会发现** | 01 §5.4 缺口 8；`AGENTS.md §8.1`「门禁全绿之后仍然必须看片」 |
| ② 机制做错时，**门禁是变严还是变松** | 04 §4 铁律：「FAIL 的唯一合法理由是『该有的纸没落盘』，绝不是『机器认为这里有战斗』」 |
| ③ **恢复动作是"删文件/关开关"还是"改散文"** | 用户原话「别改了又改错了」；05 §7 五条 grep 全是可回退测试 |

## 2. 失败模式清单（21 条）

标 **[机]** = 机器可判（零图、只读、盘上可算）；标 **[点]** = 需要一次用户点头；标 **[人]** = 必须有人写下判断，不可自动化。

#### **FM-01 · P7「缺料不停机」把已知失败行为从「意外」升格为「授权」** ｜ [机]

- **形态**：05 号 P7 原文「脚本找不到…自己写一份，继续把这一版跑完，并在已知缺口里写明未校准」。
  问题在于 P7 的补救是**散文义务**（写一句话），**没有机器执行点**。
  于是一条 01 号明说过的失败行为（「Agent 不会说我缺脚本，它会重写一个」）**获得了明文授权**，
  且默认不会触发任何红灯。
- **为什么现有机制拦不住**：`qa_gate.py` / `validate_combat_timeline.py` 只校验**时间线内部自洽**。
  一份由临时脚本写出的时间线可以完全自洽。P7 的"不许拿它当 QA 依据"是一句无人执行的话。
- **后果**：帧轴标定（08 号已证伪的 +28/+29 帧）、`build_program` 的三路求和口径，全部可能被临时实现悄悄替掉，
  **而且门禁全绿**。
- **防呆**：**P7 产物必须在盘上带机器可读的标记，且审计脚本读它。**
  ```
  scripts\write_text.py 产出的每个文件   → 顶层写 "provenance": {"producer": "...", "uncalibrated": true, "reason": "..."}
  capture_frames.py --mode point/strip   → frame_axis.json 的 verdict 字段
  任何 uncalibrated:true 的产物被 program_map.json / cut_list.json / captions\*.srt 引用
      → trust_audit C5 = RED → 直接 WITHHELD（不是 DEGRADED）
  ```
  **判据一句话**：`uncalibrated` 的东西不许流进"判定对错"的那三样（时间线 / program map / 字幕），
  也不许流进预览的时长校验。宁可交一版明显的短的。

#### **FM-02 · 「自洽的谎言」骗过全部 19 扇门** ｜ [人] ← **本轮最危险的一条**

- **形态**（04 号已实测，五个变体）：删掉一场 24.73 s 真战斗 + **把它登记进 `deleted_intervals`** +
  **顺手重算 `program_map.program_seconds_total`** → `qa_gate.py` `pass:true, fail:0, exit 0`。
- **为什么这不是假设**：**任何真实自动化都会顺手做这两步。** 删除一段之后不登记，程序下一秒就崩；
  登记之后不重算，`program_sum` 这道唯一的时长交叉校验立刻 FAIL。**自动化是被现有门禁逼着走这条路���**
- **G-C2 是防线，但它有一个致命缺口**：G-C2 要求"命中战斗词 → 必须有署名裁决记录"。
  缺口是——**自动化可以自己写那份记录，并署自己的名。** 04 号 §6-4 写了
  「签名要求无法被自动化满足（它必须是一个人写下的判断）」，**这个论断在机制层面不成立**：
  签名是一种格式要求，不是一种身份要求。
- **防呆（三层，缺一不可）**：
  1. **[机] 签名记录必须引用真实存在的帧**：`reports\deleted_audit_v<N>.md` 的每行必须有 `evidence` 路径，
     该路径必须落在 `shots\` 或 `wip\` 下、`Test-Path` 为真、`mtime > deleted_interval 落盘时刻`。
     造一张表过不了；真要造假必须先去抽真帧。
  2. **[机] 署名者字段禁止取自动化标识**：`裁决人` 若匹配 `/^(taskstate|agent|auto|qa_gate|python|powershell)/i`
     或是本轮 Agent 自引用 → 记录判无效 → FAIL。这不检查人是不是真的，只是把"随手编"这一步变成要多写一个假名。
  3. **[机] 签名速率上限**：`--automation-mode` 下，单局由自动化补的签名记录 **> 12 条即 RED**。
     864 有 6 条删除段、861 有 423 条但历史 344 条无证据（只 WARN）——
     **这个数字必须按素材实测标定，本轮只给方向不给结论。**
- **收口**：这三层都只是"提高造假的成本"。**FM-02 的真正兜底仍然是 `WITHHELD` + 用户看片**，
  这一点必须写在条文里而不是藏起来。

#### **FM-04 · G2 默认档 `streak≥1` 恰好放过"第一次出现的系统性错误"** ｜ [机] ← **本报告增量**

- **形态**：05 号 §1.1 把 G2（`streak≥1` 即可送审）**整段退回 skill 侧**，理由是"送审=用户介入"。
  但 G2 的实体作用是**降低送审强度**；05 号退回后，01 号 G2 的实体收益也一并没了。
  若将来在 skill 侧把它设成默认档，会出现一个精确的反直觉后果：
  **系统性错误（第一次出现、因此每一路都犯同样的错）只产生 1 条 streak，而阈值恰好是 1。**
  偶然性错误才会产生多条 streak。所以默认值恰好把最该抓的那一类放过。
- **防呆**：**streak 阈值降到 1 的同时必须锁轮次**——「`streak ≥ 1` 且 `ADVERSARIAL` 轮次 ≥ 3`」。
  更保守的形态（**推荐**）：**冻结门阈值不动（仍要 streak≥2），只在"降级交付"这一档允许 streak≥1**。
  这样"降级交一版"有出口，"冻结"不放松——两者本来就是两个动作，05 号把它们合成一个了。
- **归属**：这条属于 skill 侧（`roughcut-launch.md §3.7`），**不写进提示词**（05 §1.1 的归属裁决成立）。

#### **FM-05 · 「已知缺口」被写成空话，而它是用户不在场的唯一信息通道** ｜ [机] ← **本轮最阴的一条**

- **形态**：05 号 P4 要求交付报告第 7 条列已知缺口，并给了两句大白话模板。**机检为零。**
  自动化的最优策略是写「无」，或写「部分片段边界按保守处理」这类零信息句。
  用户不在场、看不到过程、只拿最终结论 —— **他判断这版能不能看的唯一材料，就是这一段。**
  而这一段现在是自由散文。
- **为什么现有机制拦不住**：`qa_gate.py` 19 扇门**没有一扇读交付报告**。
  更根本的原因：**门禁是机器，而这一段写给人。两者之间现在没有任何一致性检查。**
- **防呆（双向对齐，两条都可机判）**：
  ```
  方向 A（防漏写）：每一个 seam[id] 必须在「已知缺口」节里被点名。
                   → qa_gate 新增 gate_seams_named_in_delivery_report()
  方向 B（防空话）：「已知缺口」节里的每一条必须绑定一个可机检锚点
                   （源秒区间 / 场次 id / 路 id 之一），且该锚点必须真实存在于
                   timeline 的 seams[] 或 deleted_intervals[] 里。
                   → 解析不了锚点的句子判为无效条目。
  方向 C（自相矛盾检测）：缺口节写"无"，而 JSON 里 count(seams) + count(deleted_intervals 未裁决) > 0
                   → 直接 RED。这是 hostile_del 的散文版形态。
  ```
- **收口**：**交付报告的缺口节不是自由散文，是一个由机器从 JSON 生成、Agent 只能补充解释不能删条目的表。**
  用户看到的那一句「能不能看 + 打折在哪」，第一版应该是 `trust_audit.md` 生成的，不是 Agent 写的。

#### **FM-09 · 104 个具名字段本身就是漂移源** ｜ [机]

- **证据（已实测，不是推演）**：02 §6.2 的表头渲染出来是 **11 列**，而它自己的小标题写「12 列」；
  05 号 §1.2 又抓到「`§2.5` 默认 3 轮」vs「02 的 `attempt ≤ 2`」两个**互相矛盾的重试数字**，
  并且 02 号的 schema 与 05 号 P2 的 11 列表头是**各自独立写的**。
  **四份文件（脚本 / 投影 / 提示词 / 看门狗）各有一份字段清单，而它们已经不一致了。**
- **为什么危险**：漂移的两个方向后果不同——
  **多一个字段** → Agent 填错，无人发现；**少一个字段** → 触发器算不出来，
  861 那种"台账 300 KB 但没有回收时间列"的状态会**重新长出来，而这次是脚本生成的，看起来很权威。**
- **防呆（三条纪律 + 一个工具）**：
  1. **单源**：`config\taskstate_schema.json` 是唯一字段清单；投影列名、`verify` 检查、台账模板**全部从它生成**，
     任何地方不得手写列名。
  2. **禁止为"将来可能用"加字段**：新增字段必须能指名**哪个触发器或哪条 `verify` 检查在读它**，
     指不出名 → 不许加。**这一条直接把 104 砍到 12~20。**
  3. **`verify` 判投影列名 ≠ schema 列名 → exit 2**（不是 WARN）。
  4. `schema_version` 只增不减；每次增版写一条迁移说明，**旧任务目录允许缺新字段（缺 = 未知 = 不得当已知用）**。

#### **FM-10 · 状态比盘上事实"更乐观"，续跑时跳步** ｜ [机]

- **形态**：`phases_done` 里写着 `ACCEPT`，但 ACCEPT 从未跑完（会话死在 ACCEPT 的第一步）。

- **防呆**：**每个 phase 声明它的产出物路径**（`phase_exits[]`）。`verify` 的对账规则：
  ```
  phase ∈ phases_done  但  声明产出物不存在  →  该 phase 判未完成，从它回退
  任何对不上的地方一律往「更不可信」方向落：状态只许降级，不许升级
  ```
  **「只许降级，不许升级」是这一整组的核心原则**——它让状态机的错误方向永远是保守的。

## 3. 核心问题：链条跑完但结果可疑时，谁来发现？

### 3.1 先把"可疑"分型——四类，发现者不同

| 类 | 性质 | 现有门禁能抓吗 | 谁发现 |
|---|---|---|---|
| **T1 事实层错误** | 时间线不自洽、时长对不上、字幕正文=序号、文件损坏 | 能（19 扇门里 10 扇） | `qa_gate.py`（已有） |
| **T2 纸面缺失层错误** | 漏登记的缺口、没签名的删除段、没人看的片子、没校准的脚本 | **不能——现有门一扇都不读** | **本节新增的审计** |
| **T3 语义层错误** | 边界切错、战斗漏判、两场该分被合成一场、场尾未走完 | **不能**（04 §2 已列 7 种形态；`no_holes_in_battle` 对"缺席"结构性失明） | 只有看片。**机器永远抓不到。** |

> 而不是"**交的一定对**"。**这两句话的差别就是用户会不会白花一次审片时间。**
> 这一点必须写进最终交付的那一行（`FM-05` 方向 C），否则机制本身会变成新的过度自信来源。

### 3.3 四个必须解决的设计冲突

#### ① 「不可信就别交」与「不要问我」直接冲突

用户原话：「不要问我，不要分段汇报，最后一次性给结论」。
`WITHHELD` 字面上是"不交"——那 Agent 在干什么？在等吗？**861 就是这么死的。**

**处置：`WITHHELD` 不是"停下"，是"降级交付 + 强制点名"。**

```
WITHHELD 落盘 → 流程【继续跑】（watchdog 不停、换路不停）
              → 到达 T_witHold（建议 90 min；与 watchdog 的 deadline 上界对齐）仍未转绿
              → 【强制】降为 DEGRADED 交付，并在报告写明「因超时降级」
```

即：**永远不存在"停在不交"这个终态。** 最坏结果是交一版明确打折的，
而不是交一版看起来正常的，更不是卡住不动。
**这一条同时保住了两条用户约束：既不交不可信的，也不问他。**

#### ② 审计由谁跑？——**不能由指挥 Agent 自评**

02 §7 已经允许 Agent「否决脚本的判定，但必须写明理由；沉默即视为接受」。
**同样的口子会立刻出现在审计上**：一个被审计判定 DEGRADED 的 Agent 会说"这是误报，我否决"。
审计若可被否决，它就退化成一份建议。

**职责切分必须分三档，不能只有两档（02 §5.3 的三层要扩成四层）：**

| 层 | 可以否决自己吗 | 依据 |
|---|---|---|
| 脚本算事实 | — | 时刻、mtime、解码结果 |
| 看门狗出动作单 | **可否决，但必须写理由** | 02 §7 已定 |
| **审计判定交付态** | **不可否决。只能申诉，申诉写入报告且不改变判定** | **本报告新增** |
| 用户 | 随时 | — |

**并加一条独立于意志的兜底**：`audit` 的**输入完整性**自己写进结果
（读了多少文件、哪些读不到、`delivery_state.json` 是否可解析、ffprobe 是否可用）。
**读不到一律当红（fail-closed），不许 fail-open。**
项目已有直接先例：**L-025「盘点步骤被吞 + 陈述污染后续推断」**——
审计者自己被污染过一次，所以审计必须能被审计。

#### ③ 审计跑几次

**两次，不是一次**：
```
冻结前一次  → 决定能不能进 ACCEPT（此时可 DEGRADED，不可 WITHHELD，因为还没到交付）
交付前一次  → 决定能不能交（此时可 WITHHELD）
```
理由：**中间的 REWORK 是新的不可信来源。** 返工改的是时间线，改完的版本从未被审计过。
**只审计一次 = 审计了一个已经不存在的版本。**（864 v6 的教训正是"审的是上一版"。）

#### ④ 「不可信就别交」会不会变成"永远不交"

会。这是它最可能的表现形式，而且**它比交错片更隐蔽**——用户只看到"没结果"，
而项目里已经写了 8 个任务的目录。

**处置（可机检）**：
```
每局的 audit 必须留下一条 status_line，且必须是三态之一。
WITHHELD 若在同一局出现 > 2 次 → 强制降 DEGRADED，且在报告写「本版经过 N 次可信度拦截后降级交付」
```
**这条把 WITHHELD 的次数也变成可见数字，和 FM-06 的「看片 M 张」是同一个设计模式：
用户看不懂过程，但看得懂计数。**

### 3.4 交付给用户的那一行长什么样

这是本次改造**真正的交付物**（不是那个 mp4）。三条硬要求：

```
reports\trust_audit_<序号>_v<N>.md 第一行（机器生成，Agent 不得改写，只能在后面追加）：

  可以看。本版有 3 处打折：① 第 4–5 分钟之间的战斗边界按保守留的（没人复查过）；
  ② 2 处战斗中的面板遮住战场，靠语音判的；③ 秒点标定置信度低，边界可能整体偏半秒以内。
  全片 13 分 27 秒，看过 41 段共 168 张。

禁止出现在这一行里的词：应该 / 可能 / 大致 / 基本 / 尽量 / 待确认 / TODO
（"可能" 允许出现在"已明确降级"的说明里，不允许出现在"能不能看"的判定里）
```

**为什么必须是机器生成**：它必须与 C1–C7 的数字一一对应；
Agent 手写的这一行在用户不在场时**没有任何理由认为是诚实的**。
而它恰恰是整条链里唯一对用户诚实的东西。

## 4. 回退方案

### 4.1 判据：什么情况下应该撤掉这套改造

**按代价排序——质量判据先于时间判据。** 理由：用户不在场时，**错片的代价 > 慢**。

| # | 判据 | 阈值 | 动作 |
|---|---|---|---|
| **R1** | **交付被用户否决，且否决理由落在门禁本该覆盖的范围内**（漏战 / 边界切错 / 半成品泄漏 / 场次被合并） | **1 次** | **该门或该拦截立即降为 WARN 并重设计。不是加更多门。** |
| **R2** | 新门在 2 局内造成 ≥1 次假 FAIL，且定位耗时 > 30 min | 1 次 | 该门默认降 WARN，重新设计判据 |
| **R3** | 连续 2 局 span 未低于改造前同型局 +50%（861 型基线 10.05 h → 15 h；故障型 33.46 h） | 2 局 | 撤**当批**（不是整套） |
| **R4** | 单局 span > 15 h 且 watchdog 报告"未触发任何换路" | 1 次 | 撤 watchdog 批（它没起作用） |
| **R5** | 实施中出现了**该批设计里没有的第三种失效形态**（例：收编后又造出第 4 份 `build_program.py`） | 1 次 | **立即停止该批**，先补设计再继续 |
| **R6** | 批次实施 + 回归 > 3 天且未跑通一局完整实跑 | 3 天 | 拆小或撤 |
| **R7** | 用户因这套改造**多花了时间**（原话对照：改造后比改造前更久才看到第一版） | 1 次 | 撤"提前可见"那一类（wip / 心跳），保留纯内部机制 |

**R1 的表述要特别强调**：**被否决一次的第一反应必须是"查门禁为什么没抓到"，而不是"再加一道门"。**
项目栽过两次相反的错（`POOL.md` L-031/L-032：假 FAIL 之后静音它；
L-052：把一个错的标定当 ROI 背书）。**这条是本次改造的元纪律。**

### 4.2 倒序回退：先撤会产生错交付的，最后撤只是慢的

```
撤 1  wip（批 6）        —— 唯一直接产生"半成品被当成品"风险的一项，用户侧收益 ≈ 0
撤 2  新门（批 1/4 的 FAIL 位）—— 只降为 WARN，不删代码（代码留着当 measured 输出）
撤 3  提示词语义替换（批 4）—— 纯散文，回退 ≈ 5 分钟（05 号给了逐字原文）
撤 4  状态机强制（批 5）  —— 关开关，不删脚本
撤 5  剧本指针与 P1/P2/P3/P5（批 3）—— 纯散文
【保留】脚本收编（批 2）—— ★ 最后才撤，且通常不撤
```

**为什么收编最后撤、且通常不撤**：
脚本收编的失败模式是"**跑不通**"，不是"**跑出错**"——它只读输入、幂等、输出数字、
三路求和不一致就报错（06 §6.1 第 6 条）。**撤销它不会改善交付质量，只会让下一局重新开始重写、
重新安静地重犯 08 号已证伪的帧轴错误。**
> 这就是 AGENTS 那条数据丢失护栏的同构：**错的代价 > 慢的代价，所以倒序撤。**

### 4.3 操作

1. **每批开工前一次提交 + 一个 tag**：`oneprompt/b1-coverage` … `b6-wip`。
   回退 = `git revert` 到 tag 之前 + **保留一份 diff 文件**（`reports\batch_k_rollback_<date>.md`）。
2. **每批带一个开关**，落 `config\oneprompt_flags.json`，稳定前默认 `off`：
   ```json
   { "coverage_gate": false, "deleted_voice_audit": false, "audit_delivery": false,
     "watchdog_bg": false, "wip": false, "oneprompt_p6": false }
   ```
   **回退 = 改一个布尔，不是删代码。**
   ⚠ **纪律**：开关必须被回归测试**两组都覆盖**。只测 on 分支 ⇒ 关掉那天才发现 off 分支已腐化
   ——**这正是"别改了又改错了"的典型形态：回退路径本身没人走过。**
3. ⚠ **开关本身会成为第二份真源**（违设计原则 1）：条文里**不许写"某门是 WARN"**，
   只写「按 `coverage_gate` 开关的判定」。**开关是唯一真源。**
4. **回退必须留证据，不许删痕迹**：写 `reports\batch_k_rollback_<date>.md`，
   并在 `docs\lessons\POOL.md` 的「**⚠ 已被实测推翻**」节登记一条
   （该节已有先例：L-052 帧轴标定、L-057 合成路径）。
   **回退不是抹掉，是把结论改成"这条错了"并留在原地。**
5. **回退后必须跑一次只读回放**：`test_whole_battle_gates.sh` + 对 8 个历史任务目录跑
   `resume`（应为 `STATE=MISSING` 而不是 FAIL）+ 35 份历史时间线跑 `coverage_complete`（应零 FAIL）。

## 6. 尖锐问题：省下的时间会不会被「等结果的焦虑」吃掉？

### 6.1 冲突是真的，而且有时间账

| 事实 | 出处 |
|---|---|
| 用户要求「不要分段汇报，最后一次性给结论」 | `docs\粗剪提示词.md` L27 |
| 改造后到第一版的投影：**5.1 h 中位，地板 ~3 h** | 01 §5.1 / §5.4 |
| 改造前实况：864 型 **2.94 h**、861 正常局 **10.05 h**、861 故障局 **33.46 h** | 05 §1.2 / 02 §3.3 |
| wip 的首版时间：**2.2–2.7 h**（比改造后中位早约 2.4–2.9 h） | 03 §B.1 |

> **这 2.4–2.9 小时就是全部问题。** 更精确地说：
> **改造把"早给你看"这条收益拿走了（用户无感），却把"晚给你看"的风险留下了（用户有感）。**

### 6.2 三个选项与取舍

| 选项 | 用户侧 | 改造侧 | 判定 |
|---|---|---|---|
| **A. 严格一次**（现状条文） | 焦虑 3–5 h（正常局）/ 10–33 h（故障局），**且无任何信息** | 零额外机制 | ❌ 焦虑 = 不确定性，**不是时间**。给他 ETA 比早 2 h 强得多 |
| **B. 早交 wip**（03 号 B 节的原始设想） | 拿到一份**会变**的片子 → 更焦虑（"这版是不是最终版？"） | 泄漏风险最高（FM-21） | ❌ **在"不要分段汇报"的诉求下是反效果** |
| **C. ETA 心跳**（本报告推荐） | 每 30 min 一行：已用时长 / 预计剩余 / 当前卡点。**不含任何可播放产物** | 需要 watchdog 在线 | ✅ **焦虑被台账算术消化** |

### 6.3 推荐：**C —— 心跳，且必须是「通知」不是「汇报」**

**四条判据（写进条文，否则下一任 Agent 会以为心跳就是"分段汇报"而不敢发）**：

```
1. 心跳里【不含任何可播放产物】——不许出现 preview\ / wip\ / E:\Cujian导出 的任何路径。
   （这一条同时防住 FM-21：用户一旦看到 wip 路径，就会开始"看 wip"。）
2. 心跳里【不含结论】——只有三个数：已用时长、预计剩余、当前卡点（卡片名，不含黑话）。
3. 心跳【不可回复、不可交互】——它是通知，不是请示。用户回了也不改变流程。
4. 心跳【默认发】——不预先问用户要不要。这是唯一一条会被 R7 判据推翻的（见下）。
```

**样例（30 秒一行，不超过 3 行）**：
```
[02:10] 已用 1 小时 12 分 · 预计还需 40–70 分 · 现在在收最后 3 路扫描（14 路里回了 11 路）
[02:40] 已用 1 小时 42 分 · 预计还需 30–60 分 · 在合并 + 出第一版预览
```

### 6.4 为什么这条不是"多一个功能"，而是**最强的一条技术论证**

> **ETA 只有在 watchdog 在线时才是算术，而不是猜测。**
> 心跳里"预计还需 40–70 分"这个数，**必须来自 T2 的 `clamp(3 × p50, 60, 240)`**——
> 而 T2 需要后台进程、需要 `delivery_state.json`、需要看门狗在用户离开时还活着。
>
> **也就是说：用户对"等焦虑"的诉求，和 watchdog 上线的理由，是同一件事。**
> 而 watchdog 恰好是这套改造里最重的一项（批 5c，要点头）。
>
> → **所以批 5c 的立项理由不应该只写"尾部省 6.5 h"（02 §3.2）。**
> **应该写：没有它，用户会拿到一个编出来的 ETA；有了它，焦虑从"猜的"变成"算的"。**
> **这是驳"改造让用户更焦虑"这一质疑的最有力回应，也是唯一一处改造的收益与用户的感受正相关的点。**

### 6.5 心跳的三个已知风险与处置

| 风险 | 处置 |
|---|---|
| **用户开始干预**（"太慢了，换个素材吧"） | 心跳文案里**禁止出现任何可决策的选项**。它是状态，不是菜单 |
| **心跳退化成"分段汇报"** | 判据第 2 条：心跳不含结论。**汇报有结论，心跳没有。** 这一条可 grep |
| **用户其实不在意等待 → 心跳是纯噪声** | 默认发**一局**。如果用户回"不用"，**立刻关掉并写进 `style_profiles`**（这是用户偏好，不是门禁）。**只问一次，且这一次的答案是"关掉"，不是"开"** |

### 6.6 一句话回答用户

> **改造省下的 2.4–2.9 小时不会被他"等焦虑"吃掉——只要把"早看半成品"换成"每 30 分钟一个台账算出来的 ETA"。**
> 前者给的是**会变的东西**（更焦虑）；后者给的是**对未来的准确估计**（焦虑下降）。
> 而这个 ETA 只有 watchdog 算得出来——所以"给 ETA"不是改造之外的新要求，
> **它就是 watchdog 存在的第二个理由，而这条理由比省 6.5 h 更硬。**

## 7. 诚实边界（本报告也可能错在哪）

1. **21 条失效模式里，有 8 条（FM-03/05/06/09/13/16/19/21）是本报告的新增推断，没有实测数据。**
   它们的设计依据是 04/05/06 已实测的事实类比，但**类比不等于证明**。
   **处置**：每一条都写成了"可机检的判据"，落地时要么被 fixture 证实、要么被证伪——**不许带猜测定上线**。
2. **FM-02 的三层防伪没有一层能真正阻止自动化伪造签名**，只提高成本。
   真正拦住它的仍然是 `WITHHELD` + 用户看片。**这一条我不打算粉饰。**
3. **`WITHHELD` 的 90 min 与签名速率上限 12 条都是猜的。**
   前者应与 watchdog 的 `[60,240]` clamp 对齐后实测；后者必须拿 8 个历史任务目录标定。
4. **T3（语义层错误）本报告完全没能给出机器方案**，也不认为有。
   04 号列的 7 种漏战形态里至少 4 种（场尾未走完 / 两场该分被合成 / battle 内部顺序错乱 / 场首已在打）
   **至今没有判据**。这意味着：**改造做完之后，"看起来对但剪错了"这一类失败仍然只能靠人发现。**
   唯一能做的是让**人发现得便宜**（缺口节点名 + 看片 M 张 + ETA 早知道），
   而不是**让人不必发现**（后者才是过度自信的来源）。
5. **批 6（wip）我仍判定收益未测**，03 号已如此判定。若 D2 的实测显示
   "缺陷发现没有提前"，**wip 应直接不上**——它是全套改造里唯一一个"用户零收益"的部分。

## 8. 给决策者（六条）

> 1. **这套改造引入 21 条新失效模式**，其中最危险的不是"慢"，是 **FM-02（自动化必然走"登记成删除段 + 重算 program map"这条路，19 扇门全绿）**
>    和最阴的 **FM-05（「已知缺口」是用户不在场的唯一信息通道，而它现在是零机检的自由散文）**。
> 2. **「不可信就别交」= 一个独立于指挥 Agent 的审计脚本（7 项 CHECK → 三态出口）。**
>    三条命门：**审计的判定 Agent 不可否决**；**必须跑两次（冻结前 + 交付前）**；
>    **不存在"停在不交"这个终态**——WITHHELD 必自带续跑与超时强制降级，否则它会变成 861 的新名字。
> 3. **回退判据按代价排序，质量先于时间**：「交付被否决 1 次 → 立即降级该门为 WARN 并重设计」
>    （而不是加更多门，项目已栽过两次相反的错）。**倒序撤**：先撤 wip 与新门，最后撤脚本收编——
>    **收编的失败模式是"跑不通"，不是"跑出错"，所以通常不该撤。**
> 4. **分 6 批。104 字段必须拆：批 5a 先上 12 个字段**（刚好够 12 行 resume + T1/T2），
>    其余 92 个"指不出哪个触发器在读它就不许加"。**批 5 天然可回退，因为批 3 的 P2「两形态二选一」先落地了。**
> 5. **每批带一个开关，且开关必须被两组回归都覆盖**——否则回退那天才发现 off 分支已腐化，
>    这正是「别改了又改错了」最典型的形态：**回退路径本身没人走过。**
> 6. **对「等焦虑」的回答：给台账算出来的 ETA，不给早半成品。** 心跳必须是「通知」不是「汇报」
>    （四条判据可 grep）；而 ETA 只有 watchdog 算得出来——**「给 ETA」就是 watchdog 上线的第二个理由，
>    这条理由比尾部省 6.5 h 更硬，也把"改造会让用户更焦虑"这个质疑直接解掉了。**

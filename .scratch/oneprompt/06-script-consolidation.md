## 3 帧轴标定收编时必须换成什么基准（题目点名）

### 3.1 864 的方法为什么必须整个扔掉

`frame_calibration.md` 的做法：
- 被测 `seg4\f_00046.jpg`，由 `-ss 255 -i proxy_960.mp4 -t 90 -vf fps=1` 产出，声称源秒 = 300；
- 参照 `direct_t300.jpg`，由 **`ffmpeg -ss 300 -i proxy_960.mp4 -frames:v 1`** 产出；
- PSNR 峰值落在 index 46、两侧各低 6 dB → 判"映射成立、**不存在系统性偏移**"。

两个致命缺陷：
1. **参照系与被测对象同管线**（861 的循环论证原样复发）。两条都走 `-ss ... -i proxy`，`-ss` 落点误差**同向对消**。
2. **测量分辨率不足一个数量级**：步长 1 s = 60 帧，要发现 29 帧的偏移需要 **≤ 1/60 s** 的探针。29/60 ≈ 0.48 s 落在同一格里——**这套测法在原理上看不见它**。

而且这条错误结论已经进了经验池：`POOL.md L-052` 把它记成"回报比最高的一笔投入"。
**08 §8 的判断成立：它污染了经验池。**

### 3.2 必须换成的基准（本轮已实测复现）

> **参照系只能是"帧号 / 容器 PTS"，绝不能用第二次 `-ss` 重建。**

两条等价的干净参照，本轮都验过：

**(a) 帧号窗（推荐，一次解码拿一批）**
```
ffmpeg -i <输入> -an -vf "select='between(n\,A\,A+90)',scale=640:360" \
       -fps_mode passthrough -q:v 3 ref_%03d.jpg
```
**这一路不含 `-ss`、不含 `fps` 滤镜。** 第 k 张 = 帧号 `A+k`。

**(b) 容器 PTS（最硬，零解码）**
```
ffprobe -v error -select_streams v:0 -show_entries packet=pts,pts_time -of csv=p=0 \
         -read_intervals 249.9%+0.5 <输入>
```
860 的 `measure_offset_v4.py` 走的就是这条，完全绕开 seek 语义。

**先决断言**：ffprobe 读 `r_frame_rate == avg_frame_rate`（否则不是 CFR，帧号↔秒不是线性，**直接 `[BLOCKED]`**）。

### 3.3 本轮实测结果（在 `E:\PR导出\869` / `874` 上重跑，最佳 MAE 逐位相同）

| 素材 | 时长 | fps 滤镜 | 探针 T | 命中帧 | **偏移** | 最佳 MAE | 次优 MAE |
|---|---|---|---|---|---|---|---|
| 869 (3840×2160, 60/1 CFR) | 981.816667 s | `fps=1` | 250 / 400 / 700 / 900 | `T*60+29` | **+29 帧 = +0.483333 s** | **0.000** | 9.41 / 4.39 / 5.57 / 6.82 |
| 874 (3840×2160, 60/1 CFR) | 713.266667 s | `fps=1` | 100 / 300 / 600 | `T*60+29` | **+29 帧** | **0.000** | 3.68 / **0.095** / 4.34 |
| 869 | 981.816667 s | `fps=2` | 250 / 700 | `T*60+14` | **+14 帧 = +0.233333 s** | **0.000** | 9.29 / 4.27 |

容器事实（ffprobe 实测）：`start_time=0.000000`、`time_base=1/60000`、
`r_frame_rate == avg_frame_rate == 60/1`、`nb_frames=58909`、`pts 14970000 ↔ 249.500000 s`
→ **帧号 N ↔ N/60 秒，零歧义**。

### 3.4 三条与 04/08 不一致的实测结论（本报告的增量）

1. **偏移是 +29 帧，不是 +28。** 08 报"4K 源 = +0.4667（28 帧）"，我在**同一个 4K 源**上测得 **+29**；
   08 报的 +29 是在 960 代理上。我在**另一个 4K 源 874** 上也是 +29。
   → 08 的"源比代理少一帧"这条**在源侧没复现**。**这恰恰是最强的论据：连两次谨慎实测都差一帧，
   所以这个常数绝不能写进文档，只能做成每局执行的断言。**
2. **`-ss` 本身零误差，误差全部来自 `fps` 滤镜。** 分离实测：
   `-ss 250 -i SRC -frames:v 1` 对 `select='eq(n,15000)'` → **MAE 0.000**（`-ss` 逐帧精确）；
   `-ss 250 -i SRC -t 1 -vf fps=1` 对同帧 → **MAE 29.4**（画面换了）。
   → 收编脚本可以**直接绕开问题**：定点取证（模式 B）一律用逐帧显式 `-ss`，**永不过 `fps` 滤镜**，偏移按构造为 0；
   `fps=1` 只许用于扫描条带，且条带帧名必须带标定后的真秒。
3. **08 §6.5 Step 4 的判据"次优 MAE > 3×"是错的，不能当门禁。** 最佳 MAE 恒为 0.000，倍率无定义。
   真实情况是**次优 MAE 随场景运动量剧烈变化**：869 的 4.4–9.4 vs **874@300 的 0.095**——
   静态画面里相邻帧几乎一样，按 08 的判据会把一次**完全正确**的标定判成 FAIL。
   → 正确形态：判定用**位级相同**（`best_mae == 0.000`），**次优 MAE 只作为"可辨识度"报告**；
   次优 < 1.0 时输出 **`LOW_CONFIDENCE` 而非 FAIL**（静态场景偏移不可辨识，但画面也不变，偏移无害）。

### 3.5 写进 `frame_axis.json` 的字段

```
{ input, input_fingerprint(sha256|mtime|size), fps_filter_value, source_fps,
  probe_points: [{T, A_frame, matched_frame, offset_frames, best_mae, second_mae}],
  offset_frames, offset_seconds, verdict: CONFIRMED|LOW_CONFIDENCE|FAIL_UNSTABLE,
  verified_frame_count }
```
断言：**≥4 个探针点的偏移必须帧级完全一致**，不一致即 `FAIL_UNSTABLE`（落点不稳定，任何秒点推算都不可信）。

### 5.2 一票否决（命中即永不收编，直到该问题被解掉）

| # | 否决条件 | 实证 |
|---|---|---|
| **V1** | **源码里存在任一具体素材的常量**——时长、分辨率、具体源秒、场次名 | `freeze_kit.py` **4 处**：`abs(cursor - 1152.233)`、`(v["width"],v["height"]) == (1280,720)`、`regression_864_named_fight_present` 硬编码源秒 896.5/897/900/904/908。`extract_frames.ps1` **1 处且是默认参数值**：`[double]$Total = 1152.233` |
| **V2** | **需要 OCR / 分类器 / 阈值才能给结论** | `ui_probe.py` 是无阈值最近邻（`verdict = OPEN if a < b`）+ 硬编码裁切窗；`hud_curve.py` 需要还不存在的 OCR 能力（864 §4.1：HUD 上 `攻击提升/暴击/还阳·愈` 与敌方名牌位置极近，会读错） |
| **V3** | **写操作且无幂等 diff** | 16 个 `patch_*` 每个都是一次性 JSON 手术，无法回归测试 |
| **V4** | **规则本身有已知反例** | 碎片化"≥3 段且单段 <6 s"：864 的 `combat_002` 270 秒、`combat_005` 249.5 秒。**纯段数阈值在这类长战上必然误报，而误报后唯一理性反应就是静音它** |

### 5.3 V1 为什么是最狠的那条（本轮实证）

`extract_frames.ps1` 的 `[double]$Total = 1152.233` 是**默认参数值**。拿它去扫 869（981.816667 s）：
- `$start -ge $Total` 要到 1152.233 才停 → 会计划 **12 段**，而片长只够 **10 段**；
- 最后一段 `-ss 1105` 落在片尾之外 → **ffmpeg 输出 0 帧、不报错**；
- 脚本照样打印 `seg11 [1105, 1152.233) frames=0`。

这就是 04 §2.4 的"静默失败比崩溃贵"，**而且它已经固化成一个默认值**。
素材专属的脚本一旦收编，它的默认值会在别的素材上**静默**产出错结果——
**收编一个带素材常量的脚本，等于把这一局的坑推广到所有局。**

## 6 收编几个合适？我的数字：**3**

### 6.1 为什么是 3（而不是 1，也不是 6–7）

**下限 3 的理由**：这三个正好是 §1 量出来的**生产者缺口全集**。少任何一个，剩下两个缺口就会继续每局重写——
这正是 144:15 的成因。

**上限 3 的理由**（收编是有维护成本的，每个都要测）：

1. **另外 9 个候选里有 5 个缺前置条件**（阳性对照、幂等 patch 设计、check-name 并集、OCR 能力、阈值分离度）。
   把它们标成"必须"，等于要求**上线前就得上线**——而 04 §5.2 已经论证：**没有阳性对照的门禁比没有门禁更危险**。
2. **2 个是纯搬家、1 个有规格**：`build_program.py` / `map_captions.py` 逻辑一行不用改（只换 `argparse` + `__file__` 相对路径），
   `capture_frames.py` 有 08 §6 的完整规格，且它最难的部分（帧轴）本轮已经端到端实测通了。
3. **回归 fixture 是白送的**：855/859/860/861/864 都留了当时的时间线、SRT、cut_list 和人工答案，
   三个脚本都能直接拿历史答案当断言，**不需要新造 fixture**。
4. **维护成本可承受**：3 个脚本 ≈ 3 份测试 + 3 份 docstring + 3 个归属人。
   15 个（04 的候选数）超出现实承受力，而 04 自己也把它列成 **backlog 而不是 sprint**。
5. **改门禁 ≠ 收编脚本**：`qa_gate.py` 加 `subtitle_bodies_are_text` 是**改 1 个已存在的文件**，
   不是新增一个要维护的对象。把它算成"第 4 个脚本"会虚增维护估算。
6. **收编后的净风险必须是 0**：三个脚本全是**只读输入、幂等、输出数字、不会猜**。
   `build_program` 三路求和不一致就报错；`map_captions` 的 stats 是数字不是判决；`capture_frames` 只出文件和轴 JSON。
   **没有一个能产出假 PASS** —— 这是收编的第一原则，04 §5.1 列的 6 个"高 ROI 低风险"正好就是这三个。

### 6.2 "3"不等于"3 天"

- **零新代码**：`build_program.py`、`map_captions.py`（+ `qa_gate.py` 一处增项）
- **唯一有真实构建成本的**：`capture_frames.py`（08 自估半天 + 2 fixture），且它的正确性判据本轮已实测

### 6.3 一条必须写进 `AGENTS.md` 的硬规矩（04 §6 已提，我背书）

> 任何写在 `123\<任务>\reports\tools\` 或 `cache_scripts\` 下的脚本，若被复用第二次，
> **必须**在同一轮内收编进 `scripts\` 或 skill `scripts\`；**收编前它不算证据，只算草稿**。
> 收编时必须附一条回归 fixture，**证明它对至少一个历史任务的重跑结果与人工当时的答案一致**。

配套执行手段（否则这条规矩会像 AGENTS.md §1 的 WARN 一样被反复忽略）：
把"某个 `reports\tools\*.py` 出现第 2 次"做成 `check_task_hygiene.ps1` 的一条 **WARN→BLOCKER 升级项**。
现在这条 WARN 已经被无视过至少一次（乱码目录），教训是：**靠人记的规矩必然失效，要靠门禁。**

## 7 风险与边界（必须说清的三件事）

### 7.1 收编 ≠ 一句话出预览

04 §3.3 的账：三局 62.6 h 里 **46.5% 是纯等待**（并行度问题），脚本能吃掉的只有 26–38% 的重复劳动。
**收编这 3 个脚本不会让"一句话出预览"成立**，它只保证新任务不再重写脚本、不再重犯已证伪的错误。
把它当成产品本身会失望；它是必要条件，不是充分条件。

### 7.2 收编后的脚本不通用 = 新的桎梏

这是题目第 6 问的实质。防线是 §5.2 的 **V1**：**任何素材常量进 `scripts\` 都算污染**。
本轮实测发现的最危险一例不是某局脚本里的常量，而是 `extract_frames.ps1` 的
`[double]$Total = 1152.233` **默认值**——默认值会静默扩散，比一个只在任务目录里生锈的硬编码更坏。

配套要求：`capture_frames.py` 收编后必须做到
**「不给 `--input` / 不给几何参数就直接 `[BLOCKED]`」**，而不是"给个默认值猜"。

### 7.3 抽帧在时间账上不是瓶颈

08 §4.4：抽帧只占首版时间约 **1.7%**（3 min / 2.94 h），且实测重复抽帧 ≈ 0。
所以收编 `capture_frames.py` 的收益**不是省时间，是可追溯性**——
它是"T2 事故为什么能发生"的结构性修复。**不要用"能省几分钟"来论证它，也不必用它来论证它。**

## 1. 「关联性」这个问题，答案比想象的更干脆

### 1.1 看图根本不是瓶颈

三局实际剪辑的时间分布（三局合计 62.51 小时）：

| 环节 | 耗时 | 占比 |
|---|---|---|
| 静默 / 无产出（夜间为主） | 29.07 h | 46.5% |
| 审片 / 对抗审 / 验收（几百份报告） | 10.77 h | 17.2% |
| 时间线合并与裁决 | 4.80 h | 7.7% |
| 分段扫描（**真正看图的那部分**） | 3.54 h | 5.7% |
| 字幕、返工、4K 渲染等 | 11.5 h | 18.4% |
| 纯机器干活（转写、抽帧、检测、编码） | 1.17 h | **1.9%** |

- 所有会碰图的环节加起来，**极端假设下最多占总时间 35%**；实际估算 **9%–14%**。
- 也就是说：**就算把看图时间归零，最多也只能省下大约十分之一的时间。**
- 真正的大头是**审片**（17.2%）和**静默**（46.5%，主要是夜里没人操作）。这两块跟图片预算毫无关系。

### 1.2 而且放宽之后只会更慢

**134 路**扫描员逐路申报过用量。**没有一路碰到 50 张的上限。最高 45 张，中位数 14–26 张。**

各路停下来的原因写在报告里，**没有一条是「预算不够」**：

> `adversarial_19_v5_adv10`：抽了 **1075 帧**做扫描，只读 **26 张**就结案。
> `adversarial_864_v1_adv4`：预算脚本预跑算出「需要分 7 轮」，然后全路只用了 **15 张**。

**它们停下来是因为「没东西可查了」，不是「不敢多看」。**

读图时间大致随张数线性增长。如果真按放宽后的额度用满（比如中位数从 21 涨到 84），
在同样的总时长上要多花 **26 小时 ≈ +42%**。

> **结论：放宽预算，最可能的结果是更慢，不是更快。**

### 1.3 最干净的一次对照：看更多图的那次，输了

同一份素材（864），剪了两遍，除看图规则外**没有任何差别**：

| | **第一次（被整局否决）** | **第二次（一次过，交付）** |
|---|---|---|
| 总耗时 | **20.29 小时** | **10.90 小时** |
| 看图量 | **≈447 张** | **407 张**（更少） |
| 每秒看图密度 | 0.388 张/秒（**更高**） | 0.353 张/秒 |
| 产出报告 | **83 份** | 44 份 |
| 版本数 | v1→v6 | v1→v3 |
| 结果 | 你判定仍有问题，要求整局重剪 | **通过** |

**看更多图、跑近两倍时间、出 1.9 倍审件 —— 输了。**
**看更少图、不到一半时间 —— 过了。**

**这一条直接回答了你「关联性不强就不用改」的意思：**
关联性不只是弱，对速度是**反向**的。

## 2. 「能接受多少张」：这个数确定不了，但有些数是确定的

### 2.1 现在跑的是什么模型

`opencode-go/space-bunny-free`（旧网关的 `muse-spark` **从未在本项目用过实质工作**）。

### 2.2 能确定的（实测）

| 项 | 数字 | 来源 |
|---|---|---|
| 模型单次输入上限 | **524,288 token** | 模型元数据 |
| 工具自动压缩触发线 | **471,860 token** | 从客户端程序里读出来的算法 |
| 50 张图大约折算 | **75,000 token ≈ 上限的 14.3%** | 客户端估算常数 1500 token/张 |
| 换算：多少张会撑到压缩线 | **约 314 张** | `(471,860 − 0) ÷ 1500` |
| **实测中，单条消息带图最多** | **10 张**（651 个会话，跨 6 天，超过 10 的：**0 条**） | 直接读本机会话数据库 |
| 实测中，单个会话累计最多 | **50 张**（正好 1 个会话，压在线上，正常跑完） | 同上 |

### 2.3 确定不了的（这是重点）

**「这个模型单次到底能吃多少张」——查不到。**

四条可能的答案来源，全部查到底：

| 来源 | 查了什么 | 结果 |
|---|---|---|
| 客户端程序代码 | 有没有按张数拒绝图片的分支 | **没有**。真正存在的图片限制是**单张**的：宽度超过 2000px 会被静默缩小，单张 5 MB 上限 |
| 网关文档 | 公布的限制条款 | 只有**金额**和**token**，**没有一条跟图片张数有关** |
| 网关 API | 返回的限制字段 | 4 个字段，零限制信息 |
| 模型元数据库 | 有没有数量/尺寸字段 | 只有「支不支持图」，**没有「最多几张」** |

> **这个数字在任何公开接口上都不存在。**
> 网关是转发层，真实上限在它背后的模型手里，而那只手没有把它公开。

### 2.4 三件必须一起说的诚实修正

1. **314 张不是真上限，是「我们自己的工具开始压缩图」的那条线。**
   而且 1500 token/张是**客户端为了判断要不要压缩而用的估算常数**，不是真实计费口径。
   实测图片体积跨度有 30 倍（70 KB 到 2.6 MB），网关明说图片是**按尺寸**折算 token 的 ——
   一个固定常数在原理上就不可能一直对。所以 **314 这个数本身也是估算**。

2. **token 根本不是当前的约束轴。** token 允许 314 张，而项目记录的唯一一次真事故是 **53 张**就死了 ——
   失败点比 token 天花板**低 6 倍**。这说明卡人的东西在 token 之外，而且我们不知道是什么。

3. **50 张这个数的唯一出处，是你自己的一段回忆，而那段回忆自己就写了「我也不知道这个预算到底是多少了」。**
   项目后来把它升格成了「无论什么模型都是 50 张」的定律，还加了一条
   「任何文档不得把它写成仅适用于某个模型的临时限制」——
   **这是全项目唯一一条自带「不许复核我」的条款。**

## 3. 你可能不想听，但必须知道的事实

> ### 这条规则**从未拦住过任何东西**，也**从未救过任何东西**。

| 判据 | 结论 |
|---|---|
| 有第一手的事故证据吗（错误原文、状态码、日志、日期） | **0 条。全库一条都没有。** 「作废」这个词只出现在规则自己的文字里 |
| 规则说死过几个会话？ | **自相矛盾**：一处写「两个」，另一处一句话点名 4 个 ID |
| 这 5 个会话 ID 能核对吗 | **5 个全部不存在于本机会话库**。ID 格式属于**另一个 harness** |
| 实际读图多少次？ | **10,730 次。峰值 50 张，零超限** |
| 违规的实际后果是什么？ | 有一次**单轮看了 19 张、自认越线** —— **没死，还因此发现了三条错误结论** |
| 全库唯一死掉的会话死于什么？ | `500 Endpoint is unavailable`（服务端故障），**跟图片毫无关系** |
| 全部 44 条服务端错误里，有几条涉及图片？ | **零条** |
| 那两次事故如果真的发生过？ | 必然发生在会话数据库的记录起点（2026-09-28）之前。**本机对此零记录，git 也查不到（入库前没有版本库）。** |

### 必须同时说清的两件事，否则这封说明会变成「删规则的理由」

**第一，准确表述是「无法证实」，不是「已证伪」。**
本机查不到的那两次事故，在任何地方都没留下痕迹 —— 而一次真的把会话打死的网关故障，
通常会在错误流、状态码、或至少一句抱怨里留下脚印。
「什么都没有」本身就是一条弱证据，但**不是铁证**。

**第二，这条纪律本身是有用的，只是有用的是「纪律」，不是「50」这个数。**
- 542 个读图会话**全部逐路记账、零超限**，单条消息峰值恰好 10 = 单轮上限 —— **纪律确实被执行了**。
- 它逼出了**联系表**（863：560 帧 → 28 张表，压缩 20 倍）和**零看图数值判据**（37 份报告、87 处显式声明），
  这些成果是净收益，该留。
- **真正在起作用的是「单轮 ≤10 张」这个纪律。50 只是「单轮 10 张 × 跑满 5 轮」的算术副产品。**
  累计 ≥46 张的那 4 个会话，每一个都恰好需要 5 轮。

> **一句话：50 描述的是流程的输出，不是流程的约束。**
> 542 个读图会话里 **537 个（99.1%）是子 Agent**，一路只负责 85 秒的素材。
> 一路就算想看满 50 张，也得独自扛下整局 1152 秒 —— 而流程从来不这么干，因为**并行分工本身就是天然的预算隔离器**。

## 4. 但另一面必须讲清楚：真正伤画质的是「看不清」，不是「看太少」

这一节是给「那到底该不该留点预算」一个**正面理由**。

### 4.1 一次实测：640px 联系表，5 路全错

864 交付那次，5 路扫描员**各自独立**地在 640px 联系表上踩了同一个坑：

| 画面里实际是什么 | 在联系表上被读成了 |
|---|---|
| 紫色血条 | 强化面板 |
| 绳索摆荡 | 举弓瞄准 |
| 1.6 秒恢复 | 法门面板 |

> **「没有任何一路是看了联系表就下对的。」**（`workflow_notes_21.md §1.3` 原文）

后果直接命中你最在意的东西：**整段战斗被判成面板删掉了。**
修正办法是 **960px 单帧复核**，单位成本高 12–24 倍。

### 4.2 账本有一个系统性偏差

**一张 24 格联系表，和一张 960px 单帧，在预算账本上都记「1 张」。**

- 1 张联系表：307 token，每格摊 **12.8 token**，上游折算后每格实际只有 **131×74 像素**
- 1 张 960×540 单帧：691 token

**HUD 上的小字在 74 像素高的格子里物理上不存在。** 但账本看不见这件事，它只看得见「1 张」。

→ 所以规则里那句「**超过 10 张就优先拼联系表**」被账本系统性地补贴了：
它让「省图」在任何记账口径下都显得更划算，而省图恰恰抹掉了定性所需的信息。

### 4.3 由此得到的诚实回答

> **「因为怕超预算所以不敢多看」——这个担心方向反了。**
>
> 真正贵的是**看不清**，而「看不清」从来没被 50 限制过。
> 它们是两个不同的量：**出错的量是「每格多少像素」，账本只看得见「几张」。**
>
> 而且要把「看不清」改成「看得清」，成本极低：864 里 seg12 用联系表提的一个删除候选，
> **seg13 用 3 张 960px 单帧就把它否掉了。**
>
> **修正误判从来不需要更多预算，只需要把预算花在决定性的那几张图上。**

## 5. 「换一个模型就不行」这个顾虑

### 5.1 你的直觉是对的，确实无法预知

- 上游是**网关转发**，真实限制不公开（§2.3 四条来源全查穿）。
- 换模型后**唯一会变的量是 token 上限**：现在这个模型是 524,288，同网关另有 200,000 / 272,000 / 512,000 等档位。
  —— 但变的是 **200K → 524K**，不是 **50 → 200**。
- 而且那两次事故**发生在另一个 harness、另一个网关格式上**（规则原文里点名的三个截图工具在我们这里**根本不存在**），
  **跟现在这个模型没有任何证据链上的联系**。

### 5.2 两条不该走的路

| 做法 | 为什么不行 |
|---|---|
| **按 token 算出「能看多少张」** | 直觉答案会给出「314 张」，而**已知失败点是 53 张**。用一个已知失效 6 倍的数字指导行动，比不用数字**更危险** |
| **开会话时试出来（二分探测）** | 用一个**会杀死会话**的操作去测会话能承受什么 —— 手段和被测对象直接冲突。成本不是 token，是一次失败会话的全部上下文 |

### 5.3 务实的应对思路：不预知，改成「失败时便宜」

真值不可知，那就不编。**把工程量花在缩小失败半径上，而不是花在猜那个数上。**

三个机制**都已经在规则里了**，缺的只是把它们当成「保险」而不是「习惯」：

| 机制 | 作用 |
|---|---|
| **联系表** | 把「覆盖多少内容」和「花几张图」拆成两件事 —— 1 张表能覆盖十几帧 |
| **每轮开始前先写下核实记录** | 就算会话作废，**只损失一轮**，不损失整个任务 |
| **疑似不对就换窗口** | 恢复动作是「开新窗口」，本来就便宜、已知的流程 |

> 这三个凑齐之后，**50 这个数字本身就不那么重要了**。
> 这才是「不靠人记住」的真正答案 —— 不是记住一个更准的数，
> 而是让「记错 / 记不准」**不再有代价**。

**另外两个真实的、会咬人的限制，现在完全没人管**（都是从客户端程序里读出来的默认值）：

1. **超过 2000px 的图会被静默缩小。** 我们文档里写的「4K 复核」，在模型侧实际是 2000px 复核。
2. **逼近 471,860 token 时工具会把图片换成文字摘要。**

**这两条都不在 50 的射程里。规则守着一个不存在的敌人，同时对真敌人完全沉默。**

## 6. 三个选项：代价各自是什么

### 选项 1：数字一个都不改，但把它从「法律」降级成「备注」，并修掉真正伤画质的那句话 ★推荐

**做什么**
1. 在 2 处文档顶部加 2 行出处说明：「这个数字来自旧网关一次没留下证据的失败（2026-09-28 之前，本机无记录）；
   当前上限未复现验证，2026-10-05 起不再引用为现行约束。」
2. 删掉那句焊死条款：「任何文档不得将其写成仅适用于某一模型的临时限制。」
3. 顺手修一个**现在就是错的**数字：`README.md:18` 写着「单轮 50 张封顶」，与真源（累计 ≤50 + 单轮 ≤10）直接矛盾。
4. 加一句：「**联系表列数 ≤6（每格 ≥261px）；要更宽的视野就减列数，不要减像素。**」

**代价**：要动 4–5 个文件里的几句话，约 1–2 小时。**工作流一个字节都不动，风险接近零。**

**为什么推荐它**：它是唯一**既不碰任何已被验证有效的流程、又修掉了唯一实证的画质损失源**的做法。
第 4 条（联系表 ≤6 列）此前就被建议过、**项目至今没加** —— 而它直接对着「5 路全误判」那份证据。

---

### 选项 2：完全不动

**代价**
- 继续为一个**查不到出处的数字**付维护成本：**9 处副本**，其中一处现在就是错的。
- 那句「不许复核我」的条款继续关着重新评估的入口。
- 两条真实限制（2000px 静默缩图、471,860 压缩悬崖）继续**没人管**。
- 好处：零改动、零风险。而且要说清 —— 它现在**也是无害的**
  （预算脚本超了只打印提示就 `exit 0`，根本没有强制力）。

**什么时候选它**：如果你觉得「先别动，等哪天真撞上了再说」更安心。**这是一个合理的选择，不是错的。**

---

### 选项 3：放宽数字，或改成按 token 自动算

**代价**
- 放宽到 200 **买不到任何现在不需要的东西**（134 路里 0 路触顶，边际需求 = 0 张）。
- 真用满的话，时间 **+42%** —— **拿时间去换零信息**。
- 改成按 token 自动算更糟：会得出「可以看 314 张」，而**已知 53 张就失败过**。

**不要选这个。** 这是三个选项里唯一一个**既没有收益、又引入了新风险**的。

## 7. 我的推荐，明确说一次

> **选选项 1。**
>
> 不改 50 这个数字（改它既没收益、也有风险），但要做四件小事：
> ① 给这个数字补上出处、并注明「不再作为现行约束」；② 删掉那句「不许复核我」；
> ③ 修 `README.md` 里现在就是错的那句；④ 加一句「联系表 ≤6 列」。

如果你只想做一件事，就做 **④**（联系表 ≤6 列）——
它是四件里唯一直接对着「5 路全误判」那份证据的，且**当场就能验证**。

# 02 · 当前模型（`opencode-go/space-bunny-free`）的图片承载能力

**问题**：现在这个模型大概能够接受多少张图片？
**答**：**不能确定。** 但能把「为什么不能」和「哪几个数字是确定的」钉死。

---

## 0. 三句话

1. **现在跑的是 `opencode-go/space-bunny-free`（variant `max`）**，不是 `muse-spark-1.3-contributor-free`。
2. **token 侧完全确定**：50 张 ≈ **75,000 token ≈ 输入上限的 14.3%**。
3. **因此「50」这个数不是 token 约束逼出来的**——token 允许 **314 张**。它挡的是一个**未公开的上游失败模式**，而那个失败模式的证据**不在当前模型上**。

## 2. token 侧硬约束（全部已核实，前一 Agent 的数字均正确）

### 2.1 模型限额

来源：opencode 本地缓存的 models.dev 目录（`kv.models-dev:catalog`），
`opencode-go/space-bunny-free` 条目原文：

```json
"limit": { "context": 1048576, "input": 524288, "output": 524288 }
"modalities": { "input": ["text","image","video"] }
```

→ **输入上限 524,288 属实**；图片是声明支持的模态。

### 2.2 自动压缩触发线 471,860 —— 从 opencode 二进制里读出来的，不是猜的

`opencode-cli.exe` v2.0.22 中的原函数（已从可执行文件里提取）：

```js
F6 = 16000
N6 = (e, a) => {
  let i = e.input || e.context
  if (i <= 0) return Number.POSITIVE_INFINITY
  if (a !== undefined) return i - a
  return i - Math.max(Math.floor(i * 0.1), i >= 2 * F6 ? F6 : 0)
}
```

代入：

```
524,288 - max(floor(524288 × 0.1), 16,000)
       = 524,288 - max(52,428, 16,000)
       = 524,288 - 52,428
       = 471,860        ← 与前一 Agent 报的数完全一致
```

### 2.3 图片 → token 折算：opencode 固定 1,500/张 —— 属实

同一二进制里的估算函数（原文）：

```js
Gj = 1500   // image/*
Sj = 2000   // application/pdf
P6 = (e) => {
  let a = e.toLowerCase()
  if (a.startsWith("image/")) return Gj
  if (a === "application/pdf") return Sj
  return 0
}
```

**关键限定（前一 Agent 没写清楚）**：这个 1,500 是
**opencode 客户端为「要不要触发压缩」而做的本地估算常数**，
**不是**上游模型真实 tokenizer 的输出，也**不是**网关的计费口径。

## 3. 「张数 ↔ token」的实际关系（本次的核心计算）

| 图片数 | token（@1500/张） | 占输入上限 524,288 | 占压缩触发线 471,860 |
|---|---|---|---|
| 10 | 15,000 | 2.9% | 3.2% |
| 45（历史最高申报） | 67,500 | 12.9% | 14.3% |
| **50（本项目红线）** | **75,000** | **14.3%** | **15.9%** |
| 100 | 150,000 | 28.6% | 31.8% |
| 200 | 300,000 | 57.2% | 63.6% |
| **314** | 471,000 | 89.8% | **~100%（触压缩）** |
| 349 | 523,500 | ~100%（触顶） | 111% |

### 3.1 这张表说明什么

> **「50 张」在 token 维度上毫无约束力——它离真正的 token 天花板差 6.3 倍。**

这不是新规则能解决的问题，而是**归因问题**：
50 这条红线**不是** token 预算逼出来的，它挡的是别的东西。

**token 侧唯一与模型挂钩的量是 `limit.input`**，它随模型变动：
`opencode-go` 目录里 `grok-4.7 = 200,000`、`minimax-m3 = 512,000`、
`gpt-6-luna = 272,000`（分档价）、`space-bunny-free = 524,288`。
所以「换模型后 token 预算会变」是真的——**但变的是 200K→524K，不是 50→200**。

## 4. 能不能确定地回答「能接受多少张」？—— 不能

四条可能的答案来源，逐条查证，**全部落空**：

| 来源 | 查了什么 | 结果 |
|---|---|---|
| **opencode 客户端** | 在 v2.0.22 二进制里搜 `maxImages` / `imageLimit` / `attachment_count` / `too many image` / 按张数拒绝图片的分支 | **无张数上限**。唯一命中的 `maxImagesPerCall=10` 属于无关的 Venice AI **图像生成** SDK |
| **网关文档** `/docs/go`（本次实时抓取） | 公布的限制轴：月度金额、5 小时窗口（=月度额度 20%）、token 单价 | **三条全是金额与 token，没有一条与图片张数有关** |
| **网关 API** `/zen/go/v1/models`（本次实时抓取） | 返回字段集 | 只有 `id, object, created, owned_by` —— **4 个字段，零限制信息**。`/models/space-bunny-free` → **404** |
| **models.dev**（opencode 自己的元数据源） | 226 provider / 8393 模型的字段词表 | 与 image 相关的只有 `attachment: bool` 和 `modalities.input: [...]`；**没有任何数量/尺寸字段** |

> 四条路都查到底了：**这个数字在任何公开接口上都不存在。**
> 网关是转发层，真实上限在它背后的模型手里，而那只手没有把它公开。

### 4.1 唯一一个「实测过」的数字，恰好是最没有信息量的

从 36,449 条本地会话消息里统计（8,009 条含内联图片）：

```
单条消息携带图片数分布：
 1 张 → 3,056 条    2 张 → 652    3 张 → 141    4 张 → 75
 5 张 → 44          6 张 → 18     7 张 → 5      8 张 → 6
 9 张 → 1          10 张 → 2
单条消息最多携带 = 10 张
```

**651 个会话、跨 6 天，单条消息携带图片数的观测最大值是 10。**
这跟 `.scratch/imgbudget2/01-correlation.md` 的结论完全吻合：
**天花板从未被观测到——不是「观测到它很高」，是根本没测到。**

### 4.2 顺带查了真实 token 斜率，仍然不能定论

用「下一条 assistant 消息的总 token 增量」对图片数做最小二乘
（增量的截距吸收了消息正文）：

```
tokens ≈ 4,421 + 1,259 × n_images
斜率 ≈ 1,259 token/张     （客户端常数 = 1,500）
```

**但这个数不能用**，三重污染：

1. 增量里混着消息正文与工具结果，不是纯图片；
2. 图片字节跨度过大 —— 实测 1,204 个图片载荷 `p50=706KB, p90=2.58MB, max=3.91MB`，
   **p90/p10 = 30.7×**。网关文档明写 DeepSeek 视觉模型是
   「Images are converted into tokens **based on their dimensions**」（按尺寸折算）。
   尺寸差 30 倍，**一个扁平常数在原理上就不可能恒对**；
3. 拟合只有 3–4 个不同的 x 值（1/2/3/5），噪声大于信号。

> 只能说「与 1,500 同量级」，**不能**说「就是 1,500」。

### 4.3 最重要的一条：那条 53 张的事故，不在当前模型上

`IMAGE_LIMIT.md` 记的两次作废：`sess_03bfff9d`（小批量累加）与「一次性 53 张」。

- `sess_03bfff9d` **在本机会话库里查不到**——本地库最早只到 2026-09-29，该会话不在窗口内；
- 因此**无法确认它当时跑的是哪个模型、哪个网关**；
- 库里唯一一条 `muse-spark` 会话在 `Documents\Default Project`，与本项目无关。

> **所以：支撑「50」这个数的两条事故证据，都无法归属到当前模型。**
> 当前模型上，50 这条红线**从未被验证过，也从未被逼近过（最高 10 张/条）**。

## 5. 「换模型怎么办」——三种方案

### 方案 A：从 token 侧推导（与模型无关的换算）

**做法**：查 `limit.input` → 减压缩触发线 → ÷ 1,500 → 得可用张数。

**评价：方向对，但不能单独用。**

- ✅ 唯一**机器可读、随模型自动变**的量就是 `limit.input`，这一点确实解决「不靠人记」；
- ❌ **它测的不是约束**。实证：53 张（≈79,500 tok ≈ 15%）**失败**，
  而 token 允许 314 张。**失败点比 token 天花板低 6 倍**，
  说明真正卡人的是 token 之外的东西；
- ❌ 1,500 是客户端估算常数，不是网关计费口径，且对 30× 的尺寸跨度原理上不成立；
- ⚠️ 若要保留，必须**乘一个很大的安全系数**（不能取 1.0），
  否则一换模型就会得出「可以看 314 张」这种危险结论。

### 方案 B：会话开始时自动探测

**做法**：二分搜索图片张数，撞到报错为止。

**评价：自我拆台，不推荐。**

- 若失败形态是**按请求**（4xx），探测便宜 → 可行；
- 但本项目观察到的失败形态是「**会话作废，只能换窗口**」。
  用一个会杀死会话的操作去测量会话能承受什么 —— **手段与被测对象冲突**；
- 探测本身也在消耗要测的预算（§4.1：观测上限只有 10 张，没有可用探测空间）；
- 成本不是 token，是**一次失败会话的全部上下文**。

### 方案 C：承认无法预知，改为「出问题再处理」

**做法**：保留一个保守常数，不试图推导真值；把失败成本压到最低。

**评价：方向正确，但需要补上「恢复机制」才算完整。**

- ✅ 与证据一致：真值不可知，那就不编；
- ⚠️ 单独用不够——「出问题再处理」的前提是**处理得起**。

---

## 6. 推荐：A 的骨架 + C 的态度，把力气花在「让失败变便宜」

**推荐结论：不要去推导出那个数。把 50 当作保守常数保留，把工程量投在失败半径上。**

### 6.1 为什么推荐这个组合

1. **推导出正确数字的路径已被四条来源堵死**（§4）。继续推导是在猜。
2. **推导出错误数字的代价是灾难性的**。方案 A 直觉上给出「314 张」，
   而已知失败点在 53 张。**用一个已知失效 6 倍的数字去指导行为，比不用数字更危险。**
3. **真正的杠杆已经被本项目自己找到了**（`01-correlation.md`）：
   决定成败的是**分辨率阶梯 + 判定标尺措辞**，不是张数；
   att1 看了更多图（≈447 张）被整局否决，att2 看了更少图（407 张）一次过。
4. **零图片成本的手段已在用**：37 份报告、87 处显式声明「零看图取证法」；
   864 逮住漏战的唯一手段是「删除段语音战斗词扫描」，**图片成本为零**。

### 6.2 三个让失败变便宜的机制（全部已在规则里，缺的只是把它们当成「保险」而非「习惯」）

| 机制 | 效果 | 现状 |
|---|---|---|
| **联系表** | 把「覆盖度」与「张数」两轴解耦：1 张联系表 = N 帧 | 已在 `IMAGE_LIMIT.md §4` |
| **每轮先写核实记录** | 会话作废只损失**一轮**，不损失整个任务 | 已在 `IMAGE_LIMIT.md §16` |
| **疑似即换窗口** | 恢复动作 = 开新窗口，是**已知且便宜**的既定流程 | 已在 `IMAGE_LIMIT.md §5` |

> 三者合起来的效果：**50 这个数字变得不那么重要了。**
> 这才是「不靠人工记住」的真正答案 —— 不是记住一个更准的数，
> 而是让「记错 / 记不准」不再有代价。

### 6.3 若仍想要一条机器可读的规则

**唯一诚实的写法**是把 `limit.input` 当作**上界的上界**，并显式声明它不是约束：

```
预算(模型) = min( 保守常数 , (limit.input − 压缩触发线) / 1500 )
                └─不由 token 决定   └─由 token 决定，但当前取值远大于前者
```

当前模型下： `min(50, 314) = 50`。
换到 `grok-4.7`（`limit` 无 `input` 键，回落 `context=200,000`）：
`(200,000 − 20,000) / 1500 = 120` → `min(50, 120) = 50`。
→ **换模型时这个数不动**，这本身就是结论：**token 不是当前的约束轴。**

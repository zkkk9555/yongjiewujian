# 07 号报告 · 分辨率才是质量杠杆（不是看多少张）

> 范围：只讨论，不动任何文件。结论全部标了出处；凡属推算的，写明推算依据与置信度。
> 上游事实（采信）：864 的 640px 联系表 5/5 路误判；03 号给出 12 列 → 每格 131×74 的技术解释；

## 0. 摘要（三句话）

1. **03 号的技术解释是错的**：864 实际用的是 **4 列**、每格折算后 **392×220**，不是 12 列 / 131×74。
   它引的 `seg9_scan_report.md:4` 那一行是「区间」行，全文没有「640×360」。
2. **但结论更强了**：392×220 这个**实测**值，恰好落在「必读阈值 640–915px」的**下方**，
   而且 864 当时就有扫描员在日志里独立诊断过同一个病。⇒ 分辨率是主因，且现在**可量化**了。
3. **结构性结论**：上游 1568px 封顶下，**格宽 = 1568 ÷ 列数**。要一格达到 960px，**只能 1 列**——
   也就是**任何多格联系表在数学上都不可能承载定性判断**。这不是纪律问题，是算术。

## 2. 一格至少多少像素可读（估算 + 依据）

### 2.1 两级封顶，实际生效的是 1568

| 级 | 值 | 出处 |
|---|---|---|
| 客户端 autoResize | `maxWidth/maxHeight = 2000` | `.scratch\imgbudget2\04-why-50.md:113`（opencode-cli v2.0.22 字节流） |
| 上游 API 长边折算 | **1568px** | 同上 02 号的 token 折算模型，常量 |

折算常数自洽性校验（`03-alternatives.md:170-173` 的三个实测 token 数）：

| 源尺寸 | 折算后 | `(w×h)/750` | 报告实测 |
|---|---|---|---|
| 7680×720 | 1568×147 | 307.2 | **307** ✅ |
| 3840×1440 | 1568×588 | 1229.2 | **1229** ✅ |
| 3840×2160 | 1568×882 | 1843.8 | **1844** ✅ |

三点全中 ⇒ **1568 这个常数可用**（该模型自述精确度 ±30%，但**相对**结论稳）。
**实际送达模型的长边 = min(2000, 1568) = 1568。**

### 2.2 核心定律

```
有效格宽 = min(渲染格宽, 1568 ÷ 列数)
```

**格宽只由列数决定，与你渲染多大无关。** 这是后面所有结论的唯一支点。

### 2.3 特征尺寸与所需格宽

HUD 按 **1280×720** 设计 —— 有硬证据：`adversarial_864_v2_adv4.md:62` 把播报栏裁切坐标写作
「`x 940–1280 / y 455–625`（**1280x720 原生**）」。4K 源 = 3×。

`所需格宽 = 最小可辨渲染像素 × 3840 ÷ 特征在 4K 中的像素`

| 判读特征 | 720p 设计 | 4K 实际 | 最小可辨渲染 | **所需格宽** |
|---|---|---|---|---|
| 敌方红血条（判存在 + 判填充比） | ~8 px 高 | 24 | 4 px | **640 px** |
| 伤害数字「1319」（读出 4 位） | ~18–24 px 字高 | 54–72 | 12 px | **768 px** |
| 击杀播报 / 「攻击提升」横幅文字 | ~14 px | 42 | 10 px | **915 px** |
| 锁定线（判存在） | ~2 px | 6 | 1.5 px | 960 px |

**绑定项 = 横幅文字 915px ⇒ 规格取整：每格 ≥ 960×540。**
这与 `L-044` 已经写死的「960px 单帧复核」**数值一致，但 03 号没给出推导** ——
现在这个数是**可推出来的**，不是拍的。

### 2.4 实测夹逼（独立验证，置信度高）

| 配置 | 折算后每格 | 源自 3840 的线性系数 | 864 当时的实测表现 |
|---|---|---|---|
| 4×4 @480×270 | **392×220** | **0.102** | ❌ `seg8_scan_report.md:11`：「4x4 联系表缩到 1920x1080 后**烧字只有十几像素、极易读错**」，把 `00:09:55` 读成 `00:10:00`（**差 5 秒**） |
| 2×2 @960×540 | **784×441** | 0.204 | ✅ `seg8_scan_report.md:66`：「把 `hd\` 里的 960x540 原图 2×2 拼成 1920x1080（**每格仍是 1:1 原始像素**），一张图看 4 秒」 |
| 单帧 960×540 | 960×540 | 0.250 | ✅ `L-044` 硬规则；seg13 用 3 帧否掉 seg12 提的 [1019,1024] |
| 单帧 1280×720 | 1280×720 | 0.333 | ✅ 无额外图成本 |
| 单帧 2000px（客户端上限） | 2000×1125 | 0.521 | ✅ 天花板 |

**关键点：392×220 处失败的是「烧录的 `h:mm:ss` 大字」**——那是**故意烧大、专门为可读性服务**的字。
伤害数字、横幅文字**比它更小**。
⇒ 392px 连最容易的信号都读不准，定性特征只会更糟。**失败区间被实测钉死在 ≤441px。**

**第一性推算（640/768/915）与实测夹逼（392 失败、784 通过）相互印证，落在同一区间。**

## 3. 算一笔账：40 个判断点，三个方案要多少张图

### 3.1 先解决 06 号的批评：「需要多少图」不能是猜的

06 号对：134 路看图量是用正则从 md 里猜的。**但判断点数不需要猜 —— 它在时间线 JSON 里，是可数的。**

```
N_pts = 2 × len(combat_episodes)          # 每场 头边界 + 尾边界
      + len(deleted_intervals)            # 顶层删除段
      + Σ len(ep.deleted_inside)          # 场内挖洞
```

实测 `docs\lessons\archive\864-rejected-attempt\timeline\combat_episodes_v*.json`：

| 版本 | episodes | deleted_intervals | deleted_inside | **N_pts** |
|---|---|---|---|---|
| v1（首版） | 11 | 16 | 0 | **38** |
| v2 | 11 | 11 | 0 | 33 |
| v3 | 11 | 11 | 0 | 33 |
| v4 | 11 | 11 | 0 | 33 |
| v5 | 11 | 11 | 0 | 33 |
| v6（终版） | **7** | **8** | 0 | **22** |

**任务书里的「约 40」= 实测 38。** 数字对得上，而且现在**有出处、有算法**。

顺带一个更狠的数：**v1 → v6 有 16 个判断点被推翻 = 42%**
（= 4 场 × 2 边界 + 8 个 deleted_intervals，账正好对平）。
**这就是「用 392×220 判读」的可测缺陷率，而且它是从 JSON 数出来的，不是从散文里猜的。**

> 注：864 时间线 `deleted_inside` 全为 0 —— 这正是 AGENTS.md §8.1「一整场完整战斗」那条规则要治的病。

### 3.2 四个方案，按 38 个判断点

| 方案 | 每点图数 | **总图数** | 轮次(@10/轮) | 有效格宽 | 实测质量 |
|---|---|---|---|---|---|
| **A. 4×4@480 联系表**（864 实际跑法） | 1/16 点 | **3** | 1 | **392×220** | ❌ **42% 判断被推翻** |
| **B. 960×540 单帧/点** | 1 | **38** | 4 | 960×540 | ✅ 已验证 |
| **C. 1280×720 单帧/点** | 1 | **38** | 4 | 1280×720 | ✅ **与 B 同价** |
| D. 联系表普查 + 960px 只定性 | 1/16 + 1 | 3 + 38 = **41** | 5 | 混合 | 联系表不能定性，定性仍是 38 |

### 3.3 三条从账里直接读出来的结论

1. **B 与 C 总图数完全相同（38 = 38）。** 「960 还是 1280」是个**假权衡**——
   **分辨率在图数记账上是免费的**。没有任何预算理由偏好 960。
2. **A 最省图（3 张）却最差。** 它把 38 个真问题压成 3 张图，代价是 42% 的判断错。
   **这是「省图」这个目标函数的直接反噬。**
3. **864 实际烧掉的不是 3 张。** `01-correlation.md` / `04-why-50.md:318` 实测：
   att1 为了同样这 38 个问题**看了 ≈447 张，整局被否决**；att2 看 407 张一次过。
   ⇒ **正确答案（38 张）比实际做法（447 张）少一个数量级，而且结论还是对的。**

**所以这条分辨率下限不是「多花钱买质量」，它是「把钱从错的地方挪到对的地方」。总花费是降的。**

### 4.4 联系表的正确定位（按第 2 节的算术）

```
最大列数 = floor(1568 / 960) = 1
```

⇒ **多格联系表与「定性判读」在数学上互斥。** 不是不该用，是**做不到**。

| 用途 | 正确规格 | 每格有效 |
|---|---|---|
| **粗筛**（有没有人 / 有没有大面板 / 场景有没有切） | 4 列 × 480×270，16 格/表 | 392×220 —— **够用** |
| **定性**（是战斗还是舔包 / 边界在哪一秒） | **1 格 1 图，≥960×540** | 960×540 |

- 联系表**保留**，但它的职责收窄为**定位**：回答「第 N 秒有没有异常」，不回答「这是什么」。
- 拼表脚本应**打印折算后每格像素**，并在列数 > 4 时给 `[WARN]`（注意：**不是 03 号的 6**）。

## 5. 关键判断：预算该约束什么

### 5.1 推荐：约束「证据」，不是约束「张数」

设**两本账**，只动其中一本：

| 账 | 内容 | 处置 |
|---|---|---|
| **R1 预算机制** | 单次请求累计 ≤50、单轮新增 ≤10，由 `check_image_budget.ps1` 记账 | **完全不动** |
| **R2 取证分辨率下限** | 每条定性主张（边界 / 删除 / 事件类型）必须引用 **≥1 张有效格宽 ≥960×540 的帧** | **新增** |

**R2 的性质**：它约束的是**一张图里必须有什么**，与已有的「§5 禁烧录禁内嵌字幕」**完全同类**——
那也是对图像内容的约束，不是对张数的约束。它应该以**引用有效性**的形式进 QA
（`qa_gate.py` 里一条 `evidence_frame_legible`），而不是进预算脚本。

### 5.2 为什么 R1 是错的杠杆

`01-correlation.md`：134 路里红线**最高只用到 45/50，从未被逼近**。
⇒ **50 从来不是绑定约束。** 绑定的是「把图花在哪儿」。
**动张数上限 = 解决一个不存在的问题；动分辨率下限 = 解决真问题。**

### 5.3 依据（可复核）

| 证据 | 内容 |
|---|---|
| `seg8:11` | 392×220 处，**故意烧大的**时间戳都读错 5 秒 |
| `04-why-50.md:318` | **张数多的那次输了**：att1 ≈447 张被整局否决，att2 407 张一次过 |
| `04-why-50.md:319` | **修正误判的边际成本极低**：seg12 的删除候选被 seg13 用 **3 张 960px** 否掉 |
| `01-correlation.md` | 134 路最高 45/50 —— 红线从未绑定 |

## 6. 诚实说明：这算不算改预算机制

### 6.1 结论：**不算。** 这是两件事，必须分开说

| | 预算机制 | 取证分辨率规格 |
|---|---|---|
| 管什么 | 一次请求能带几张、怎么记账、封顶值 | **一张图必须长什么样** |
| R2 改了没有 | **一项都没改** | **改这个** |
| 38 个判断点要几张图 | 改前 38，改后 **38** | — |
| 轮次 | 改前 4，改后 **4** | — |
| 50 / 10 两条红线 | **原样** | — |
| 先例 | — | AGENTS.md §5「禁烧录禁内嵌」= 同类约束 |

### 6.2 三种情况下它**才会**变成改预算（本次都不是）

1. 顺带放宽 50 / 10 —— **不提议**。
2. 把「16 格表」重新定义成「更便宜」 —— **不提议**。
3. 以「看清要 38 张、超预算」为理由去要第 51 张 —— **这才是改预算**，本报告不主张。

### 6.3 必须承认的一点（不藏）

分辨率下限**确实会改变「预期消耗量」**：一个靠拼表跑完的流程，
从「3 张表」变成「38 张帧」。**所以图数会动。**

但要分清两句话：

- **「会花多少图」变了** —— 是的。
- **「预算机制」变了** —— 没有。记账单位、封顶值、每轮增量都没动。

而且净消耗是**降**的：同样这 38 个问题，864 实测烧了 ≈447 张、结论 42% 错；
按 R2 走是 38 张、结论应当一次对。
**R2 降低总花费，只是把钱从「拼表」挪到「决定性帧」。**

### 6.4 一句话表述（建议直接采用）

> **改的是「一张图必须长什么样」，不是「一次能带几张图」。**
> 前者属取证规格，后者属预算机制。**R2 不动 50 / 10，也不改记账。**

## 7. 怎么把「需要多少图」变成可测量的（回应 06 号）

两条**只增不改**的脚本增强（`Cap` / `PerRoundNew` 一律不动）：

**(a) `check_image_budget.ps1` 加尺寸感知**
目前 69 行全是 `Get-ChildItem` 计数。增：读每个图的宽高 + 列数，打印

```
eff_cell = min(rendered_w, 1568/cols) x min(rendered_h, 1568/rows)
[FLOOR VIOLATION] a_04.jpg  eff_cell 392x220 < 960  ← 不可用于定性
```

**(b) `check_image_budget.ps1` 加 `-Timeline <json>`**
直接从 `timeline\combat_episodes_vN.json` 算

```
N_pts = 2*len(combat_episodes) + len(deleted_intervals) + Σ len(deleted_inside)
→ required readable frames = N_pts          (864 实测 v1=38, v6=22)
→ rounds = ceil(N_pts / PerRoundNew)        (38 → 4 轮)
```

⇒ 「要多少图」从此**由时间线 JSON 推导**，不再由正则猜散文。
（这同时让 06 号对「134 路」的批评失效：那个数本就不该从 md 数。）

## 0. 三句话结论

1. **50 没有任何原始证据。全库 36,547 条会话消息里，唯一一处"50 从哪来"的第一手陈述是用户本人的回忆，
   而同一句话自带免责声明「其实我也不知道这个预算到底是多少了」。** 项目把它升格成了
   「无论使用什么模型……都是 50 张」，并另写一条条款禁止以后再把它改回「某个模型的限制」。
2. **它永远用不到上限，不是因为需求小，是因为工作单元比预算单元小。** 本单实测：
   **542 个读图会话里 537 个（99.1%）是子 Agent**；红线按「会话」计，工作流按「路」计，
   一路只负责 85 秒源。同一份 1152 秒素材，**任务层要 407 张图，但任何单个会话最多只承担 50 张**。
   **50 是流程的产物被误读成了流程的约束。**
3. **它是「没有被验证的安全」，但危险那一面更真**——因为**实测峰值恰好 = 50 = 红线本身**，
   且真正会咬人的那条限制（`auto_resize` 把 >2000px 的图缩掉、单张 5 MB 上限）**50 一个字都没提**。

## 1. 考古：50 是怎么来的

### 1.1 全库唯一的第一手陈述，是用户自己说的（2026-10-05，会话 `ses_f16498506ffedrgwnWeoUrw4tJ`）

我把「网关限制得不太好」当关键词扫了全库文本 + 36,547 条会话消息。**仓内 0 命中；会话库里只有 1 处命中，
而且它是一条 user 消息**（时间戳 `1791084956621`）：

> 「2. 评估看图预算的必要性与否
> 另外，关于这个"看图预算"的限制，其实是因为我之前的模型有 50 张的上限，当时网关限制得不太好，
> 所以在这个项目里会有这个限制。但是现在我换成了其他的网关和其他的模型，
> **其实我也不知道这个预算到底是多少了。**
> 我也不知道保留这个看图预算还有没有什么意义，因为感觉它好像降低了剪辑的效率。」

三点必须说清：

| # | 事实 | 依据 |
|---|---|---|
| a | 出处是**记忆**，不是引文 | 这句里没有网关文档 ID、没有配额页、没有 provider 声明、没有日期、没有错误原文 |
| b | 这句**自己声明了不知道真值** | 「其实我也不知道这个预算到底是多少了」——所以它是"我印象里卡过"，不是"我验证过是 50" |
| c | 它**只声称"某一个旧模型"**，规则文本把它扩成了"所有模型" | 原文「我之前的模型」→ `IMAGE_LIMIT.md:3`「无论使用什么模型……都是 50 张」 |

### 1.2 项目加上去的那一步，才是这条规则变成公理的地方

原始素材是**一个模型的一次经历**。项目把它做成了三件事：

1. **升格为模型无关的定律**：`IMAGE_LIMIT.md:3` / `AGENTS.md §9`「无论使用什么模型（含 `muse-spark-1.3-contributor-free`
   及任何后续模型），上游单次请求携带的图片总数上限**都是 50 张**」。
2. **写入焊死条款**（`IMAGE_LIMIT.md:21` / `AGENTS.md §9`）：
   > 「本条与模型名称无关：即使上游模型更换，50 张红线仍然有效；
   > **任何文档不得将其写成仅适用于某一模型的临时限制**；如有冲突以 50 张上限为准。」

   这是全项目**唯一一条自带「不许复核我」的条款**。它把一条关于 A 的记忆焊成了关于一切的公理，
   并**关闭了重新评估的入口**。
3. **用它正当化文档重复**（`docs/粗剪提示词.md:21`，设计原则第 4 条）：
   > 「**唯一允许的重复是看图上限。** 因为违反它不是报错，是整个会话报废，代价太大，值得付这点重复成本。」

   即：**8 处副本的成本，是用一个未证实的威胁勒索出来的。**

| `sess_fd6d3012` | 26 | 10 | 12 | 2 | 同上 |
| `sess_47c354c9` | 26 | 10 | 12 | 2 | 同上 |

  → 规则文本连同它的工具名，是从**另一个 harness** 搬来的。

### 1.5 唯一一条**独立于事故**、且我能实测的真约束（这是本单的新发现）

我从 `opencode-cli.exe` v2.0.22 字节流里读出了 @opencode/Image 的**真实**配置（原文）：

```js
initial: () => ({ autoResize: true, maxWidth: 2000, maxHeight: 2000, maxBase64Bytes: 5242880 })
// 描述串：
//   "Maximum image width before resizing or rejecting the attachment (default: 2000)"
//   "Maximum base64 payload bytes for an image attachment (default: 5242880)"
class OT ... `Image ${resource} is ${w}x${h} with base64 size ${bytes},
              exceeding configured limits ${maxWidth}x${maxHeight}/${maxBytes} bytes`
```

同时全串检索的结果：

| 检索项 | 命中 | 含义 |
|---|---|---|
| `maxImages` | 3 | 唯一实现在 **Venice 图像生成 SDK**（`maxImagesPerCall=10` / `Number.MAX_SAFE_INTEGER`），与读图无关 |
| `max_images` / `imageLimit` / `attachment_count` | **0** | 客户端**没有任何按张数拒绝图片的分支** |
| `too many image` | **0** | 不存在这种错误 |
| `payload-too-large` / `request_too_large` / `entity too large` | 4 / 3 / 2 | 存在，但按**字节**分类，且带降级重试路径 |

**结论：客户端真实存在的图片约束是「单张」的，不是「每次请求多少张」的。**

> **⚠ 顺带一条对本项目用词的事实纠正（不是指责，是精度问题）**
> 864 的成功经验里写着「命中即回看 **4K 帧**」。但 `autoResize` 默认开、`maxWidth/maxHeight = 2000`，
> 所以一张 3840×2160 的 4K 帧**在进模型之前就被缩到 2000×1125**。
> 「4K 复核」在模型侧实际是 2000px 复核——而 2000px 与 960px 的差别，远小于 960px 与 640px 联系表的差别。
> 这不影响 960px 铁律的有效性（它依然远高于联系表），但**项目文档里没有一处提到这条 2000px 天花板**。

## 2. 为什么它永远用不到上限：**工作单元比预算单元小**

### 2.1 决定性实测：99.1% 的读图发生在子 Agent 会话里

| 指标 | 值 |
|---|---|
| 读图会话总数 | **542** |
| 其中**子 Agent**（`parent_id` 非空） | **537（99.1%）** |
| 单条消息最多图片 | **10** |
| 单会话累计最多图片 | **50** |

**看图量最高的 20 个会话，20 个全是子 Agent，全部 `succeeded`：**

```
cnt=50 | parent=YES | succeeded | 2026-09-29 10:25 | Scan seg8 [595,685)
cnt=49 | parent=YES | succeeded | 2026-09-30 06:44 | Self-audit v1 four passes
cnt=48 | parent=YES | succeeded | 2026-09-28 23:10 | Resolve seg4 seg5 conflict
cnt=46 | parent=YES | succeeded | 2026-09-30 04:58 | Re-audit oversized deletions
cnt=45 | parent=YES | succeeded | 2026-09-28 23:07 | Verify episode heads 001-010
...（前 20 名 parent 全为 YES，outcome 全为 succeeded）
```

**主会话几乎不读图；指挥只派工、收报告、合并。**（`e4_parallel_throughput.md:85` 原文：
「指挥下发后立即写台账 20 行 `已派未回`，然后收手等待，**不做任何看图与渲染**」。）

### 2.2 一路的工作量 = 85 秒源，不是整局

864（att2，交付那次）实测：1152.233 s ÷ 85 s/路 + 5 s 重叠 = **14 路**，
14 路**全部申报**，合计 **407 张**（23/22/44/23/25/29/30/17/35/31/35/35/36/22，`dispatch_ledger.md`）。

```
任务层需求：  407 张
单个会话上限：50 张
单个会话实际：14 路 × ≈29 张

⇒ 要让任何一个会话单独用满 50，它得独自承担一整局 1152 秒；
  而流程设计上它只负责 85 秒。
```

**这就是答案：不是"没人想看那么多图"，是没有任何一个会话有机会看那么多图。**
把 14 段拼进一个会话（≈407 张）当然会爆——但流程从不这么干，因为**并行扇出既是吞吐设计，也是天然的预算隔离器**。

### 2.3 还有三层解耦，任意一层单独存在都足以让 50 够不上

| # | 解耦层 | 机制 | 实证 |
|---|---|---|---|
| 1 | **抽稀** | ffmpeg 先出 1/10fps、1fps 底帧，帧数与读图数不是同一个量 | 861 全片 1fps = 2,399 帧，只读 29 张；864：1,237 帧 → 407 张 |
| 2 | **拼表** | 一张联系表 = 12/24 帧，**1 张图** | 863：560 帧 → 28 张表，20×；864：1237 帧 → 108 张表 |
| 3 | **零看图取证** | 语音战斗词、luma/YAVG 探针、MD5、scene-detect、HUD 读数 | 37 份报告 / 87 处显式声明「零看图预算」；**864 逮住漏战的唯一手段是删除段语音战斗词扫描（POOL L-014）** |

再加一个**官方泄压阀**（`e4_parallel_throughput.md:133`）：

> 「派新路 `segNb`：新 prompt 写明 `resume_from = <断点源秒>` + 已有证据绝对路径；
> 新路复用证据、不复看已看图（**预算从 0 起算，旧图不计入新路累计**）。」

⇒ 预算**可以重置**，不是一次性资源。卡住的路换条路继续，而不是硬撑到爆。

### 2.4 分布形状证明：50 根本没进过决策

我自己复算的逐会话累计分布（542 会话 / 10,875 张，与 03 号独立复算完全一致）：

| 累计张数 | 会话数 | | 累计张数 | 会话数 |
|---|---|---|---|---|
| 1–5 | 9 | | 36–40 | 20 |
| 6–10 | 87 | | 41–45 | 15 |
| 11–15 | 100 | | 46–48 | 2 |
| **16–20** | **111（峰值）** | | 49–50 | 2 |
| 21–25 | 94 | | **≥51** | **0** |
| 26–30 | 56 | | | |
| 31–35 | 46 | | | |

**这是一条钟形曲线，不是"贴着天花板的一条平顶"。** 峰值在 16–25，中位数约 20。

各路停下来的时候，原因写在报告里，**不是"预算不够"**：

| 实例 | 原文 |
|---|---|
| `adversarial_19_v3_adv6` | 抽了 **1,075 帧**，只读 **26 张**就结案 |
| `adversarial_864_v1_adv4` | 预跑预算脚本花了 **0 张**，输出 `RoundsNeeded 7`，然后全路只用了 **15 张** |

### 2.5 最干净的一条发现：**50 = 5 × 10，它是被 ≤10/轮 定义掉的**

实测：累计 ≥46 的 4 个会话是 50 / 49 / 48 / 46 —— **每一个都恰好需要 5 轮**（`ceil(n/10) = 5`）。

```
≤10 张/轮（纪律） × 5 轮 = 50 张（红线）
```

**50 在实践中从来没有独立地约束过任何东西**——真正在起作用的是 ≤10/轮，
而 50 只是这条纪律跑满 5 轮的算术副产品。（`image-limit-enforce/NOTES.md` 记载：选 ≤10 的理由是
「locking the top at 10 keeps **5x safety margin under 50**」——先有 50，再有 10；但两者的关系是 5×10，
这让「50 是被观测出来的」这个可能性无法排除。）

### 2.6 本节结论

> **这条规则是在流程建好之后才被贴上去的标签。**
> 流程的四个设计选择——**扇出、每路 85 秒、抽稀/拼表/数值探针、每路独立预算**——
> 任意一个单独存在，都足以让 50 够不上限；四个同时存在，50 就永远够不上。
>
> **它描述的是流程的输出，不是流程的输入。**

## 3. 如果明天突然生效：**没有被验证的安全**，且危险那面更真

### 3.1 判定与依据

| # | 依据 | 数字 |
|---|---|---|
| 1 | **余量为零。** 观测峰值 = 50 = 红线本身。这不是"离上限还很远"，这是"正好站在线上" | 峰值 50；≥45 的 **7** 个；≥46 的 **4** 个 |
| 2 | **分布是被数字塑形的，不是被天花板塑形的**（自指） | 50 这个数在每份报告、每份派工单里都被抄一遍。**没有任何一个观测点能区分「我们守住了天花板」和「我们照着一个数字行事」** |
| 3 | 对"真上限比 50 低"这个方向，**零保护** | 见 §3.2 反事实表 |
| 4 | 它宣称的失败形态**在本 harness 里没有实现** | 客户端无张数闸（§1.5） |
| 5 | 而唯一**真的会拒绝图片**的那条闸，规则一个字没提 | `maxWidth/Height 2000` + `max_base64_bytes 5 MB` |

### 3.2 反事实：如果真上限在别处，会死多少（这是我最想让你看的一张表）

```
若真实每请求上限 = N，历史上会越线的会话数（542 个读图会话 / 10,875 张）
  cap= 30 ->   85 / 542 (15.7%)   3,096 张处于风险中
  cap= 35 ->   39 / 542 ( 7.2%)   1,596 张
  cap= 40 ->   19 / 542 ( 3.5%)     843 张
  cap= 45 ->    4 / 542 ( 0.7%)     193 张
  cap= 50 ->    0 / 542 ( 0.0%)       0 张
```

**如果真上限是 30 或 35（都在 token 预算完全够得着的范围内），今天这套工作流已经死了 7%–16% 的会话，
而 50 这条规则一点忙都帮不上。** 它只对"真上限恰好 = 50"这一个点有效，而那正是它自称的那个点。

### 3.3 它给的保护是**假绿灯**，不是没有

`scripts\check_image_budget.ps1`（我读了全文，69 行）：

| 情形 | 脚本行为 |
|---|---|
| 盘上张数 > Cap | 打 `[PLAN]`，**`exit 0`**（L59–63） |
| `-Cap 500` | 照常 `[PASS]`——**50 是命令行默认值，不是硬编码**（L6） |
| `Get-ChildItem` 无 `-Recurse`（L18） | 子目录的帧一张都不数 → 报 `[PASS]` |
| 真的去 `Read` 超额图片 | **完全不介入** |

**"违例"的实测后果（本项目自己的记录）**：
`adversarial_864_v3_adv3.md:358` —— 「它只扫目录根的 `*.jpg`，我的帧在子目录，故报 `TotalOnDisk: 0`」。
⇒ **预算工具给出了一个"0 张预算"的绿灯。** 真出事那天，它给的就是这个。

### 3.4 真正的风险不在 50，在两个地方

1. **`auto_resize` + `maxWidth/maxHeight = 2000`**（§1.5）：所有 >2000px 的图被静默缩小。
   864 的"4K 复核"实际是 2000px。这是**正在发生、静默、不可逆**的信息损失，且直接打在"HUD 小字"上——
   **正是 864 误判的那一类**。
2. **471,860 的自动压缩悬崖**：逼近时会把帧换成文字摘要。02 号已从二进制里读出该算法。

> **两条都不在 50 的射程里。规则守着一个不存在的敌人，同时对真敌人完全沉默。**

### 3.5 本节一句话

> **50 不是"没被验证的安全"，是"没被验证的运气"——而且这份运气正在被当成安全。**
> 更准确地说：它**现在无害**（强制力为零，拦不住任何东西），

### 4.3 判定：真正的病灶是**记账单位选错了**

03 号的算术已经算清了，这里只做推论：

| 记账 | 实际成本 | 承载的信息 |
|---|---|---|
| 1 张 12 列 × 640×360 联系表 | **307 tok** = 每格 **12.8 tok**（上游 1568px 折算后每格仅 **131×74**） | **0** —— HUD 小字在 74px 高的格子里**物理上不存在** |
| 1 张 960×540 单帧 | 691 tok | 全部 |

**一张 24 格表和一张 960px 单帧，在预算账本上都记「1 张」。**
⇒ **"超 10 帧优先拼联系表"这条由预算派生出的方法偏好，被账本系统性地补贴了**——
它让"省图"在任何记账口径下都显得更划算，而省图恰恰抹掉了定性所需的信息。

**所以对你的问题「预算会不会成为提高质量的障碍」的诚实回答是：**

> **「因为怕超预算所以不敢多看」这个担心，方向反了。**
> 真正贵的不是多看，是**看不清**；而 50 从来没有限制过看不清——它限制的（张数）
> 和出错的（每格像素）是两个不同的量纲，而账本只看得见前者。
>
> **50 这个数不是障碍。「超 10 帧优先拼联系表」这个由它派生出的方法偏好才是障碍**，
> 而那一句话**恰好不在"改 50"的射程内**——它是 `AGENTS.md §9` 第 4 步。
> 已被实证的替代品已经在规则里了：`L-044`（候选删除段必须 960px 单帧复核）。
> **它只差一句「联系表列数 ≤6（每格 ≥261px）」——`03-alternatives.md §3.2` 建议过，项目至今没加。**

## 5. 「不动」的两条逻辑：为什么它们导向相反的结论

### 逻辑 A：「无害，所以不动」

- **它给谁定价**：`50` 这个数字。
- **前提**：改动成本 > 改动收益。
- **证据**：
  - 强制力为零（脚本只打印，超 Cap 仍 `exit 0`），所以"不动"不会带来任何额外风险；
  - 0/542 会话触顶、0 次 provider 图片错误 ⇒ 它的**保护价值实测为 0**；
  - 但纪律本身有效：542 个会话全部逐路记账、零超限、单消息峰值恰好 10 = 纪律上限；
  - `AGENTS.md §9` 是**唯一被自动注入的防绕过层**（09 号 §5.1 实测）——动它风险 > 收益；
  - 放宽到 200 买不到任何现在没被需要的东西（01 号 §3.1 边际张数需求 = 0）；若真用满，时间 **+42%**。
- **结论**：**数字不动。**

### 逻辑 B：「无害**且无用**，所以更该动」

- **它给谁定价**：「围绕这个数字的整套教义」——不只是那个数。
- **前提**：规则价值 = 防住的 − 造成的；**「零收益 + 有成本」是负价值，不是零价值**。
- **证据**：
  1. 零收益：出处是记忆不是引文；5/5 会话 ID 不存在；496 次引用里事故记录 0 条；
     伤亡数自相矛盾（`粗剪提示词.md:131` 说「两个」，`50-hardline/spec.md:13` 点名 4 个）；
     全库 provider 错误去重后 4 种，**无一涉及图片**。
  2. 有成本，而且**已经付过了**（§4.1 的 A/B/C/C'）。
  3. **维护负债已经开始漂移**：9 处副本；`README.md:18` 现在就写着**错的**「单轮 50 张封顶」
     （正好是它自己声称的失败形态）；`roughcut-launch.md:90` 是不完整副本；861 私自发明了第三个数 **40**。
  4. **它关闭了重新评估的入口**：`任何文档不得将其写成仅适用于某一模型的临时限制`。
     全项目只有这一条规则自带"不许复核我"。
- **结论**：**动。** 而且动的对象不是数字，是**那句焊死的条款**和 8 处副本里那句没有出处的断言。

### 它们为什么导向相反结论

**因为它们在给不同的东西定价，而「要不要动」这个问题没有指定动什么：**

| 问题 | 谁对 |
|---|---|
| 「50 改成 200 划不划算？」 | **逻辑 A** — 不划算，不动 |
| 「这条规则该不该继续以物理定律的身份留在项目里？」 | **逻辑 B** — 不该，必须动 |

**二者共享同一个前提：「零触发 = 无害」。而这个前提正是本单要推翻的那一条。**
观测峰值 = 50 = 红线本身，说明我们不是"离上限还很远"，而是**正好站在线上，且不知道线上有没有线**。
零触发不是"它保护了我们"，也可能是"它保护的是一个不存在的东西，所以永远不会被触发"。

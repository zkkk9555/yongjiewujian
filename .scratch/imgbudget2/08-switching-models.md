# 08 · 换模型时怎么办

> **范围**：只讨论，未修改任何项目文件、脚本、配置或任务目录。新增文件仅此一份。
> **采信**：01–07 号已确认的事实。**本单新增的取证**（可复核，脚本在 `%TEMP%\opencode\q*.py`）：
> 从 `opencode-cli.exe` v2.0.22 字节流里读出压缩算法原文；从 `opencode.db`（15 GB，659 个会话）
> 里逐条解析出每张图的真实像素、每条请求的真实上下文占用。

## 0. 摘要

用户的原话是：「我感觉每一个模型其实都不太一样。现在的理论也是建立在当前这个模型上的，换一个还是不太行。」

**这句话一半是对的，一半可以被证伪。**

- **对的一半**：换模型确实会改变**一个**量 —— 压缩线。而它正是 07 号说的「不可逆伤证据」的那条线。
- **可证伪的一半**：「理论建立在当前模型上」这个说法，**在张数这一维上不成立**。
  本项目读过的 **10,778 张图，全部由客户端按同一套规则处理，与模型无关**。
  模型在这条链路上唯一的作用是提供一个 token 上限数字。

> **本单的核心结论（一句话）**：
> **与模型无关的锚不是「token 占比」，是「有效格宽」（每格多少像素）。**
> 因为模型换掉之后，唯一会变的是「能塞多少 token」，
> 而**唯一不会变的是「一张图能承载多少可判读信息」—— 那由 1568px 折算和客户端 2000px 封顶决定，两者都在模型之上。**

## 1. 换模型时，到底会变的是什么

我把客户端里跟图片沾边的每一条逻辑都读了出来，逐项判定「会不会随模型变」。

### 1.1 逐项判定表

| # | 量 | 现在的值 | 换模型会变吗 | 判定依据 |
|---|---|---|---|---|
| 1 | **图片张数上限** | **不存在** | **不会变（因为它不存在）** | 全二进制搜 `too many image` / `max_images` / `image limit` / `exceeds.{0,20}image` = **0 命中**。`maxImagesPerCall=10` 存在于二进制，但属于**图像生成** provider 规范（`_0` class），与读图无关 |
| 2 | **单图尺寸上限** | 2000×2000 px，5 MB base64 | **不会变** | `Image` 命名空间：`{autoResize:!0, maxWidth:2000, maxHeight:2000, maxBase64Bytes:5242880}`。**这是客户端配置，与模型无接口**（`Config.Media.Image` 只有 4 个字段，没有 model 字段） |
| 3 | **图片 token 折算** | 客户端用**固定 1500/张** | **不会变** | `P6=(e)=>{if(e.startsWith("image/"))return Gj /*1500*/; ...}`。**只按 mime 判定，完全不看像素** |
| 4 | **压缩触发线** | **471,860** | **会变 —— 而且是唯一会变的** | 见 §1.2，算法原文已读出 |
| 5 | 失败是硬失败非静默降级 | 是 | **不会变** | 见 §1.4 |
| 6 | 单条消息带图峰值 | 10 | 与模型无关（这是**我们自己**的纪律，不是约束） | 全库 7,993 条带图消息，**峰值恰好 10，一条都没超过** |
| 7 | 上游把长边折到 1568 | 是 | **不会变**（这是网关/上游的协议行为，不是模型属性） | 见 §1.3 的实测反证 |

### 1.2 第 4 项：压缩线的完整算法（这是唯一的真变量）

从字节流里读出的原文（`SessionCompaction` 段）：

```js
F6 = 16000                                  // 缓冲地板
N6 = (limit, buffer) => {
  let i = limit.input || limit.context;
  if (i <= 0) return Number.POSITIVE_INFINITY;
  if (buffer !== undefined) return i - buffer;
  return i - Math.max(Math.floor(i * 0.1), i >= 2*F6 ? F6 : 0);
};
```

代入当前模型：

```
524,288 - max(floor(524288 × 0.1), 16000)
       = 524,288 - max(52,428, 16,000)
       = 524,288 - 52,428
       = 471,860          ← 与 02/05 号读出的数字逐位吻合，算法首次得到确认
```

**这条线的三个性质**：

1. **它是模型上限的一个固定比例（90%）**，不是常数。换模型它就等比缩放。
2. **同网关的其它档位**（成本表里带 `context` tier 的几个）：

   | 模型 | 上限 | 压缩线 | 相对现在 |
   |---|---|---|---|
   | **space-bunny-free（现在）** | 524,288 | **471,860** | — |
   | minimax-m3 | 512,000 | 460,800 | −11,060（几乎无差） |
   | gpt-6-luna | 272,000 | 244,800 | **−227,060** |
   | qwen3.7-plus | 256,000 | 230,400 | −241,460 |
   | grok-4.7 | 200,000 | 180,000 | **−291,860** |
   | longcat-2.5-preview-free | 200,000 | 180,000 | −291,860 |
   | *客户端兜底* `bj` | *200,000* | *180,000* | **元数据缺失时按 200K 算** |

3. **兜底值是 200,000**（`bj=200000`）。这意味着**只要网关没报上限，客户端就按 200K 算压缩线 = 180,000**。
   比现在的 471,860 低 **2.6 倍**。这是一个**真实的降级风险**，而且用户不会收到任何提示。

### 1.3 第 7 项：1568 折算是模型之上的（实测反证）

07 号把 1568 当成「上游 API 的折算常数」。这一点需要区分：**1568 是网关的行为，不是模型的行为。**

实测反证（本单新增）：**10,778 张图里，49.69% 的长边 ≥ 2000px，p90 = 2000，p99 = 2000，最大值恰好 2000。**

```
长边分布（客户端落库前的真实尺寸）：
  ≥2000      5,356 张  49.69%   ← 全部被客户端 autoResize 削到 2000
  1568–1999  2,422 张  22.47%
  1000–1567  1,573 张  14.59%
  500–999    1,424 张  13.21%
```

**含义**：客户端先削到 2000，上游再折到 1568。**两级封顶叠加，且两级都在模型之上。**
换模型最多影响第二级（如果新网关用别的常数），但**第一级的 2000px 削图完全不变** ——
而第一级已经吃掉了近一半的图。

> **一个立刻可用的推论**：文档里写的「4K 复核」在模型侧从来就是 2000px 复核。
> 这一条**与选哪个模型无关**，是客户端写死的默认值。

### 1.4 第 5 项：「硬失败非静默降级」这条会不会变

**不会变，而且现在有了比之前更强的证据。**

| 层 | 机制 | 性质 |
|---|---|---|
| 客户端 | 图片超限 → `Image.SizeError`，**抛异常，不静默** | 硬失败 |
| 客户端 | 图片过多 → **无此分支**（0 命中） | — |
| 客户端 | 压缩触发 → 写一条 `type=compaction` 消息，**不报错** | 显式降级，可审计 |
| 上游 | 超限 → HTTP 413 / `context_length_exceeded` / `payload-too-large` | 硬失败 |

**全库 50 条错误消息，逐条分类**：

| 次数 | 错误 | 与图片的关系 |
|---|---|---|
| 38 | `provider.invalid-output: OpenAI Chat stream ended without finish_reason`（HTTP 200） | 无关 |
| 8 | `aborted: Step interrupted` | 无关 |
| 3 | `provider.internal: [api_error] internal server error` | 无关 |
| 1 | `provider.internal: Endpoint is unavailable`（HTTP 500） | 无关 |

**涉及 image / media / vision / attachment 的错误：0 条。**

> **这条不但不会随模型变，而且它本身就是「张数不是约束轴」的证明**：
> 如果上游有张数上限，它必然以某种错误形式出现过。它一次都没出现。

## 2. 有没有一个与模型无关的量，可以当锚

### 2.1 四个候选，逐个打分

| 候选 | 与模型无关？ | 实测稳定性 | 判定 |
|---|---|---|---|
| **A. token 占比**（50 张 ≈ 14.3%） | ❌ **会变**，且是唯一会变的 | 上游折算常数不确定（§3.2） | **不能当锚** |
| **B. 单图尺寸**（2000px） | ✅ 完全无关（客户端配置） | p90 = p99 = 2000，**零离散** | ✅ **是最稳的，但它只管住上限，不管住工作量** |
| **C. 单轮张数**（≤10） | ✅ 无关（我们自己的纪律） | 7,993 条消息峰值恰好 10，**零违规** | ✅ 稳，但它是**流程产物**不是**物理约束** |
| **D. 项目自己的工作量**（19 分钟素材 38 张判断点） | ✅ 完全无关 | 从时间线 JSON **可数**（07 号 §3.1） | ✅ **最稳，且是唯一能自动算出来的** |

### 2.2 为什么 token 占比是最差的那个锚（这是本单最重要的判断之一）

用户的顾虑是「理论建立在当前模型上」。**token 占比恰恰是建立在当前模型上的那个量。** 三重不可移植：

1. **它挂在模型上限上**（§1.2）——换模型直接失效。
2. **它挂在图片折算上**（§1.1 第 3 项）—— 客户端写死 1500，**不看像素**。
3. **那 1500 本身不准。** 本单用真实像素复算了 10,778 张图：

   | 口径 | 均值 | 中位 | 最小 | 最大 |
   |---|---|---|---|---|
   | 像素公式（1568 折算后 `w×h/750`） | **1,511** | 1,384 | 5 | 3,278 |
   | 客户端常数 | 1,500 | — | — | — |
   | **真实上下文增量实测**（302 个 ≥3 张的样本） | **1,158** | 789 | 117 | 2,777 |

   - 像素公式与实测的比值 = **0.85**（说明公式方向对，量级对）。
   - 客户端的 1500 **高估约 30%**（1500 / 1158）。

   **一个高估 30% 的常数，被用来推导「314 张」。** 314 这个数从一开始就不该被当真。

> **更要命的是：单张图的 token 成本在本项目里跨度是 5 → 3,278，659 倍。**
> 也就是说「张数」这个单位**本身**就不是一个齐次的量 ——
> 10 张 960×540 联系表和 10 张 4K 复核帧，在 token 账本上不是一回事。
> **用一个跨度 659 倍的量去卡上限，等于没有上限。**

### 2.3 那到底哪个最稳？

**答案是 B 和 D 的组合，不选 A。**

理由：B（单图尺寸）物理上最稳，但它只能回答「一张图最多带多少信息」，
回答不了「这一局需要几张图」。D（工作量）能回答后者，且**能自动算**。

**07 号已经证明 D 可数**：

```
N_pts = 2 × len(combat_episodes) + len(deleted_intervals) + Σ len(ep.deleted_inside)
```

实测 864 时间线：v1 = 38 → v6 = 22。
**这个式子的输入全部来自项目自己的文件，一个模型数字都不含。**

> **一句话锚**：
> **不看「能看多少张」，看「这一局有几个必须用图回答的问题」（N_pts）。**
> 38 个问题 × 1 张 ≥960px 的帧 = 38 张 ≈ 4 轮 —— 这个结论在 524K 和 200K 下**完全一样**。

## 3. 三条路线各自的可行性

### 路线 1：从 token 侧推导（与模型无关）

**做法**：读模型上限 → 算压缩线 → 除以单图 token → 得到张数上限。

**可靠性：低。** 三个独立的失效点：

1. 分母（单图 token）不确定，客户端常数高估 30%，实测跨度 659 倍（§2.2）。
2. 分子侧**漏掉了真正占上下文的东西**。本单实测（542 个读图会话）：

   | 相关性（对峰值上下文，log-log） | r |
   |---|---|
   | **工具输出字符数** | **+0.771** |
   | 推理（reasoning）字符数 | +0.737 |
   | 工具调用次数 | +0.609 |
   | 消息条数 | +0.570 |
   | **图片 token** | **+0.400** |
   | **图片张数** | **+0.335** |

   **工具输出对上下文压力的解释力是图片张数的 2.3 倍。**
   只按图片推上限，等于在错误的轴上做优化。

3. **最致命**：本单把 542 个会话的**真实峰值上下文**原样重放到不同压缩线上：

   | 模型 | 压缩线 | 会触发压缩的会话数 |
   |---|---|---|
   | space-bunny-free（现在） | 471,860 | **1 / 542（0.2%）** |
   | minimax-m3 | 460,800 | 5 / 542（0.9%） |
   | gpt-6-luna | 244,800 | 40 / 542（7.4%） |
   | qwen3.7-plus | 230,400 | 51 / 542（9.4%） |
   | **grok-4.7 / longcat / 兜底 200K** | 180,000 | **145 / 542（26.8%）** |

   **换到 200K 档位，四分之一的读图会话会被压缩。**
   而按 token 推导出来的「张数上限」在 200K 下会给出 110 张 —— **这个数毫无意义**，
   因为触发压缩的并不是图，是那 40 万 token 的工具输出。

**成本**：低（一次计算）。
**会不会浪费**：**会，而且是系统性的浪费。**
它把注意力引向「张数」，而 05 号已经证明 134 路里 **0 路触顶、最高只用到 45/50**。

> **判定：路线 1 单独用不可行。** 但它揭示了一个真事实（见 §3.4 的兜底风险），值得作为**监控项**而不是**预算项**。

### 路线 2：会话开始时探测

**做法**：开会话时先塞 N 张图试试上限。

**可靠性：零。** 05 号已经否掉了它，本单给出更硬的理由：

1. **探测手段与被测对象直接冲突** —— 探测「能吃多少张」的必然动作就是「吃很多张直到失败」。
2. **失败是真失败。** 客户端没有图片重试阶梯。二进制里有 `S6=[0.7, 0.5, 0.35]` 这条重试阶梯，
   但它**只挂在压缩请求上**，且只在收到 `payload-too-large` / `context-overflow` 时触发。
   **读图路径上一次都没有触发过。**
3. **更糟：探测不到。** 因为上游**没有张数上限**（§1.1 第 1 项）。
   你塞 50 张不失败、塞 100 张也不失败 —— **不是因为能吃，是因为根本没有这个限制。**
   探测会得出「上限 ≥ 100」，然后你真的按 100 去用，然后撞上的是**上下文线**，
   而那是一条你本来就能算出来的线。**探测把一条可算的线变成了一场事故。**

**成本**：高（一次探测 = 一次真实风险 + 一次会话上下文）。
**会不会浪费**：**会烧掉整段上下文**。实测：读图会话的峰值上下文 p50 = 135,208，p90 ≈ 226,000。
一次探测就能吃掉这个量级。

> **判定：路线 2 明确否决。** 它探测的是一个不存在的限制，代价是一次真实会话。

### 路线 3：承认无法预知，改为「出问题再处理」

**做法**：不猜上限，把工程量花在**缩小失败半径**上。

**这是唯一与模型无关的路线**，因为它不依赖任何模型数字。

关键问题：**「出问题」在实践中长什么样？** 本单查清了，这是本单第二个重要发现。

### 3.4 「出问题」的实际形态：压缩，不是崩溃

**全库 13 次压缩事件，全部 `reason=auto`、`status=completed`、全部所在会话最终 `succeeded`。**

| 压缩前上下文 | 压缩后上下文 | 摘要字数 | 保留 recent 字数 |
|---|---|---|---|
| 470,572 | **15,674** | 10,166 | 0 |
| 500,430 | **12,572** | 7,584 | 14 |
| 480,523 | **12,790** | 4,290 | 14 |
| 471,815 | **13,447** | 5,800 | 0 |
| 467,526 | 127,893 | 11,716 | 328,155 |
| 470,468 | 136,494 | 7,113 | 366,494 |

**两个关键观察**：

1. **压缩不是崩溃，是一次成功的重写。** 上下文从 47 万降到 1.3 万（降 97%），
   换成一段 7,000–11,000 字的摘要。会话继续跑，最终 `succeeded`。
2. **压缩后能重新长回去，但不会立刻撞线。** 13 个会话压缩后的最高点 = 19%–90% 中位数。

**这直接改写了「失败」的代价估算**：

> **「上下文丢弃 → 会话作废 → 上下文全丢 → 要重开」这条链，在数据上不成立。**
>
> 实测：13 次压缩，**0 次导致会话死亡**，13 个会话全部正常收尾。
> 真正丢的是**细节**（逐轮判读记录、具体帧号），不是**会话**。

**成本**：低（改流程，不改数字）。
**会不会浪费**：**不会**。这是三条里唯一「即使判断错了也不亏」的路线 ——
因为它防的不是失败，是**不可逆的证据丢失**，而证据丢失只需要靠「每轮先落盘」来防。

## 4. 「出问题再处理」具体怎么处理 —— 子 Agent 这个思路，数据支持吗

### 4.1 思路本身：核实结果 = **已经在用，而且是本项目最有效的一条**

用户的直觉是「把看图放在子 Agent 里，子会话作废不影响主线」。本单核实：

| 判据 | 实测 |
|---|---|
| 542 个读图会话里是子 Agent 的 | **537（99.1%）** |
| 单条消息带图峰值 | **恰好 10**（= 单轮纪律），7,993 条消息**零超限** |
| 单会话累计峰值 | **50 张**（唯一一个，压在线上，正常跑完） |
| 17 个顶层会话平均派发子 Agent | **38 个** |

### 4.2 决定性证据：子 Agent 死过 5 次，主线全部存活

这是本单最有价值的一张表：

| 死亡的子会话 | 死因 | 父会话 | 父会话结局 | 父在子死后又活了 |
|---|---|---|---|---|
| `ses_f100cb1e7ffe…` | **HTTP 500 Endpoint is unavailable** | `ses_f135ede3fffe…` | **succeeded** | **+2.8 h** |
| `ses_f0fb1fddcffe…` | interrupted | `ses_f135ede3fffe…` | **succeeded** | **+1.2 h** |
| `ses_f0db366d7ffe…` | （无结局） | `ses_f0f570101ffd…` | **succeeded** | **+10.4 h** |
| `ses_efa72fb98ffe…` | （无结局） | `ses_f16498506ffed…` | **succeeded** | **+12.1 h** |
| `ses_ef67548d6ffe…` | （无结局） | `ses_f16498506ffed…` | **succeeded** | （同会话） |

> **5 个子会话死了，5 个父会话全部正常收尾，没有一个因为孩子出事而中断。**
>
> 那个死于 HTTP 500 的子会话，正是**唯一带图的失败会话（17 张图）** ——
> 而它的父会话在它死后又跑了 **2.8 小时**，完成了整个任务。

**⇒ 「子 Agent 作废不影响主线」这条，数据完全支持。**

### 4.3 那失败到底贵不贵？—— 量化

**硬失败（上游报错）的真实代价，实测是「那一路的工作」：**

- 一个子 Agent 的典型工作量：实测读图子会话的**生命周期中位数约 1 分钟**
  （例：`ses_f0a244e78ffe…` 创建于 05:06，更新于 05:06）。
- 它交付的成果是**一个文件**（`reports\segN_scan_report.md`）。
- 父会话从失败到恢复：**不需要任何人工动作**，它继续派下一个子 Agent。

**⇒ 让失败变便宜的三件事，本项目已经全部具备：**

| 机制 | 状态 | 证据 |
|---|---|---|
| 看图放在子 Agent | ✅ **已在用** | 537/542 = 99.1% |
| 每轮结论落盘成文件 | ✅ **已在用** | 358 份 `reports\*.md` |
| 失败后重派而不是重开 | ✅ **已在用** | 5/5 父会话存活 |

**⇒ 不需要新增任何机制。** 用户担心的「失败很贵」在这个架构下**已经不贵了**。

### 4.4 那还剩什么真风险？—— 压缩时的细节丢失

压缩丢的是**这一轮看图的判读记录**。这不是会话死亡，是**证据降级**：

- 压缩把 12,572 token 的上下文换成 **4,290–11,716 字的文字摘要**。
- 摘要里**没有帧号、没有逐格判读、没有"第 3 轮读了 sheet02"这类记录**。
- 客户端渲染媒体的方式是 `[image/png omitted]` —— **确认了：图变成文字，这是设计如此。**

> **这才是「不可逆伤证据」的确切机制，而且它与模型无关**：
> 压缩线是模型上限的 90%，换小模型只是让它来得更早（180,000 vs 471,860）。
> **唯一的解药是 05 号已经写的那条：每轮开始前先写下核实记录。**
> 落盘的东西不会被压缩吃掉 —— 这是唯一一条与模型完全无关的防线。

## 5. 用户的真实风险敞口

### 5.1 seg4 的「余 20 张」—— 核实结论：**预算确实没超，但 06 号的因果解释是错的**

先确认引文是真的（`seg4_scan_report.md:143`）：

> 累计看图 30 张 / 单轮新增最多 8 张（第 1 轮）· 其余各轮 ≤2 / 共 15 轮 / 红线 50 张 → 余 20 张。

**引文逐字属实。** 但 06 号由此推出「真正的危险不是张数，是上下文被别的东西挤掉」，
**这一步在机制上不成立**，理由如下。

**核实一：那段时间根本没有发生过压缩。**

```
13 次压缩事件的日期：09-29 (×2)  09-30 (×9)  10-04  10-05
10-01 的压缩次数：0
seg4_scan_report.md mtime = 10-01 15:07
```

**seg4 写报告的那一天，全库没有任何一次压缩。** 所以「上下文丢弃」**不可能是压缩造成的**。

**核实二：客户端没有任何路径会在活上下文里悄悄丢图。**

从字节流里逐条排查：

| 搜索项 | 命中 | 结论 |
|---|---|---|
| `evict` | 57 | 全部是 EventEmitter / LRU cache / HTTP2，与上下文无关 |
| `pruneMessages` / `sliceTail` / `keepLast` / `historyLimit` | **0** | 不存在 |
| `replaceImages` / `stripImages` / `dropMedia` / `filterImages` | **0** | 不存在 |
| 把 media 渲染成文字的函数 | **只有 `Oj()` 一个** | 它**只被压缩请求构造器调用** |

```js
Oj=(e)=>{ ... if(a.type==="media")return[`[${a.media.mediaType} omitted]`]; ... }
```

**⇒ 唯一的丢图路径就是压缩，而那天没有压缩。**

**核实三：那 10 路扫描会话到底发生了什么？**

### 5.3 那用户真正的风险敞口是什么

| # | 风险 | 现状 | 换模型后 |
|---|---|---|---|
| **1** | **联系表每格 392×220 判读失败** | 已发生，5/5 误判 + seg4 的 6 轮白读 | **不变**（2000px 和 1568 都在模型之上） |

## 6. 结论与建议

### 6.1 直接回答用户的顾虑

> 「我感觉每一个模型其实都不太一样。现在的理论也是建立在当前这个模型上的，换一个还是不太行。」

**「不太行」的部分要改一个字：不是「不太行」，是「有一个量会变，其余全都不变」。**

| 换模型会变 | 换模型不会变 |
|---|---|
| **只有压缩线**（= 上限 − 10%） | 图片张数上限（**根本不存在**） |
| | 单图 2000px 封顶（客户端配置） |
| | 图片 token 折算口径（客户端固定 1500） |
| | **单张图能承载多少可判读信息**（1568px 折算 ÷ 列数） |
| | 「失败是硬失败」这个性质 |
| | 「50 张 = 5 轮 × 10 张」这个流程产物 |

### 6.2 最稳定的锚

> **不是 token 占比，不是张数。是「有效格宽」和「N_pts」。**
>
> - **有效格宽** = `min(渲染格宽, 1568 ÷ 列数)` —— 与模型无关，是物理量。
>   定性判读需要 **≥960px**（07 号 §2.3 推导 + §2.4 实测夹逼）。
> - **N_pts** = `2×episodes + deleted_intervals + Σ deleted_inside` —— 从时间线 JSON 可数，与模型无关。
>
> 864 实测：v1 = 38 → v6 = 22。**38 个问题 × 1 张 960px 帧 = 4 轮，在 524K 和 200K 下结论一样。**

### 6.3 三条路线推荐

> **推荐路线 3（出问题再处理），但要做两件事才算完整：**

| | 内容 | 为什么 |
|---|---|---|
| **主** | 承认张数上限不可知，改用 **N_pts 驱动**：「这一局有 38 个判断点，每个点配 1 张 ≥960px 的帧」 | 与模型完全无关，可自动算，结论在所有模型下一致 |
| **辅** | 加一条**单图尺寸**检查（打印折算后每格像素） | 这是唯一 100% 稳定的物理量，能直接拦住 392×220 |

**明确不推荐**：
- ❌ **路线 1（token 推导）单独用** —— 分母高估 30%，跨度 659 倍，
  且 200K 下会给出「110 张」这种与真实约束无关的数。
  它唯一揭示的真事实是**兜底 200K 的风险**（§5.3 风险 2），值得当监控项。
- ❌ **路线 2（会话探测）** —— 探测的是一个**不存在的限制**，
  塞 50 张不失败不是因为能吃，是因为根本没这条限制。代价是一次真实会话。

### 6.4 一页纸

| 问题 | 答案 |
|---|---|
| 换模型会变什么 | **只有压缩线**（上限 − 10%）。200K 档位 → 180,000，比现在低 2.6 倍 |
| 换模型不会变什么 | 张数上限（不存在）、2000px 封顶、1500/张 的折算口径、**单图有效像素** |
| 最稳的锚 | **有效格宽（≥960px）+ N_pts（从时间线 JSON 数）**。不是 token 占比 |
| 推荐路线 | **路线 3**，主用 N_pts 驱动，辅以单图尺寸检查 |
| 兜底 200K 风险 | **唯一真降级风险，无告警**。触发时 26.8% 读图会话会被压缩 |
| 子 Agent 隔离 | **已在用且有效**：537/542 读图会话是子 Agent；5 个子会话死过，**5 个父会话全部存活**（一个多跑 2.8h 完成全任务） |
| 「失败」的代价 | 比想象小得多：13 次压缩**全部可恢复**，0 次导致会话死亡。丢的是细节不是会话 |
| 真实风险敞口 | **离 50 张红线的距离是 0.2%（1/542，且与图片无关）；离真危险的距离是「一直都在」—— 每张联系表都是 392×220，已赌输 5 次** |

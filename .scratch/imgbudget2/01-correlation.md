# 01 · 看图预算 ↔ 剪辑速度 的关联性量化

**问题**：看图预算跟剪辑视频的速度有没有关联？关联性不强就不用改。
**结论**：**关联性弱，对速度甚至略呈负相关。建议不动 50 张红线。**

---

## 0. 一句话

50 张红线**从未被任何一路触碰过**（358 份报告 / 134 路自报用量里，**最高 45 张**）。
既然没人用满，放宽到 200 就买不到任何已经存在的东西；而真按 200 用满，时间只会**变长**不会变短。
唯一被实证决定成败的变量是**分辨率阶梯 + 判定标尺措辞**，不是图片张数。

## 2. 瓶颈到底在哪

时间口径来自 `.scratch\efficiency\01-timeline-forensics.md`（861 + 863 + 864-att2，span 合计 62.51 h）：

| 口径 | 时长 | 占 span |
|---|---|---|
| **静默 / 无产出** | 29.07 h | **46.5%** |
| F 审片 / 对抗审 / 验收（多路报告） | 10.77 h | 17.2% |
| D 时间线合并 / 合并裁决 | 4.80 h | 7.7% |
| C 分段扫描（看图判定） | 3.54 h | 5.7% |
| H 字幕外挂映射 | 3.24 h | 5.2% |
| G 返工 / 补验 | 2.95 h | 4.7% |
| I 4K 渲染 + 验收 | 2.09 h | 3.3% |
| **B 纯机器（转写/抽帧/检测/编码）** | **1.17 h** | **1.9%** |

**硬上限推导**：所有会碰图的路（C+F+D+G）= 3.54+10.77+4.80+2.95 = **22.06 h = span 的 35.3%**。
这是「把整条路每一秒都算成看图」的极端假设，实际不可能——这些路同时要写 20–73 KB 报告、
跑 ffmpeg/python 脚本、读 JSON/SRT/转写。

**估算**：这些路里真正读图的部分约 25–40%
→ **看图 ≈ span 的 9–14%（5.5–8.8 h），即活跃时间的 17–26%**。

独立交叉验证：att2 扫描相 14 路 / 2 名 worker / 13:05→15:31（146 min），
407 张图 → 吞吐 167 张/worker·h，即 **21.5 s/张的整路墙钟**；而 att2 单路整墙钟约 21 min、
其中读图 29 张 ≈ 7 min，**读图约占单路时间 1/3**，与上面的 25–40% 吻合。

**所以机器不是瓶颈（1.9%），静默不是可归因项（46.5%，夜间为主），看图更不是大头。**

## 3. 关键问题：50 → 200 会让剪辑变快吗？

**不会。三条独立理由：**

### 3.1 天花板效应——放宽了也没人用

134 路申报用量里 **0 路到过 50**，最高 45。中位数 14–26。
各路停下来的原因是**「没东西可查了」**，不是「预算不够」——
典型如 `adversarial_19_v5_adv10`：抽了 **1075 帧**做数值扫描，只读 **26 张**就结案。

放宽到 200 的边际收益 = **0 张**，因为那 150 张现在就没被需要。

### 3.2 若真用满，时间只会变长

读图时间随张数近似线性。当前 ≈5.5–8.8 h；若各路按比例涨到 4 倍中位数（21→84），
读图 ≈22–35 h，在 62.51 h 的 span 上是 **+26 h ≈ +42%**。
即：**放宽预算的最可能后果是更慢，不是更快。**

### 3.3 实测反证：更多图 + 更多审 = 更慢且被否决

同一素材 864，两次尝试，除预算规则相同外**没有任何差别**：

| | **att1（被整局否决）** | **att2（交付）** |
|---|---|---|
| span | **20.29 h** | **10.90 h** |
| 活跃 | 10.96 h | 3.76 h |
| 静默占比 | 46.0% | **65.4%** |
| 版本数 | v1→v6 | **v1→v3** |
| 审件文件数 | **83 份**（另 timeline 21 / captions 13） | **44 份** |
| 审查路数 | 7 路对抗审 + 4 遍自审 + 3 路验收 | 12 路独立审查 |
| 扫描底帧分辨率 | **480×270** | **640×360** + 强制 960px 复核 |
| 扫描相看图 | **≈447 张** | **407 张** |
| 结果 | **用户判定仍有问题、要求整局重剪** | **一次过、交付** |

**att1 看了更多图、跑了近两倍时间、出了 1.9 倍审件，然后被否决。
att2 看了更少图、用了不到一半时间、通过。**

## 4. 反向验证：「审片数量增加换不来质量」——核实结果

用户交办的推论**成立，而且比原推论更强**。

`docs\lessons\archive\864-rejected-attempt\reports\user_corrections_and_lessons_2026-10-01.md` §4.4 原文：

> 「现行标尺的『删：……全屏 UI（除属收束环节的）』隐含了『面板默认该删』……
> **一条措辞的偏差，会被 7 个审片员一致地执行成 4 个版本。**」

§4.1：

> 「共派出 **7 路对抗审 + 4 遍自审 + 3 路独立验收**……**没有一份任务书要求过「检查被删除的区间里是否有被冤杀的战斗」。**」

**推论链**：
att1 不是「看得不够」而是**判定标尺写错了**。22 路对抗审共享同一份错标尺，
于是 305+ 张图**齐心协力产出了同一个错误答案**。
在这种情形下加预算 = **把错误答案乘以更多份**，不产生新信息。

**最关键的反证**：逮住 att1 缺陷（E1 漏战）的手段是什么？§5 明写——

> 「**删除段语音战斗词扫描**……**零图片成本**，是逮到 E1 的唯一手段」

**赢下这次的方法，看图预算成本为零。**

同族证据（861）——项目早已自发把工作移出图片预算：

- `adversarial_19_v3_adv6`：「这 4,900 次误读里的第 1 次，就这样被 bbox 检查挡住了，**且没花任何看图预算**」
- `adversarial_19_v3_adv12`：「**零看图预算** · 画面活性/亮度扫描（0.5 s 步长，183 采样）」
  /「**零看图预算** · 屏上文字普查（0.25 s 步长，245 采样）」
- `adversarial_19_v3_adv1`：「6 个零图片预算结构化扫描（含 **1400 帧** 0.1 s 卡片区探针）」
- 861 全库：**37 份报告、87 处**显式声明零看图取证法（863 为 8 份 / 9 处，864-att2 为 1 份 / 1 处）

**抽帧量与读图量的比例 routinely 是 30:1 以上**（941 帧 → 读 29 张；1075 帧 → 读 26 张）。
增长方向早已是「更多数值探针、更少图片」，不是「更多图片」。

## 5. 唯一支持正相关的那个数据（如实列出）

必须诚实记录反向证据，否则这份报告不成立：

这一条要**如实纠正一个先入判断**：att2 的扫描相看图密度其实**并不更高**。
407 张 / 1152 s 源 = **0.353 张/秒**（att2）；att1 ≈447 张 / 1152 s = **0.388 张/秒**（att1）——
**att1 反而更高，却是被否决的那一次。** 同素材、同预算规则，张数高的那次输了。

真正发生变化、且能解释成败的不是张数，而是**分辨率阶梯**：att1 全程 **480×270**；att2 **640×360** 底帧
**且强制「凡标为面板/舔包/补给/倒地的候选删除段，必须先出 960px 单帧复核再定性」**
（`workflow_notes_21.md` §1.3）。

而 att2 **自己**也在 640px 上被坑了 **5 路**（§1.3：「五路扫描员各自独立踩到，
**没有任何一路是看了联系表就下对的**」），所以它才把复核分辨率提到 960px。

**结论：起作用的是「对决定性帧做定向升分辨率复核」这条纪律，不是全局张数配额。**
定向纪律已经在规则里了；它不依赖把 50 改成 200。反过来说，改成 200 并不会自动产生定向纪律，
只会让「联系表上先下个结论再补图」这种更省事的做法更容易发生。

## 6. 判定与建议

| 问 | 答 |
|---|---|
| 看图占总耗时比例 | **9–14%**（活跃时间的 17–26%）；硬上限 35.3%；纯机器仅 1.9% |
| 50 张是否成为约束 | **否**。134 路申报中 0 路触顶，最高 45 张 |
| 50 → 200 能否提速 | **否**。边际张数当前需求为 0；若真用满则时间 **+42%** |
| 关联性 | **弱；对速度略负相关，对质量零相关或负相关** |
| 建议 | **不动。** 保持 50 张红线与其配套的 `check_image_budget.ps1` 分轮计划 |

**如果要动，该动的不是数字，而是这两条已被实证的杠杆：**

1. **提高决定性帧的分辨率**（480/640 → 960/1280），不是提高张数。att1 480×270 失败、att2 640×360+960 复核通过，是本案最干净的因果对照。
2. **补「删除段审计员」这一路**（AGENTS.md §8.2 已列为第 8 种审片角色）——用**语音战斗词扫描**（零图片成本）交叉验证删除段。att1 的漏战正是栽在没有这一路。

## 7. 附带发现：用户另一个问题，本数据无法回答

> 「现在这个模型大概能够接受多少张图片呢？」

**实测答不了。** 因为 358 份报告里没有任何一路接近过 50，
模型的实际天花板**从未被观测到**——不是「观测到它很高」，是**根本没测到**。

要测它，必须先有「愿意把预算用满」的激励；而本次数据恰恰显示没有任何这种激励。
任何关于「当前模型能吃多少张」的数字，此刻都只能是推测，不能进文档当事实。

## 1. 派工模板规定的并发上限是多少？实际做到了吗？

### 1.1 规则原文（`roughcut-launch.md §2.2` / `§2.8`）

| 环节 | 规定并发 | 出处 |
|---|---|---|
| 扫描 · 常规档 | **单任务在途 10**，总路数 `ceil(时长/85)` | §2.2 |
| 扫描 · 最快档 e4 | **单任务在途 16–20**，下限 60 秒/路 | §2.2 |
| 扫描 · 全局 | **≤ 24**（跨任务扫描 + 对抗审合计），超限排队 | §2.2 |
| **合并（修线）** | **在途 1**，离线岛 ≤ 2 | §2.8 |
| 预合专员 | 2 名，只出 `*-draft` 岛草稿 | §2.8 |
| validate 实跑 | **单进程，禁并行** | §2.8 / §3 |
| 对抗审举证 | 可并行；**定稿单人一次** | §2.8 |
| 成片 NVENC | **全局锁，禁并行** | §2.8 / `time-budget.md §3` |

**规则本身的判断是对的**：分片可并行，裁决必须串行（`g-shard-merge.md §0` 原话）。合并/validate/成片锁在 1 是**质量守恒的必要代价**，不是浪费。

### 1.2 实际做到的

| 任务 | 扫描路数 | 台账声明档位 | 实际在途 | 回收跨度 | median→末路尾巴 | 合规? |
|---|---|---|---|---|---|---|
| 861 | 29 | 常规，"**单波全发**" | **29**（>10 上限） | **523.5 min** | **503.3 min** | ✗ 超上限 2.9 倍 |
| 863 | 14 | 常规，W1=seg1–7 / W2=seg8–14 | 7 | 38.6 min | 13.9 min | ✓ |
| 864-att1 | 14 | 常规 | 14 | 57.5 min | 49.0 min | ✗ 超 10 |
| 864-att2 | 14 | 常规，W1=seg1–10 / W2=seg11–14 | 10 | **108.8 min** | 23.9 min | ✓ |

**读数**：

1. **扫描阶段的并行度基本做到了，864-att2 甚至比 864-att1 慢一倍**（109 min vs 58 min）。原因不是并行度不够，是**每路看图量差 2.5 倍**（864-att2 台账自报"看图 17–44 张/路"，864-att1 与 863 是 7–18 张/路）。**这是质量选择，不是调度失败**——不能算进串行账。
2. **861 严重超上限**（29 路一次性全发 > 规定的 10）。后果直接见 §2。
3. **合并阶段并发 = 1，四个任务全部照做——但一条 partial 岛草稿都没产出过。** 全样本 `*partial*` 文件数 = **0**，`merge_decision_v*-partial-*` = 0，`*-draft` = 0。台账里 `PARTIAL` / `BRIDGED` / `SEAM` 三个三态词在四本台账里出现 **1 次**（861 L293，且是"验收 D4 命名一致 = PARTIAL"，与岛式合并无关）。
   → **规则 §2.3/§2.8 写了一套流式合并的触发器（回 1 路出 partial / 回 2 路预合岛 / 回半数全量草稿 / 缺路成岛 / 搭桥升段），一次都没执行。** 这是本次诊断最实的一条：**逃生阀存在但从未被打开**。

## 2. 从"扫描全部回收"到"合成一条时间线"有几道必须等齐才能动的关口？

### 2.1 规则设计的关口数

`§2.3` 六档触发器里，**只有最后一档（全回 + 双证齐 + validate pass）能进下游**（字幕/渲染/自审只认冻结版）。也就是说从扫描到能渲预览，规则上是 **1 道硬闸门 + 5 道只出草稿的软触发器**。

**实际执行的是硬闸门，5 道软触发器全部跳过。**

### 2.2 实测：这道闸门各任务等多久

| 864-att1 | 13:20 | 13:29 | 14:17 | 14:30 | 1.02 h | 1.22 h |

| 863 | 13:47 | 14:12 | 14:26 | 14:42 | 0.50 h | 0.92 h |

### 2.3 861 这 9.3 小时到底发生了什么（逐条取证）

**问题不在"丢了 3 路"，在于丢了以后没有任何降级路径被启用**：

- 结果：**26 份报告在盘上躺了 8 小时，一帧成片都没有。**

**跨样本这道闸门的干等合计 ≈ 9.27 + 1.02 + 0.78 + 0.50 = 11.6 h**，其中 **80% 集中在 861 一个任务**。

## 3. 「对抗审 → 复验 → 冻结」需要几个串行往返？864-att1 六版 vs 864-att2 三版，差别在哪？

### 3.1 往返次数实测

| 任务 | 时间线版本 | 全片对抗审波次 | 审件总数 | 单波回收跨度 | v1→末版耗时 | **每版均耗** |
|---|---|---|---|---|---|---|
| 861 | **9** | 3（v2 / v3 / v5） | 46 adv + 6 accept + 3 reverify + 1 selfaudit + 1 delaudit = **57** | 31 / 93 / 118 min | 12.33 h | 1.37 h |
| 863 | **6** | 4（v2 / v3 / v4 / v5） | 39 adv + 2 accept + 2 reverify + 2 census = **45** | 33 / 72 / 81 / 42 min | 13.31 h | 2.22 h |
| 864-att1 | **6** | 3（v1 / v2 / v3） | 23 adv + 17 accept + 1 reverify + 3 selfaudit = **44** | 20 / 24 / **376** min | 17.72 h | 2.95 h |
| **864-att2** | **3** | **1（只有 v1）** | 6 adv + 2 reverify + 1 selfaudit + 2 delaudit + 2 adjudicate = **13** | **8 min** | **2.12 h** | **0.71 h** |

**全部对抗审波次的总墙钟 = 227 + 243 + 419 + 8 = 897 min ≈ 15.0 h。**

### 3.2 循环次数由什么决定？不是审查强度，是 **v1 的结构质量**

| | 864-att1（废） | 864-att2（交付） |
|---|---|---|
| v1 结构 | 11 场 / 16 删除段 / **1 处段内挖洞** / **无 `whole_battle_policy`** | 5 场 / 6 删除段 / **0 挖洞** / **`whole_battle_policy: "864"`** |
| v1 `needs_review` | 多处 | **0** |
| 每波对抗审能发现什么 | 新的挖洞、新的面板残留、新的断链——**问题清单长度与版本数同步增长** | 6 路合计确认低级错误 **0**，只有 2 条 needs_review 走定点裁决 |
| 收敛路径 | v1→v6 **6 版** | v1→v3 **3 版** |

**机制**：v1 结构错 → 每个对抗审波次都在发现**新类别**的问题 → 每个问题逼出 1 个新版本 → 每个新版本触发 §3.6 强制的**全片重扫** → 循环次数 = v1 缺陷数，不是审查细致度。

864-att2 反过来：v1 就带 policy 标记、0 挖洞、0 needs_review → 对抗审一波 8 min 就零新增 → 后面两版只跑**定点复验**（`reverify_864_v2/v3`），**再没跑过第二波全片对抗审**。

### 3.3 864-att2 靠"违规"才收敛——但违规是对的

| 规则 | 864-att2 实际 | 台账原话（L103–109） |
|---|---|---|
| §3.6「**每版冻结后必派**对抗审，按节目时间切 60–90 秒/路多路并行」 | **只在 v1 跑了一波**，v2/v3 只跑 reverify | — |
| §3.7「`streak ≥ 2`（连续两版零新增）才送审」 | **明确豁免**，v3 的 `streak = 1` 就交付 | 「继续推 v4 的边际收益为零……本轮已经用 6 路对抗审 + 四遍自审 + 2 次定点裁决 + 3 轮复验 = 12 路独立审查满足了这个目的」 |

**864-att2 是四局里唯一被用户第一次就接受的版本，而它是唯一违反 §3.6 + §3.7 的版本。**

> 这不是"规则错了"，是**规则把"审查覆盖度"当成了代理指标，而真正该保证的是"v1 结构正确"**。864-att1 的 44 份审件一份都没拦住"把一整场战斗从中间切开"——审件数量与正确率**负相关**（见 §3.1 表：57 份审件 → 用户仍否；13 份审件 → 一次过）。

### 3.4 §3.6 全片重扫的单点最坏情况

`864-att1` 的 v3 波：`adversarial_864_v3_adv6.md`

```
19:46:22  该波 median 落盘（7 路里的第 4 路）
19:46 ─── 10-01 01:33  全项目零该路产出  ← 单路拖了 5.79 h
01:33:38  adv6 落盘
01:33 ─── 02:29  adjudicate_v3_b
02:36 ─── 03:01  combat_episodes_v4.json
```

**单路拖 5.79 h，直接卡住整个 v3→v4 推版。** 波次跨度 376 min，其中 358.7 min 是纯尾巴。规则对此**零超时条款**——`§2.5` 的 3 轮超时只写在扫描路（`segNb`）上，对抗审路没有对应的冻结换路机制。

### 5.2 「秒数必须自己先算一遍」——这条经验值多少秒 × 多少路？

**派工单里必须自己算好的秒数 = 逐路的区间边界 + 每路的 P↔S 换算式。**

| 任务 | 需预算的秒数个数 | 依据 |

## 6. `streak ≥ 2` 与 §3.4/§3.7 的隐藏税

| 规则 | 内容 | 实际执行情况 | 代价 |
|---|---|---|---|
| §3.7 | 「`streak ≥ 2`（vN-1、vN 连续两版零新增）才送用户审片」 | **864-att2 豁免**（streak=1 交付）；**861 用"两种独立证据链"折算**（源轴密集扫 + 节目轴对抗审）记作两遍 | 每任务 **+2–3 h**（多一整轮 = 一次全片重扫 + 一次重渲 + 一次复验） |
| §3.4 | 「四路验收报告**全部落盘前**，修线员不得开 vN+1」 | 全部照做 | 861 v2 冻结门禁（04:53）→ v3（06:38）= **1.75 h**，其中验收报告落盘集中在 04:52–05:03 |
| §3.2 | 「同一版本号的修线员/字幕员/渲染员不得兼任该版本任何验收角色，验收派工必须换新子 Agent」 | 全部照做（新增会话成本） | 每个版本多 3–4 个新会话 |
| §2.8 | 「冻结判定全回后一次判定」 | 全部照做 | 与 S1 同源 |

**`streak ≥ 2` 是最贵的一条隐藏税**：它把"至少 2 个完整版本循环"写成了硬性前置。864-att2 豁免它省下的时间，直接体现在 `v1→v3 = 2.12 h`（对比 863 的 13.31 h / 6 版）。

**但要注意**：864-att2 能豁免是因为 v1 结构就对。**在 v1 结构错的情况下（864-att1），`streak ≥ 2` 只会把 6 版拖成 12 版**——它防的是"一次侥幸"，代价是"必然多跑一轮"。规则应该改成**条件触发**（v1 结构有 `needs_review` / 挖洞 / 无 policy 标记时才要求 streak ≥ 2），而不是无条件。

## 7. 改动清单：哪一步最该并行化

按"每小时省下的墙钟"排序：

### P0 — 打开岛式合并（省 ~12 h，其中 8.7 h 在异常路径）

- **动作**：把 `§2.3` 六档触发器从"可选"改成"**默认执行**"。回 1 路即出 `merge_decision_vN-partial-r{k}`，回半数即出全量草稿。派 2 名预合专员（只出 `*-draft`，不碰 `timeline/` 与台账）。
- **不改任何剪辑规则**，只改调度。
- **验收**：`partial` / `draft` 文件数 > 0；`FROZEN` 台账行引用的 `PARTIAL` seq 数 ≥ 1。
- **风险**：版本血统（§2.8"一动全废"）——partial 作废是设计内的，返工成本低。

### P0 — 对抗审改 delta 复验，不改全片重扫（省 ~13 h）

- **动作**：`§3.6` 的「每版必派全片对抗审」改为「**改动落在哪几条 episode / 哪几个切口，就只重审那几段 + 相邻缝**」。全片重扫只在下列情况触发：① v1 首次送审 ② 场数变化 ③ 节目总时长变化 > 30 s ④ 上轮有漏战/战斗中断。
- **实证**：864-att2 v1→v2 只改 1 个字段 2 秒，v2→v3 只改 1 个字段 6.5 秒，两版都靠 `reverify` 闭环，**没有一个字节的内容需要重看**。861 L1796 自己写了「v8 相对 v7……14 路对抗审所看的画面内容逐帧不变」。
- **配套**：对抗审路**必须设超时**（§2.5 的 3 轮规则目前只覆盖扫描路）。864-att1 单路拖 5.79 h 就是没有这条。

### P1 — 定点裁决并发派发（省 0.5–5.5 h/次）

- **动作**：`§2.3` 加一条「**裁决之间无数据依赖时必须同时派出，不得排队**」。派工单里显式列出「本议题不依赖/不重叠于哪几条裁决」。
- **实证**：864-att2 的两条裁决（gap266 / gap444）台账自己并列写在一起，串行等了 51 min。864-att1 的两条隔了 5.57 h。

### P1 — 派工单秒数脚本化（省每次 15–50 min × 每任务 3–4 次）

- **动作**：派工 prompt 里的区间端点与 P↔S 换算式，由 `program_map_vN.json` / `cut_list_vN.json` **自动生成**，禁止人手写。生成物落 `reports/dispatch_seconds_vN.json`，派工单引用该文件而不内联数字。
- **实证**：863 三次、861 四次、864-att2 一次同类错误，每次都是下游先发现、指挥后返工。

### P2 — `streak ≥ 2` 改条件触发（省 2–3 h/任务）

- **动作**：仅当 v1 存在 `needs_review` / 段内挖洞 / 缺 `whole_battle_policy` 时才要求 `streak ≥ 2`；否则 `streak ≥ 1` + 定点裁决闭环即可送审。
- **实证**：864-att2 用这个口径交付，用户一次接受；864-att1 用旧口径跑满 6 版仍被否。

## 9. 复算方法与脚本

全部数字由文件 `mtime` 重算，不采信台账自述：

| 量 | 口径 |
|---|---|
| 扫描回收跨度 | `reports\segN_scan_report.md` 的 mtime，`max − min` |
| 扫描尾巴 | `max(mtime) − median(mtime)` |
| 对抗审波次 | 按文件名 `_v(\d+)` 分组，组内 `max − min` |
| 首路/median/末路 → v1 | 与 `timeline\combat_episodes_vN.json`（v1）mtime 相减 |
| partial 流式化收益 | `(首路 mtime − v1 mtime) − (末路 mtime − merge_decision_v1 mtime)` |
| 冗余重扫 | 对抗审波次中版本号 > 1 的全部波次墙钟之和 |
| 审件总数 | `reports\` 下 `adversarial_*` + `accept*` + `reverify*` + `selfaudit*` + `deleted_audit*` + `*census*` 计数 |

> ⚠ 与 01 号报告的差异说明：01 号用「活跃簇（20 min 阈值）」分活跃/静默；本报告用「事件 mtime 差值」算**具体关口**的等待时长。两者口径不同，数字不互相替代——01 号的 29.07 h 静默是**总量**，本文的 11.6 h（合成闸门）+ 13.4 h（冗余重扫）是**其中可归因于串行的子集**。两者相加无意义，本文数字只用于定位改造点。

## 10. 一句话给决策者

**并行度不是问题——14–29 路扫描的回收跨度只有 39–109 min，机器重活只占 span 的 3.1%。问题是回收之后的两道串行闸门：「必须 100% 回收才能合成」（规则自带岛式合并逃生阀，四局一次没用，白等 11.6 h）和「每改一个字段就重扫全片」（§3.6 强制，冗余墙钟 13.4 h）。两处合计约 25 h，占三局 span 的 40%。**

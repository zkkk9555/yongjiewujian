# 完整战斗粗剪模式

## 目标

这个模式解决的不是"把更多精彩瞬间拼起来"，而是把素材中的每一场有效战斗完整截取出来：

```text
交战前的必要进入
  → 第一次明确交战
  → 这一场战斗中的连续交换/拆火/追击/救援
  → 最后一次关键动作
  → 结果明确和短暂收束
  → 下一场战斗
```

最小剪辑单位是 `combat_episode`（完整战斗事件），不是单个击杀、音量峰值、场景变化或字幕关键词。任何一个证据都只能帮助发现候选，不能单独决定切点。

## 第一层：硬性规则（违反即返工）

1. 战斗没有结束，不得转场到下一场。
2. 不以 PySceneDetect 的场景边界、Auto-Editor 的静音边界或单个音频峰值作为战斗结束证明。
3. 每个入选片段必须同时保留：进入交战、关键动作、结果和必要收束。
4. 战斗内部的短暂拉扯、换甲、蓄力、救援、追击、躲避和重新接战属于同一场战斗时，必须保留。
5. 只有在确认已经脱离战斗后，才删除搜物资、跑图、长时间等待和无事件画面。
6. 对边界不确定的片段，宁可保留为 `needs_review` 候选，也不要自动切断正在进行的战斗。
   `needs_review=True` 的 episode 不得进入预览 QA，必须先高清定点清零（839 v1）。
7. 粗剪审片版默认不加 BGM、对话字幕和装饰特效；先验证选片和连续性，确认后再进入高质量成片阶段。

## 第二层：证据与判定标准

### 2.1 开战判定：双独立信号

从以下证据中至少找到两个相互独立的信号，再确定 `engage_start`：

- 画面中出现明确敌人并进入可交战距离、瞄准或锁定状态；
- 第一次攻击、受击、振刀预备、技能施放或明显躲避动作；
- 队友被攻击/倒地、语音呼救或玩家明确报点；
- HUD、伤害反馈、击杀/倒地提示或明显战斗特效出现；
- 音频出现连续战斗声，而不是单个环境声。

从 `engage_start` 往前回看 3–8 秒，保留必要的接近、发现敌人、队友遇袭或战术铺垫。前置画面如果只是搜物资、跑图或无关移动，不要为了"留上下文"整段带入。

默认 `source_start = engage_start - 5s`，再向前后微调避开全屏 UI 与纯跑图；开战帧前已是交战中时，头前段为有效进入 + 开战不得裁（837 v2：ep1 头 7–17，17 已交战故 7 保留）；前置内必须能看懂"为什么打起来"：敌人接近、钩锁/技能先手、队友被打、报点集火至少出现其一；若前置撞上上一场的结果收束或全屏强化/背包界面，优先保证上一场结果完整，再另找干净进入点，不得把两场粘成一场；审片时若仍感觉"突兀、第一秒就开打"，直接再前扩 2–3 秒并重新渲染预览验证（832 v3）。

画面三信号（敌方红血条 / 伤害数字 / 锁定线）是开战与否的最终裁决：

- 定出 `engage_start` 后必须用三信号向前回查（834 v4）：音频候选起点不等于开战点；
  若画面首现交战证据比 `engage_start` 早 8 秒以上，直接把 `engage` 前移到画面证据处再定前置；
  回查按 2–5 秒步长加密取高清帧（960×540），只看"红条出现的第一帧"，不要凭转写猜。
  反例：834 combat_007 曾以音频起点 793 定 engage，画面回查 762 已现红条、764 已有伤害 37 + 锁定线，真开战在 763（头 788→758，补 30 秒）。
- 保留段内部出现单人跑位/舔包/架枪/御空侦查时，用"敌我锁定 + 伤害数字 + 红血条 + 战斗语音"四信号判断是否为战斗内拉扯（834 v4）：四者居其二即保留，不得挖空；稀疏抽帧看到疑似跑图必须用转写连续战斗语音 + 高清复核确认，不得凭一张小图删段。
- 战斗尾的"拉扯跑位"在稀疏图上极似"收束跑路"，尾部判定必须用高清逐秒 + 红血条/伤害数字双信号，稀疏图只能做初筛（838 v1：320px 稀疏图误判 GH 尾收束，高清显示 T1188–1195 连续交战，两场按 rejoin 合并为 GHI）。
- 钩锁/御空/蓝盾类位移特效不得单独作为交战证据（838 v1）；边界帧用烧录级分辨率复核，320 缩略图判干净不算数（835 v11–v12）。

特殊开战情形——队友先被打（832 v2）：队友被打意味着战斗已经开始，即使玩家还没赶到，赶路支援、听报点、看队友血条都是战斗进入的一部分，开战点前移到"队友被打 + 玩家开始赶路/报点"处。队友只是被远程摸一下（掉一小格、对方不追、我方直接跑开）则不算；四信号（队友血条大掉/倒地、有连续交战语音、玩家转向支援、后续连续交战）至少中其二才算开战。

### 2.2 战斗持续与结束

持续信号（任一持续或短间隔交替出现即战斗未结束）：玩家/队友/敌人在攻击、防御、受击、追击、逃生或救援动作中；敌我仍在同一交战区域，画面仍有近战交换、远程压制或技能影响；关键动作间只有短暂换甲、拉开、躲技能、转视角或重接；战斗语音/脚步/武器碰撞/技能/受击声构成连续上下文；最后一人未倒地、逃脱、被淘汰或明确脱险。

#### 2.2.1 一整场完整战斗（864 用户准则 2026-10-01，最高优先级）

> **用户原话**：「我想要记录一整场完整的战斗。不管中间我去干啥，可能去舔包了、打药了，或者去拉扯了。因为战斗并不是说我必须要跟别人干到死，可能这个时间甚至能持续 5 分钟，中间可能有二三十秒我都是在观察的状态，其实那也算是战斗的一部分。**我不想中间有断断档的时间，因为一断之后，战斗就不连贯了，观看体验就会很差。**」

**一场完整战斗** ＝ 对同一队（或那两三队）敌人的**第一次接战，到最后一次交战结束**。中间的每一次战术停顿都属于这场战斗：拉开距离、脱离战场、打药／补血、舔包、换武器、拿魂玉、选法门、重新进场、长时间观察态势——**一个都不许切**。

只有**换了对手**、或发生了真正的场景／时间断裂（去城镇交易、结算界面）时，才算下一场。

**判据是因果链，不是 UI 类型，也不是间隔秒数。** 判断一段该不该删，问的是「它在这场战斗的因果链里吗」，不是「它是不是面板」「它有几秒」「它有没有交战动作」。

三条推论（**864 实证：前两条被逐条违反过**）：

| # | 规则 | 864 的教训 |
|---|---|---|
| **R2-1** | **`(engage_start, outcome_time)` 区间内不允许任何 `excluded_inside`。**战术停顿要**包含进来**，不是挖掉。 | v1–v4 挖了 11 场战斗共 30 段 |
| **R2-2** | **相邻两场若战斗流程延续，必须合并成一段连续画面**，间隙（哪怕只有 6 秒）也要包含进去。 | **v5 修完了所有洞，用户仍指出"2分36秒还在截断"——洞清光了≠战斗没被切断，场边界本身也在切** |
| **R2-3** | `excluded_inside` 只允许出现在 `outcome_time` **之后**（结果后的大地图／结算面板）或 `engage_start` **之前**（前置跑图），用于清理首尾杂讯。 | 864 v6 最终版有 3 个洞，全部在 outcome 之后，**合法**。所以是**位置**有讲究，不是禁用该字段 |

**合并判据（R3，864 反例）**：不要用「间隙 ≤ N 秒就并入」这种纯计时判据，**逐帧核实间隙里到底在干什么**：

| 间隙内容 | 处置 |
|---|---|
| 拉开 / 打药 / 舔包 / 换装 / 跑动 / 重新进场 | **合并**（同一场） |
| 换了对头、跑图、闲聊 | 分开 |
| 去城镇交易、结算、复活 | 分开（属战场之间的补给，不属于任何一场） |

同一素材内的实证对比：12.99 秒的间隙＝拉开+强化面板+跑动+重新接战 → **合并**；0 秒的间隙＝两场首尾本就相接于同一秒、源上完全连续 → **合并**（否则是一道纯多余切口，视觉上会闪）；84 秒的间隙＝「去买点东西去」「等下补充一下物资」→ **不合并**（并进去会把 84 秒商城塞进战斗）。

#### UI 处置口径（863 定死，别再逐案重议；864 覆盖了战斗内的部分）

**优先级：先问「这个 UI 在不在战斗的因果链里」（864），再问「它盖没盖住战场」（863）。战斗内一律留。**

| 情形 | 处置 |
|---|---|
| **落在 `(engage_start, outcome_time)` 内的任何面板** —— 舔包 / 打药 / 换装 / 拿魂玉 / 选法门 | **一律保留**，不挖。哪怕超半屏、不透明（864 `combat_003` 实证） |
| 战斗窗口**之外**（前置 / 结果后）的超半屏、不透明、盖住战场视野的全屏 UI | **逐实例挖除**（§2.3 一票否决，优先于 8 秒计时器） |
| **半透明** / 占屏不足半屏 / **背后有活体交战** | **留**（被盖住的部分观众看得见） |

> **863 与 864 冲突时以 864 为准**：863 §③ 曾规定「超半屏+不透明+盖住战场视野 → 逐实例挖」，
> 而 864 的 `combat_003` 恰好是这种面板且**在战斗中**，用户明确要求保留。
> 修订后：863 那条只适用于战斗窗口之外。这条冲突本身就是教训——
> **口径冲突必须写明谁覆盖谁，否则下一局还会反复。**

**若确实需要挖除战斗外的 UI 实例，四条硬规则（863 四次复发后定的）**：

1. **定界要从「最后一个非 UI 帧之后」起算**，不是从「量到的 UI 首帧」起算。
   863 v2 因此多挖了 3 秒战斗。
2. **实例逐个挖、不要跨实例合并** —— 合并会把实例之间「面板关闭的真实内容」也挖掉。
   863 v6 特意保留 0.55–1.15 秒的碎片切片就是为此。
3. **检测必须看局部区域，不能只看全画面平均** —— 全画面平均会漏掉半透明层
   （863 据此漏检了源 1009.4–1010.25 那 0.483 秒）。
4. **「只量了 UI 的一个实例」是 863 四次返工的同一个根因** —— 定界用的是
   「我抽到的那个样本从哪开始」，而不是「这段里 UI 到底开过几次」。
   必须做全片普查，不能抽样。

`internal_gap_seconds = 8` **只管玩家姿态的战术停顿**（喝药、修理、换甲、腾空机动），
**不管盖在它上面的 UI 层** —— 这两条优先级搞错过一次（863 v3 同时用了两条口径）。

**「开大」诊断启发式（864 E1，零成本）**：若入片时**已经处于开大／技能释放进行中的状态** → 前置战斗很可能被删了 → **立即回查该场 `source_start` 之前**。用户原话：「6分28 那一场战斗进来，我都是直接开大的状态。那肯定是之前有战斗啊」。

截断保护（832 v2，e2升级见尾验证窗）：打宝窟怪/舔包架时周围仍有怪或队友交战、打药/救人时敌方还在场、追击/逃生途中仍有伤害交换或锁定，战斗继续；尾部验证窗 `[outcome_time, candidate_source_end]` 非终局段必须 ≥13 秒连续三信号全绿（outcome_hold 8 + recovery_tail 5，大于 rejoin 12；升级来源 `123\workflow_upgrade\e2_anticut_tail.md`），窗内任一秒出现战斗信号即时钟重置（`outcome_time` 移到新的最后关键动作处重起13秒），13秒不够时直接看到"无敌人 + 无伤害 + 语音回到非战斗"三信号同时成立才收。

结束条件（须同时成立，e2三信号口径）：最后一次攻击/受击/技能交换结束；结果可见（击杀、团灭、敌人逃脱、玩家脱险、救援/拆火完成）；画面无正在处理的敌人且无紧接追击/反打；语音回到非战斗或有明确结果语句；向后13秒尾验证窗连续无回拉。

**倒地—救援—复活的因果链（2026-09-30 用户准则，必保，不得当死时间整段删除）**

玩家倒地不是剪辑终点。「等待救援」在游戏内**有硬时限**（魂种计时），长时间挂着等待救援在规则上不成立——要么队友赶来救，要么玩家转入返魂场。因此**只要一段待核区间里出现超过正常魂种时长的"等待救援"，就必须先证伪"这整段没有事件"，不能凭一条常驻横幅就判定为无信息死时间**。

必保的三类内容，缺一即视为抹掉战斗事件：

1. **死亡视角本身**：玩家倒地后镜头仍在战场上，能看到队友与敌人的交战、击杀播报、增援到达。这是有效战场信息，不是废片。判"无战斗"必须逐段核验，**不得用"玩家自己不能动"一票否决**。
2. **队友来救**：队友赶路支援、贴身、按 F 救援、救援读条、复活白光——**救援本身就是战斗**。这既是"救"也是"被救"，属于玩家与队友之间的交战事件。参照本文件 §2.1「特殊开战情形——队友先被打」的同类口径：队友状态的变化就是战斗的进入与结果。**后勤救援与前线交战同级，不得因为"没有挥刀"而降级。**
3. **重新站起来 / 转返魂**：玩家恢复可操作的那一刻（技能轮恢复、弹药恢复、倒地提示消失、E（长按）转化成灵魂状态 提示消失）是明确的**结果帧**，与击杀/团灭同级。跳过它，下一场戏就会从"倒地"直接跳到"站立"，观感上等同于瞬移，剧情断链。

处置规则：

- `source_end` 应延到"恢复可操作 + 短暂收束"，而不是停在倒地那一刻。
- 段内若有**全屏菜单**横在倒地与被救之间，允许**按断裂点拆段**（保留倒地→被救的完整链条，删掉中间纯菜单长段），但**不得**中段挖除把倒地与被救劈开。
- 反过来，把整段"等待救援"当无战斗删除，**同样违规**——它既包含救援这一战斗事件，也包含死亡视角的战场信息。
- 最常见的误判：被常驻的「等待救援」横幅误导，把"玩家不能动"读成"没有战斗"。此为 **HUD 误读类错误**，与"320px 把常驻 HUD 误读成背包面板"同源，须在 ≥960px 复核后才可定罪。
- 自检句式：**"玩家倒了所以这段没战斗"不成立**。凡以此结案的删除，必须能指出倒地图上队友在做什么、以及玩家何时重新站起来。

收束帧规则（832 v4，e2升级：收束三步步步有帧，来源 `123\workflow_upgrade\e2_anticut_tail.md`）：击杀播报出现战斗即结束，但切点不得收在击杀帧或舔包 UI 全屏帧上——`source_end` 须含收束三步：①击杀播报（播报文字高清帧 + 明确结果语句，≥1秒可读）→ ②舔包关UI（UI打开帧 + 关闭后首干净帧两帧可查）→ ③跑路转点（无敌人无伤害下跑路 ≥2 秒）；步步有帧可查，缺一步即收束不足（838 v1：D2 尾 562→564），延长至少 +5 秒并重走13秒尾窗验证。两场间 ≤5 秒纯战术间隙（战后感叹词，无新交战）并入上一场尾；高清见"无敌人 + 无伤害 + 舔包/跑路"只补收束，见"红血条 + 伤害数字 + 锁定"必须延长。扫描员报告尾部必填（并入扫描报告，不另起文件）：`outcome_time` + 播报证据帧 / `tail_window`（≥13秒，非终局段）/ `tri_signal` 三行各写区间 / `close_steps` 三步帧（缺一写缺哪步 + 延长秒数）/ `tail_frames` 高清逐秒帧目录 + 联系表 + 最后5秒全绿表 / 尾窗存疑即 `needs_review` 不得送预览。

终局结算保留（用户规则）：若源素材含本局最终结算画面（段位/排位加分屏），最后一场战斗的收束延长至结算——从本局终局（吃鸡/夺冠，或被杀淘汰且无返魂/重开）起，保留"终局 → 结算屏（含段位加分）"完整片段，不得切在"打完 → 黑屏/结算前"。结算延长正确做法是并入最后一战（只改 `source_end`、outcome 落段位帧、event 加 `victory_settlement`），不得独立成段（独立段 engage 无处安放会被 validate 打回，841）。中间选人/大厅过渡帧若短（≤5 秒紧邻结算）可保留作衔接；结算完成后新开对局（下一把选人/出生）仍删除。本次七局追溯已全量执行（830/832/834/835/837/838/839），此句不再是"旧任务豁免"而是"已追溯完毕"记录。

终局链形态（七局追溯实证）：吃鸡局为"终局 → 黑屏/插画 → 名次屏 → 段位屏（段位名 + 经验条完整呈现即收）→ 加分屏 → 熟练屏（若有）→ 大厅"；被杀淘汰局为"被杀 → 淘汰面板（伤害列表）→ 举报/鉴定过渡（同因果链，即使 20 秒以上、无交战三信号也可保留衔接）→ 段位屏 → 经验详情 → 大厅"。判定要点：outcome_time 落在段位确认帧而非终局击杀帧（834：1573 非 1550；832：1132 非 1128.4），impact_points 补终局/段位两点，event_types 可加 `victory_settlement`；结算延长只改 `source_end` 不动 `engage_start`，审计写明"结算为收束延长"（837）；中间黑屏/加载（834：21 秒终局→结算必经流）、源原生瑕疵（835：1–2 秒切屏任务栏闪现，前后均为结算屏）保留不挖空，审计写明瑕疵来源非剪辑引入；超限保留须写明理由（839：选人 6 秒略超 5 秒但为唯一衔接桥）；转写结论引用前重拉全尾，旧"转写止于某秒"可能过期（834：转写实际到 1575.9）；终局插画衔接帧可证"黑屏→名次屏"为正常过渡非缺失（832：f1157 蓬莱岛插画）。

停顿后处理：停顿小于 `rejoin_window_seconds`（默认 12）且敌人在同一战区、战斗信号连续，合并为同一 episode；rejoin 窗口是"合并充分条件"而非"合并必要条件"——间隔 <12 秒但期间无战斗信号、上一场已有完整收束，判两场成立（839 v2：E6/E7 间隔 8 秒判两场）；有清晰脱离、移动到新区域、搜物资或长时间无事件，再开下一场；两场间非战斗段可删，但不得删上一场结果或下一场进入。宝窟→野外场切的可靠双信号：场景切换（宝窟 UI 关闭过渡）+ 转写从物资语音突变为接战语音（838 v1）。

默认计时参数（起始值，画面证据优先于计时器）：`lead_in_seconds` 5（交战前进入）、`internal_gap_seconds` 8（小于此值的战术停顿先保留）、`rejoin_window_seconds` 12（停顿后重接则合并）、`outcome_hold_seconds` 8（最后动作后等结果明确，e2升级：旧4秒→8秒）、`recovery_tail_seconds` 5（胜负/脱险短收束，e2升级：旧3秒→5秒）。尾验证窗合计13秒（8+5）必须大于rejoin窗12秒，窗内任一秒出现战斗信号即重置时钟（升级来源：`123\workflow_upgrade\e2_anticut_tail.md`）。

## 第三层：执行流程与核验方法

### 3.1 分析分工

自动工具只负责发现候选：faster-whisper GPU 给人声/报点/呼救/击杀关键词时间参考（不把角色台词当人声字幕，不把关键词当剪点）；PySceneDetect 给画面变化候选边界；Auto-Editor 给音频活动/静音参考（短暂安静不得删出战斗中间）；FFmpeg/FFprobe 探测、提音频、缩略图/联系表、渲染预览与成片。

Agent 必须做的判断：对每个候选向前、向后扩展检查，不只看事件几秒；至少检查开始、第一次交锋、每个主要转折、最后一次攻击和结果收束；识别"战斗仍在继续但画面变化不大"；对候选间隙做反向抽查；重叠候选去重但不剪掉同场后半段。

删除区间按长度分级核验（835 v11）：≤60 秒可用已有边界帧结论，但缝内有音频活动 ≥8 秒或转写战斗词时不适用豁免，必须加密复核（837 leakfix：1254–1281 短缝 27 秒因 audio_022 11.5 秒 + "小推车"漏掉追击战）；60–120 秒至少按 1/5fps 独立抽帧拼 1 张联系表；>120 秒必须独立抽帧核验全段，不得复用全程 1/10fps 稀疏图旧结论（835 即因此漏掉 383–448 整场战斗；837 leakfix：g1 348 秒复用全程 1/30fps 旧表，回阳境 81 秒仅分 3 帧被误判选人 UI；841：360–630 缺口 270 秒独立补抽 54 格，返魂光柱 + 聚集证伪为复活等待/跑图）。能量 hot（音频峰值）必须逐个对齐画面 + 转写，买货/换装/飞行风声等非战斗活动声不作交战证据（838 v1）；音频长活动段与"删除"初判矛盾时，按 839 v1 规则 2 秒步长加密复核，不得凭转写一句话带过（837 leakfix：audio_008 55 秒被"搜刮解密"一句带过丢整场回阳境，audio_010 34.5 秒被"灰屏呼喊"一句带过丢致死战）。删除段关键词交叉须逐条看语境：转写"打"字在闲聊中高频（带打招/半夜打），不可按字命中建段（840）；"救人"等状态词必须画面双重确认（无倒地/灰屏/返魂 UI 即观战闲聊，841）。删除段关键词命中后先量距下一场 engage 的时间距离：10 秒左右的战术铺垫属前置进入而非漏战（838 再审：T1017 距 engage 1028 仅 11 秒）；转写 JSON 用 Python 加载后正则扫，Bash 直接 grep 中文易乱码（838 再审）。

多路并行扫描时的区间切分（80–90 秒一路 + 5 秒重叠带）与重叠带互证规则按 `roughcut-launch.md §2` 执行，本文件判定准则不变。e1防漏扫升级（来源 `123\workflow_upgrade\e1_antimiss_scan.md`）：全片无差别1fps密集扫——删除段与已选段同一精度各扫一遍，不得复用旧稀疏图；每路80–90秒 + 段间5秒重叠带（`segN_end = segN+1_start + 5s`），重叠带双方独立证据互证；极限下限60秒/路（见 `roughcut-launch.md §2` e4引用，不再更细）；无战斗结论必须写"无战斗声明"双重否定，否则视为未扫完。

### 3.2 看图与取证规范

看图限流（全模型硬性红线，每轮持久有效，违者会话作废）：上游单次请求图片总数上限 50 张，累计口径（含历史已看 + 本轮新增：Read 图片 + 截图 + zoom 裁图）。看图前先 `ls`/`dir` 计数并跑 `scripts\check_image_budget.ps1` 做预算；单轮新增 ≤10 张（常规 4–10 张）；超 10 帧优先拼联系表（1 张表算 1 张），只对边界前后小批量补帧；每轮先写核实结论再开下一轮。失败教训：53 张单轮作废、`sess_03bfff9d` 累加作废。完整口径见根目录 `IMAGE_LIMIT.md` 与 `AGENTS.md §9`。

取证规范：审计帧必须带时间戳 provenance（834 v4）——文件名只有序号、来源时间戳不明的旧残留帧不得直接作证据，必须按已知源时间重抽（秒级时间戳命名）并拼联系表后复核，结论落盘写明帧来源区间。分辨率分级：初筛 320px 稀疏图 → 判定 640px → 定点 960px 高清逐秒（838 v1 逐级证伪链）。拼表工具：ffmpeg tile 对多图输入只进首帧，统一用 `scripts/make_contact_sheet.ps1`（xstack 方案）逐段拼表（837 v2）；子 Agent 无 PIL 环境时不要现装，用脚本方案。拼表末尾绿格为填充位（格数不满时），先数格数再报问题，预览全片解码通过即证非视频缺失（838 再审）。判读边界：段外删除帧混入段内表头时以 source_start 为界，段外帧只证删除正确（837 再审）；单帧异常（白茧/蓝盾/白闪）必须看前后连续帧，无三信号即非战斗，特效白闪前后为连续战斗画面、真冻结是全黑/静止重复帧（837/839 再审）。

### 3.3 自审停止线与交付门禁

自审迭代直到连续 3 遍发现不了问题再停（834 v4：在第 10 轮发现 007 头截断后重计，第 11/12/13 轮连过 3 轮冻结）。三遍视角必须错开：切点帧抓衔接错位、中段拼表抓长场挖空、转写交叉 + 结算链抓漏战与终局完整性，不复用同一批图作同一结论（838 再审）；再审沿用冻结版本不得改线时仍要落三份审计 writing evidence（837/838/839 再审）。时间线版本规则：任一边界改动即新版本号，旧预览立即过时归档、不得作为 QA 依据，QA 从新预览起计（839 v2：v1 含未定边界作废删抽帧，v3→v4 同理）。冻结判据以时间线 JSON + validate JSON + 现行预览三件套为准，deliverables 下旧 delivery 文件过期未更新不算冻结失败，但终版交付时须统一更新（837 再审）。

预览交付前逐条检查：每段开头能看懂为什么打；每段结尾能看懂结果；无战斗中途切走；无搜物资/跑图/等待残留；战斗内短暂停顿未挖空；衔接在上一场结果明确后；预览完整解码无黑帧/冻结/漂移/重复字幕；原始素材只读、派生全在任务目录。不满足先改源时间线和 `combat_episodes.json` 再重渲，不在错预览上叠剪。

状态因果链审计（837 leakfix）：在上述门禁之外，对成片做一次状态突变倒查——列出每一次玩家状态突变（获得神兽之力/变灵魂/阵亡/复活/进出回阳境），逐一要求"导致该状态的战斗必须在片中"；凡状态无来源，一律回删除段加密重查。旧门禁只查"开头可懂/结尾可懂"不查"状态有来源"，回阳境整场（神兽之力无来源）与致死战（变灵魂无死因）即因此漏网。回阳境/冥界复活赛是独立战斗场景（竞技场金环 + 石柱 + 暖光），320px 稀疏图易与备战选人 UI 混淆，边界帧必须用 ≥960px 高清 + 三信号裁决。

```json
}
```

`source_start` 和 `source_end` 才是渲染依据；`engage_start`、`impact_points` 和 `outcome_time` 用于解释、质检、卡点和后续特效。时间线保持源素材顺序，片段不得重叠或倒序。删除审计 `deleted_intervals[{start, end, category}]` 必须内嵌在时间线 JSON 本体，独立审计文件不算过门（835 v11）；任一边界改动须同步更新相邻删除段并重跑无缝覆盖检查（835 v13）。字段命名以 `scripts/validate_combat_timeline.py` 为准：episode 用 `engage_start`（非 `engage`），删除用 `deleted_intervals`（非 `deletions`/`gaps`）（838 v1）；落盘后用脚本实跑一遍验证，不要只看手工对账。

#### `excluded_inside`：段内挖洞与节目时长公式（861 v4 定案）

`excluded_inside` 是**源时间轴坐标**上的洞——一场战斗打到一半开了战利品面板、进了菜单、或者出现无信息停顿，就把那段挖掉（§3.3 把「战斗内短暂停顿未挖空」列为交付前必查违规项）。**节目时长必须扣掉它**：

```
program_seconds = Σ_episodes [ (source_end − source_start)
                             − Σ_holes (hole.end − hole.start) ]
```

每个带洞的 episode 按洞展开成若干连续切片，按顺序切、顺序 concat。

**861 v4 是这条规则的由来**：时间线声明挖 28.9 s，实际渲出 1090.5 s，`program_map_v4.json` 头部 `program_seconds_total = 1090.5` —— 三者一致，**渲染是对的**。但 `qa_gate.py` 当时用 `Σ(source_end − source_start)` 算期望值（1119.4），把一个正确的渲染判成 `preview_duration FAIL`；`read_episode_bounds.ps1` 只吐 `S=/E=` 对，4K 链路更是**结构上无法表达洞**。已用段内挖洞的任务不止 861：849（5 段）、860（8 段）也在用，所以这是每局都会复发的坑，不是单次意外。

规则在两处实现，**都从洞计算节目时长**：

| 实现 | 服务于 |
|---|---|
| `scripts/episode_geometry.py` | `qa_gate.py`、`validate_combat_timeline.py`、OTIO/XML/卡点导出 |
| `scripts/read_episode_bounds.ps1` | 4K 母版链路（**刻意不依赖 Python**） |

`scripts/test_insegment_holes.sh` 把同一批 fixture 喂给两边、逐段比对，任何一边单独改动都会红。`scripts/test_hole_render_e2e.sh` 再真渲一次 4K 验证成片时长等于扣洞后的值。**改这个公式必须同时改两边并跑这两个测试。**

洞的合法性由 `qa_gate.py` 的 `in_segment_holes` 门禁把守：越界、长度非正、或挖空整段即 FAIL。**重叠与相邻的洞不报错，按并集合并**——取并集没有歧义，报错只会让门禁拦住一个渲染器能正常处理的时间线（这正是原 bug 的同类病）。
